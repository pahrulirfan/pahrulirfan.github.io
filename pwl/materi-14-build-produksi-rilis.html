1. Build Produksi untuk API dan Antarmuka Indikator 8.1

Selama ini kalian menjalankan npm run dev — mode pengembangan: kode tidak diminifikasi, ada alat bantu debug ekstra, dan biasanya lebih lambat. Mode produksi dioptimalkan untuk pengguna sungguhan.

1.1 Build Frontend (React + Vite)

$ npm run build vite v6.0.0 building for production... ✓ 34 modules transformed. dist/index.html 0.46 kB dist/assets/index-C8f2a1B9.css 8.21 kB │ gzip: 2.31 kB dist/assets/index-DkT91xQz.js 142.83 kB │ gzip: 45.92 kB ✓ built in 1.84s

Hasilnya: folder dist/ berisi berkas statis (HTML, CSS, JS) yang sudah diminifikasi dan di-bundle — siap disajikan langsung tanpa Node.js sama sekali di sisi frontend.

1.2 Build Backend (Express)

Express tidak punya langkah "build" seperti Vite — kodenya dijalankan langsung oleh Node.js. Yang perlu disiapkan: memastikan hanya dependencies yang terpasang (bukan devDependencies seperti Vitest, Playwright).

$ npm ci --omit=dev added 87 packages in 3.2s $ NODE_ENV=production node index.js Server jalan di http://localhost:3000
NODE_ENV=production memberi tahu Express dan banyak pustaka untuk berperilaku dalam mode produksi — misalnya pesan galat Express default menjadi lebih ringkas, tidak menampilkan stack trace ke klien (ingat OWASP A05 dari Pertemuan 10).

2. Variabel Environment & Pengelolaan Rahasia Indikator 8.2

Ingat .env dari Pertemuan 1 dan JWT_SECRET dari Pertemuan 9? Aturan yang sama berlaku, dengan satu penambahan penting: nilai untuk produksi harus berbeda dari nilai untuk pengembangan.

Development (lokal)
DATABASE_URL=postgresql://localhost:5432/dev JWT_SECRET=rahasia-untuk-latihan NODE_ENV=development
Production (layanan rilis)
DATABASE_URL=postgresql://host-rilis.../db JWT_SECRET=<acak, panjang, unik> NODE_ENV=production
Mengapa harus berbeda? Kalau JWT_SECRET produksi sama dengan yang dipakai untuk latihan (yang mungkin pernah tertulis di dokumen, chat kelompok, atau bahkan ter-commit sebelumnya), siapa pun yang tahu nilai itu bisa memalsukan token yang tampak valid di sistem produksi sungguhan.

2.1 Cara Mengatur Variabel Environment di Layanan Hosting

Variabel environment produksi tidak disimpan dalam berkas .env yang di-commit — melainkan diatur lewat dashboard/pengaturan layanan hosting itu sendiri (nama menunya bervariasi tiap layanan: "Environment Variables", "Secrets", "Config Vars").

// src/lib/prisma.js — TIDAK BERUBAH!
import { PrismaClient } from '@prisma/client';
export const prisma = new PrismaClient();
// Prisma otomatis membaca DATABASE_URL dari process.env,
// entah nilainya datang dari .env lokal atau dashboard hosting
Ini keuntungan besar dari kebiasaan sejak Pertemuan 1: karena kode kalian SELALU membaca lewat process.env, tidak pernah menaruh nilai langsung di kode, berpindah dari lokal ke produksi hanya soal mengubah nilai variabel, bukan mengubah kode.

3. Basis Data pada Layanan Rilis & Migrasi Indikator 8.3

Basis data produksi biasanya disediakan sebagai layanan terpisah (bukan PostgreSQL lokal seperti Pertemuan 1). Setelah database produksi siap, migrasi (Pertemuan 6) perlu dijalankan terhadapnya.

$ # Migrasi ke database PRODUKSI — beda perintah dari saat pengembangan! DATABASE_URL="postgresql://host-produksi.../db" npx prisma migrate deploy 3 migrations found in prisma/migrations Applying migration `20260215120000_init` Applying migration `20260220083000_tambah_kelas_pendaftaran` Applying migration `20260301100000_tambah_user` All migrations have been successfully applied.
prisma migrate deploy, BUKAN prisma migrate dev, untuk produksi. migrate dev (yang dipakai sejak Pertemuan 6) bisa membuat migrasi baru dan mereset database saat konflik — berbahaya kalau dijalankan ke database produksi yang sudah berisi data sungguhan. migrate deploy hanya menjalankan migrasi yang sudah ada, tanpa membuat yang baru.

Seed di Produksi?

Data seed (Pertemuan 7) untuk pengembangan biasanya tidak dijalankan di produksi — nama-nama tiruan seperti "Andi", "Budi" tidak seharusnya muncul di sistem yang sesungguhnya dipakai. Cukup pastikan skema (struktur tabel) sudah benar lewat migrasi; datanya diisi oleh pengguna sungguhan.

Karena backend dan frontend adalah dua proyek terpisah (arsitektur sejak Pertemuan 1), keduanya dirilis secara terpisah pula — backend butuh proses Node.js yang terus berjalan, frontend cukup berkas statis yang bisa disajikan CDN mana pun.

4.2 Yang Perlu Disiapkan Sebelum Rilis

KomponenYang dibutuhkan layanan hosting
Backend (Express)Perintah start (node index.js), variabel environment (Section 2), port dari process.env.PORT
Frontend (React)Perintah build (npm run build), folder output (dist/)
Basis dataConnection string produksi, migrasi sudah dijalankan (Section 3)
Port tidak boleh di-hardcode. Layanan hosting biasanya menentukan port secara dinamis lewat variabel environment PORT. Kode app.listen(3000) harus diubah menjadi app.listen(process.env.PORT ?? 3000) — fallback ke 3000 hanya untuk pengembangan lokal.

4.4 Menjaga Proses Tetap Hidup: Process Manager

                
Layanan hosting seperti Railway atau Render menjalankan ulang aplikasi kalian sendiri saat ia berhenti — itu sudah termasuk dalam layanan. Tapi bagaimana kalau aplikasi dirilis ke server sendiri (VPS, atau server kampus)? Di sana, node index.js yang kalian jalankan lewat SSH akan mati begitu sesi SSH ditutup. Dan kalau aplikasi crash pukul tiga pagi, tidak ada yang menyalakannya kembali sampai ada yang menyadarinya.

                
Tugas itu diambil alih oleh process manager. PM2 adalah yang paling umum di ekosistem Node.js.


                
$ npm install -g pm2
$ pm2 start npm --name "mahasiswa-api" -- run start
[PM2] Starting /usr/bin/npm in fork_mode (1 instance)
[PM2] Done.


                
Mari kita bedah perintahnya. pm2 start npm berarti yang dijalankan adalah npm, bukan node langsung. --name "mahasiswa-api" memberi nama proses agar bisa dirujuk pada perintah berikutnya. Dan -- memisahkan argumen milik PM2 dari argumen yang diteruskan ke npm; segala setelahnya (run start) diberikan apa adanya kepada npm.


                

                    
PerintahKegunaan

                    
pm2 listMelihat semua proses beserta status dan penggunaan memorinya

                    
pm2 logs mahasiswa-apiMembaca keluaran aplikasi — tempat pertama yang dilihat saat ada masalah

                    
pm2 restart mahasiswa-apiMemuat ulang setelah kode baru di-pull

                    
pm2 stop mahasiswa-apiMenghentikan tanpa menghapus dari daftar

                    
pm2 startup lalu pm2 saveMembuat proses ikut hidup kembali setelah server di-reboot

                


                
Dua baris terakhir mudah terlewat dan penting. pm2 startup mendaftarkan PM2 ke sistem operasi, sedangkan pm2 save menyimpan daftar proses yang sedang berjalan. Tanpa keduanya, aplikasi memang selamat dari crash, tetapi tidak selamat dari server yang dinyalakan ulang.


                

                    Untuk tugas mata kuliah ini, PM2 tidak wajib — rilis ke layanan hosting yang sudah menangani hal ini jauh lebih sederhana, dan itu yang dipakai pada praktik di bawah. Bagian ini ada supaya kalian mengerti apa yang sebenarnya dikerjakan layanan hosting di balik layar, dan siap ketika suatu saat harus merilis ke server sendiri.

5. Berkas Petunjuk Penyerahan Indikator 8.7

Produk kelompok harus bisa dipasang dan dijalankan oleh orang lain — dosen penguji, misalnya — dari salinan bersih repositori, tanpa penjelasan lisan tambahan. Ini adalah jalur cadangan kalau layanan hosting daring tidak bisa diakses saat penilaian.

Struktur README.md yang Wajib Ada

# Aplikasi Manajemen Mahasiswa

## Anggota Kelompok
- Nama (NIM) — peran/bagian yang dikerjakan
- ...

## Tumpukan Teknologi
Node.js 24, Express, Prisma + PostgreSQL, React + Vite

## Menjalankan di Komputer Lokal (Jalur Cadangan)

### Backend
```
cd backend
npm ci
cp .env.example .env    # isi DATABASE_URL dan JWT_SECRET
npx prisma migrate deploy
npx prisma db seed      # opsional, mengisi data contoh
npm start
```

### Frontend
```
cd frontend
npm ci
npm run dev
```

## Alamat Rilis Publik
- Frontend: https://antarmuka-mahasiswa.contoh-hosting.app
- Backend:  https://api-mahasiswa.contoh-hosting.app

## Akun untuk Menguji
- Admin: admin@contoh.id / (kata sandi diberikan terpisah ke dosen)
- Mahasiswa: mahasiswa@contoh.id / (idem)

6. Praktik: Rilis Aplikasi Kelompok Latihan

Langkah 1 — Siapkan Backend untuk Produksi

// index.js — pastikan port dinamis
const PORT = process.env.PORT ?? 3000;
app.listen(PORT, () => console.log(`Server jalan di port ${PORT}`));

Langkah 2 — Buat Basis Data Produksi

Sediakan basis data PostgreSQL di layanan hosting pilihan kelompok, salin connection string-nya.

Langkah 3 — Atur Variabel Environment di Dashboard Hosting

Masukkan DATABASE_URL, JWT_SECRET (nilai BARU, jangan sama dengan yang dipakai lokal), dan NODE_ENV=production lewat dashboard layanan hosting — bukan dengan meng-commit .env.

Langkah 4 — Jalankan Migrasi Produksi

$ DATABASE_URL="..." npx prisma migrate deploy

Langkah 5 — Rilis Backend, lalu Frontend

Sambungkan repositori ke layanan hosting pilihan kelompok. Perbarui CORS (Section 4.3) begitu backend punya alamat publik. Baru rilis frontend, dengan alamat API produksi dikonfigurasi lewat variabel environment Vite (VITE_API_URL).

Langkah 6 — Lengkapi Berkas Penyerahan

Perbarui README.md (Section 5) dengan alamat rilis publik dan akun uji. Pastikan .env.example, SECURITY.md, dan API.md sudah mutakhir.

Langkah 7 — Uji Jalur Cadangan

Minta satu anggota kelompok meng-clone repositori ke folder BARU (bukan folder kerja biasa), lalu ikuti README.md dari nol, tanpa bertanya ke anggota lain. Kalau berhasil berjalan, jalur cadangan terbukti bekerja.

Selesai kalau: aplikasi bisa diakses lewat alamat publik, ATAU (kalau layanan hosting bermasalah saat pengujian) bisa dipasang penuh dari salinan bersih repositori mengikuti README.md saja.
Menuju Pertemuan 15: dengan aplikasi sudah live, pertemuan berikutnya mengaudit kualitasnya — seberapa cepat dimuat, dan seberapa bisa diakses pengguna dengan keterbatasan.
