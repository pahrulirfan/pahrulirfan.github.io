1. Middleware dan Urutannya Indikator 3.4

Apa itu Middleware?

Middleware adalah fungsi yang berdiri di antara permintaan masuk dan handler akhir. Setiap middleware bisa memeriksa, mengubah, atau menolak permintaan sebelum diteruskan ke middleware berikutnya — persis seperti middleware di Laravel (auth, throttle, dsb), hanya saja di Express kalian menulis dan menyusun sendiri urutannya secara eksplisit.

1.1 Anatomi Middleware

function contohMiddleware(req, res, next) {
    console.log(`${req.method} ${req.path}`);   // lakukan sesuatu
    next();                                // WAJIB dipanggil agar lanjut ke berikutnya
}

app.use(contohMiddleware);
Lupa memanggil next() adalah kesalahan nomor satu. Kalau next() tidak dipanggil, permintaan menggantung selamanya — klien menunggu tanpa batas waktu sampai time out, tanpa pesan error yang jelas.

1.2 Alur Middleware: Sebuah Pipeline

Bayangkan permintaan sebagai bola yang menggelinding melewati serangkaian pos pemeriksaan. Setiap pos boleh meloloskan bola (next()) atau menghentikannya (mengirim tanggapan langsung).

1.4 Urutan SANGAT Menentukan

// ❌ SALAH — express.json() dipasang TERLAMBAT
app.post('/mahasiswa', (req, res) => {
    console.log(req.body);   // undefined! belum diurai
});
app.use(express.json());   // terlambat, handler di atas sudah lebih dulu terdaftar

// ✅ BENAR — middleware global dipasang PALING AWAL
app.use(express.json());
app.use(logger);
app.post('/mahasiswa', (req, res) => {
    console.log(req.body);   // ✅ sudah terurai
});

1.5 Middleware Khusus Satu Rute

function cekToken(req, res, next) {
    const token = req.headers.authorization;
    if (!token) {
        return res.status(401).json({ error: { pesan: 'Token diperlukan' } });
    }
    next();
}

// Middleware disisipkan sebagai argumen tambahan, hanya berlaku di rute ini
app.delete('/mahasiswa/:id', cekToken, (req, res) => {
    // hanya sampai ke sini kalau cekToken() memanggil next()
});

1.6 Tingkat Aplikasi vs Tingkat Router

Sejauh ini semua middleware kita pasang di app — itu disebut middleware tingkat aplikasi (application-level): berlaku untuk setiap permintaan yang masuk. Express juga menyediakan middleware tingkat router (router-level), yang hanya berlaku bagi sekelompok rute yang dikumpulkan dalam satu express.Router().

 Tingkat aplikasiTingkat router
Dipasang padaapp.use(...)router.use(...)
Cakupanseluruh aplikasihanya rute di dalam router itu
Cocok untukparsing body, CORS, log, penanganan errorcek token untuk satu modul, validasi khusus, prefiks URL

// routes/mahasiswa.js — satu file untuk satu kelompok sumber daya
import express from 'express';
const router = express.Router();

// Middleware tingkat router: hanya jalan untuk rute di file ini
router.use((req, res, next) => {
    console.log('[mahasiswa]', req.method, req.originalUrl);
    next();
});

router.get('/', (req, res) => { /* GET /mahasiswa */ });
router.get('/:id', (req, res) => { /* GET /mahasiswa/:id */ });

export default router;
// index.js — router dipasang di satu titik, prefiks ditentukan di sini
import mahasiswaRouter from './routes/mahasiswa.js';

app.use(express.json());              // tingkat aplikasi: semua rute
app.use('/mahasiswa', mahasiswaRouter); // tingkat router: hanya /mahasiswa/*

Mari kita bedah keuntungannya. Pertama, prefiks ditulis sekali — di dalam routes/mahasiswa.js kita cukup menulis '/' dan '/:id', bukan '/mahasiswa' dan '/mahasiswa/:id'. Kalau suatu saat alamatnya berubah menjadi /api/v1/mahasiswa, hanya satu baris di index.js yang disunting.

Kedua, middleware ikut terkurung. Middleware log di atas tidak akan mengotori rute lain. Di Pertemuan 9 nanti, middleware pemeriksa token akan dipasang persis di sini — sehingga seluruh rute mahasiswa terlindungi sekaligus tanpa menyentuh rute publik seperti /login.

Kaitan dengan bagian 3. Struktur proyek yang kita rapikan pada bagian 3 nanti memakai pola ini: satu file router per sumber daya di dalam folder routes/, lalu semuanya dipasang dari index.js.

2. Penanganan Error Terpusat Indikator 3.5

Di Pertemuan 4, setiap handler menangani errornya sendiri-sendiri dengan if berulang. Express punya cara yang jauh lebih rapi: error-handling middleware — satu tempat tunggal yang menangkap semua error dari seluruh aplikasi.

2.1 Error-Handling Middleware

Bentuknya persis middleware biasa, hanya dengan empat parameter (bukan tiga). Express mengenali ini secara khusus lewat jumlah parameternya:

// src/middleware/errorHandler.js
export function errorHandler(err, req, res, next) {   // 4 parameter!
    console.error(err);   // log untuk developer

    const status = err.status ?? 500;
    res.status(status).json({
        error: {
            pesan: err.message ?? 'Terjadi kesalahan pada server',
            kode: err.kode ?? 'INTERNAL_ERROR'
        }
    });
}

// index.js — DIPASANG PALING TERAKHIR, setelah semua rute
app.use(errorHandler);
Posisi sangat menentukan: error-handling middleware harus didaftarkan setelah semua app.get/post/put/delete. Express mencari middleware error hanya ketika ada yang memanggil next(err) atau melempar error — dan ia mencarinya ke bawah dari titik kegagalan.

2.2 Kelas Error Kustom (Sambungan dari Pertemuan 3)

Ingat kelas error kustom yang dibuat di Pertemuan 3 untuk menangani respons fetch? Pola yang sama dipakai di sisi server:

// src/utils/AppError.js
export class AppError extends Error {
    constructor(status, pesan, kode) {
        super(pesan);
        this.status = status;
        this.kode = kode;
    }
}

// Dipakai di route handler
app.get('/mahasiswa/:id', (req, res, next) => {
    const m = mahasiswa.find(x => x.id === Number(req.params.id));
    if (!m) {
        return next(new AppError(404, 'Mahasiswa tidak ditemukan', 'NOT_FOUND'));
    }
    res.json({ data: m });
});

2.3 Menangani Error pada Handler async

Ini jebakan yang sangat sering: Express tidak otomatis menangkap error yang dilempar dari dalam fungsi async. Ingat Materi 2 — error di dalam async perlu ditangani secara eksplisit.

// ❌ Error di sini TIDAK tertangkap errorHandler — server bisa crash
app.get('/mahasiswa/:id', async (req, res) => {
    const m = await ambilDariDatabase(req.params.id);   // kalau ini reject...
    res.json({ data: m });
});

// ✅ Bungkus dengan try/catch, teruskan ke next()
app.get('/mahasiswa/:id', async (req, res, next) => {
    try {
        const m = await ambilDariDatabase(req.params.id);
        res.json({ data: m });
    } catch (err) {
        next(err);   // diteruskan ke errorHandler, TIDAK dilempar langsung
    }
});

// ✅✅ Lebih rapi — pembungkus generik (dipakai seterusnya di mata kuliah ini)
const asyncHandler = (fn) => (req, res, next) => {
    Promise.resolve(fn(req, res, next)).catch(next);
};

app.get('/mahasiswa/:id', asyncHandler(async (req, res) => {
    const m = await ambilDariDatabase(req.params.id);
    res.json({ data: m });
}));
asyncHandler akan dipakai terus mulai sekarang — membungkus setiap handler async sekali, sehingga tidak perlu menulis try/catch berulang-ulang di setiap rute. Pola ini menjadi standar di Pertemuan 6 dan seterusnya.

2.4 Validasi Masukan sebagai Middleware

Sampai di sini penanganan error sudah terpusat. Sekarang pertanyaannya: di mana masukan dari klien seharusnya diperiksa? Kalau pemeriksaan ditaruh di dalam setiap handler, kodenya akan berulang dan mudah terlewat. Cara yang lebih rapi: jadikan validasi itu sendiri sebagai middleware, dipasang sebelum handler.

Menulis aturan validasi dengan if bertumpuk cepat menjadi panjang. Pustaka Joi menggantinya dengan skema — deskripsi bentuk data yang kita harapkan.

$ npm install joi
// validators/mahasiswa.js
import Joi from 'joi';

export const skemaMahasiswa = Joi.object({
    nim:     Joi.string().length(11).required(),
    nama:    Joi.string().min(3).max(100).required(),
    email:   Joi.string().email().required(),
    semester: Joi.number().integer().min(1).max(14).required(),
});

Mari kita bedah skemanya. Joi.object({...}) mendeskripsikan sebuah objek; setiap properti diisi rangkaian method yang dirantai. Joi.string() menetapkan tipe, .length(11) menetapkan panjang persis, dan .required() menandai properti itu wajib ada. Rantai ini dibaca dari kiri ke kanan seperti kalimat: “nim adalah string, panjangnya 11, dan wajib diisi”.

Skema diperiksa dengan skema.validate(data), yang mengembalikan objek hasil. Bila properti error pada hasil itu bukan undefined, berarti validasi gagal, dan error.message menjelaskan alasannya.

// middlewares/validasi.js — satu pabrik middleware, dipakai semua rute
import { AppError } from '../errors/AppError.js';

export const validasi = (skema) => (req, res, next) => {
    const { error, value } = skema.validate(req.body, { abortEarly: false });

    if (error) {
        // Semua pesan digabung, lalu diserahkan ke errorHandler lewat next()
        const pesan = error.details.map((d) => d.message).join('; ');
        return next(new AppError(pesan, 400));
    }

    req.body = value;   // pakai nilai yang sudah dibersihkan Joi
    next();
};

Perhatikan tiga keputusan pada kode di atas. validasi bukan middleware, melainkan fungsi yang mengembalikan middleware — sehingga satu file ini bisa dipakai untuk skema apa pun. Opsi abortEarly: false membuat Joi melaporkan seluruh kesalahan sekaligus, bukan berhenti di kesalahan pertama; bagi pengguna formulir, ini jauh lebih ramah. Dan yang terpenting: kegagalan validasi tidak dibalas langsung dengan res.status(400), melainkan diserahkan ke next(new AppError(...)) — supaya bentuk tanggapan errornya tetap seragam dengan error lain, persis seperti yang kita bangun di 2.1–2.2.

// routes/mahasiswa.js — validasi dipasang di antara rute dan handler
router.post('/', validasi(skemaMahasiswa), asyncHandler(async (req, res) => {
    // Sampai di sini req.body DIJAMIN sudah sesuai skema
    const baru = await mahasiswaService.tambah(req.body);
    res.status(201).json({ data: baru });
}));
Handler menjadi bersih. Karena validasi sudah dijamin oleh middleware di depannya, isi handler tinggal mengurus satu hal: logika bisnisnya. Inilah alasan validasi ditaruh sebagai middleware, bukan di dalam handler.
Validasi sisi klien bukan pengganti. Pemeriksaan di formulir React (Pertemuan 11) hanya membantu pengguna; siapa pun tetap bisa mengirim permintaan langsung ke API lewat cURL atau REST Client. Validasi sisi server adalah satu-satunya yang benar-benar menjaga data — ini akan kita perdalam di Pertemuan 10 sebagai bagian dari OWASP.

3. Struktur Proyek: Pemisahan Tanggung Jawab Indikator 3.6

Selama ini semua kode masih ada di index.js. Untuk proyek yang akan tumbuh sampai akhir semester, kita pisahkan menjadi tiga lapis — padanan MVC di Laravel, dengan nama yang lebih menjelaskan perannya:

// src/routes/mahasiswa.routes.js — HANYA routing
import { Router } from 'express';
import * as ctrl from '../controllers/mahasiswa.controller.js';
const router = Router();

router.get('/', ctrl.daftar);
router.get('/:id', ctrl.detail);
router.post('/', ctrl.buat);

export default router;

// src/controllers/mahasiswa.controller.js — HANYA req/res, tidak ada logika bisnis
import * as service from '../services/mahasiswa.service.js';
import { asyncHandler } from '../utils/asyncHandler.js';

export const daftar = asyncHandler(async (req, res) => {
    const hasil = await service.daftarMahasiswa(req.query);
    res.json({ data: hasil });
});

export const buat = asyncHandler(async (req, res) => {
    const baru = await service.buatMahasiswa(req.body);
    res.status(201).json({ data: baru });
});

// src/services/mahasiswa.service.js — LOGIKA BISNIS ada di sini
import * as data from '../data/mahasiswa.data.js';
import { AppError } from '../utils/AppError.js';

export async function buatMahasiswa(input) {
    if (!input.nim || !input.nama) {
        throw new AppError(422, 'nim dan nama wajib diisi', 'VALIDATION_ERROR');
    }
    return data.simpan(input);
}
Mengapa dipisah begini? Kalau Pertemuan 6 mengganti data/mahasiswa.data.js dari array biasa menjadi Prisma, controller dan service tidak perlu diubah sama sekali. Perubahan terisolasi hanya di satu lapis. Ini juga memudahkan pengujian otomatis di Pertemuan 13 — service bisa diuji tanpa harus menjalankan server HTTP sungguhan.

4. Menguji API dengan REST Client Indikator 3.7

Sejauh ini kalian menguji lewat curl atau browser. Untuk API dengan banyak endpoint, cara yang lebih rapi adalah menyimpan kumpulan permintaan dalam sebuah file .http yang bisa dijalankan ulang kapan saja.

4.1 Ekstensi REST Client (VS Code)

Pasang ekstensi REST Client (humao.rest-client) di VS Code. Buat file requests.http:

### Daftar semua mahasiswa
GET http://localhost:3000/mahasiswa

### Filter berdasarkan semester
GET http://localhost:3000/mahasiswa?semester=6

### Detail satu mahasiswa
GET http://localhost:3000/mahasiswa/1

### Mahasiswa yang tidak ada — harus 404
GET http://localhost:3000/mahasiswa/999

### Buat mahasiswa baru
POST http://localhost:3000/mahasiswa
Content-Type: application/json

{
    "nim": "F1D021010",
    "nama": "Fajar",
    "ipk": 3.6,
    "semester": 6
}

### Buat TANPA nama — harus 422
POST http://localhost:3000/mahasiswa
Content-Type: application/json

{
    "nim": "F1D021011"
}
Cara pakai: setiap blok dipisah tiga tanda pagar ###. Klik "Send Request" yang muncul di atas tiap blok. Hasilnya tampil di panel terpisah tanpa harus mengetik ulang perintah curl.

4.2 Mengapa File .http Disimpan di Repositori

  • Rekan satu kelompok bisa memakai koleksi permintaan yang sama tanpa menyusun ulang
  • Berfungsi sebagai dokumentasi hidup — bisa dibaca dan dijalankan, bukan sekadar teks
  • Kasus uji "harus gagal" (seperti 404 dan 422 di atas) ikut tersimpan, bukan hanya kasus yang berhasil
Kebiasaan yang wajib dibangun mulai sekarang: setiap kali menambah endpoint baru, tambahkan juga permintaan ujinya di requests.http — termasuk minimal satu kasus yang sengaja gagal (data tidak valid, id tidak ada). Kebiasaan ini akan langsung terpakai lagi saat menyusun pengujian otomatis di Pertemuan 13.

5. Praktik: Merapikan API Mahasiswa Latihan

Ambil proyek api-mahasiswa dari Pertemuan 4, lalu rapikan menjadi struktur berlapis dengan middleware dan penanganan error terpusat.

Langkah 1 — Buat AppError dan asyncHandler

Salin persis kode AppError (Section 2.2) dan asyncHandler (Section 2.3) ke src/utils/.

Langkah 2 — Pindahkan Data

// src/data/mahasiswa.data.js
const mahasiswa = [
    { id: 1, nim: "F1D021001", nama: "Andi", ipk: 3.75, semester: 6 },
    { id: 2, nim: "F1D021002", nama: "Budi", ipk: 3.20, semester: 6 }
];

export function semua() { return mahasiswa; }
export function cariById(id) { return mahasiswa.find(m => m.id === id); }
export function simpan(input) {
    const baru = { id: mahasiswa.length + 1, ...input };
    mahasiswa.push(baru);
    return baru;
}

Langkah 3 — Service dengan Validasi

// src/services/mahasiswa.service.js
import * as data from '../data/mahasiswa.data.js';
import { AppError } from '../utils/AppError.js';

export async function daftarMahasiswa(query) {
    const semua = data.semua();
    if (query.semester) {
        return semua.filter(m => m.semester === Number(query.semester));
    }
    return semua;
}

export async function detailMahasiswa(id) {
    const m = data.cariById(Number(id));
    if (!m) throw new AppError(404, 'Mahasiswa tidak ditemukan', 'NOT_FOUND');
    return m;
}

export async function buatMahasiswa(input) {
    if (!input.nim || !input.nama) {
        throw new AppError(422, 'nim dan nama wajib diisi', 'VALIDATION_ERROR');
    }
    return data.simpan(input);
}

Langkah 4 — index.js Menjadi Sangat Ringkas

import express from 'express';
import mahasiswaRoutes from './src/routes/mahasiswa.routes.js';
import { errorHandler } from './src/middleware/errorHandler.js';

const app = express();
app.use(express.json());
app.use('/mahasiswa', mahasiswaRoutes);
app.use(errorHandler);   // SELALU paling terakhir

app.listen(3000, () => console.log('Server jalan di http://localhost:3000'));

Langkah 5 — Buat requests.http dan Uji

Salin koleksi permintaan pada Section 4.1, sesuaikan dengan data kalian, lalu jalankan satu per satu memakai REST Client.

Selesai kalau: struktur folder mengikuti Section 3, semua error (404, 422) melewati errorHandler yang sama, dan seluruh permintaan di requests.http memberi hasil yang sesuai.

Latihan Mandiri

  1. Tambahkan middleware logger sederhana yang mencatat method, path, dan waktu tiap permintaan ke konsol.
  2. Pindahkan PUT dan DELETE dari Pertemuan 4 ke struktur berlapis yang baru (routes → controller → service → data).
  3. Tambahkan penanganan untuk error yang tidak terduga (misalnya data.simpan() melempar TypeError biasa, bukan AppError) — pastikan errorHandler tetap mengembalikan 500 dengan format yang konsisten, bukan meng-crash server.
Menuju Pertemuan 6: lapis data/ yang kalian buat hari ini masih berupa array di memori — hilang setiap kali server di-restart. Pertemuan 6 mengganti lapis ini dengan Prisma yang tersambung ke PostgreSQL sungguhan, tanpa mengubah controller atau service sama sekali.
