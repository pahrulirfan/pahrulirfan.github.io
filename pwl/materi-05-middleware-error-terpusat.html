1. Router Indikator 3.6

Bagian ini dikerjakan di proyek yang sama, api-mahasiswa dari Pertemuan 4. Kita mulai dengan Router: dijelaskan dulu, lalu dipraktikkan. Hasilnya menjadi wadah tempat middleware di Section 2 dipasang.

1.1 Apa itu Router?

Di Pertemuan 4 semua rute ditulis langsung di index.js lewat app.get(...) dan app.post(...). Untuk satu sumber daya itu masih nyaman. Tetapi bayangkan nanti ada juga /dosen dan /mata-kuliah: index.js menjadi penuh sesak, dan awalan '/mahasiswa' harus diulang di setiap rute.

Router adalah “mini-aplikasi” yang menampung sekelompok rute. Ia punya get, post, dan use seperti app, tetapi hanya mengurus rutenya sendiri. Rute yang sekelompok (misalnya semua rute mahasiswa) dikumpulkan di satu router, biasanya satu file, lalu router itu dipasang ke aplikasi pada satu awalan alamat.

 Tanpa router (Pertemuan 4)Dengan router
Tempat rutesemua di index.jssatu file per sumber daya
Awalan alamat'/mahasiswa' diulang di tiap ruteditulis sekali, saat router dipasang
Menulis ruteapp.get('/mahasiswa/:id', ...)router.get('/:id', ...)
Padanan Laravel—Route::prefix('mahasiswa')->group(...)

Bentuk dasarnya hanya tiga langkah: buat router, isi dengan rute, lalu pasang ke aplikasi.

const router = express.Router();                  // 1. buat router
router.get('/', (req, res) => { /* ... */ });     // 2. isi dengan rute (path relatif terhadap awalan)
app.use('/mahasiswa', router);                    // 3. pasang ke aplikasi pada awalan '/mahasiswa'

Baris ketiga dibaca: “setiap permintaan yang alamatnya diawali /mahasiswa, serahkan ke router”. Sisa alamatnya dicocokkan di dalam router, jadi GET /mahasiswa cocok dengan '/', dan GET /mahasiswa/2 cocok dengan '/:id'. Sekarang kita praktikkan di proyek.

1.2 Praktik: Pindahkan Rute ke Router

Langkah 0 — Siapkan proyek (lanjutan Pertemuan 4)

Buka folder api-mahasiswa hasil Pertemuan 4 (sampai Section 7.3). Kalau belum punya, selesaikan dulu bagian itu. Kondisi awalnya:

api-mahasiswa/
index.js // semua rute + helper kirimError ada di sini
package.json // "type": "module", script dev
src/data/mahasiswa.js // array 3 mahasiswa
$ cd api-mahasiswa $ npm run dev

Di terminal lain, pastikan API masih berjalan seperti akhir Pertemuan 4. Tanda " pada URL penting, karena tanpa itu terminal (zsh) menganggap ? sebagai karakter khusus:

$ curl "http://localhost:3000/mahasiswa?semester=6" {"data":[{"id":1,"nim":"F1D021001","nama":"Andi","ipk":3.75,"semester":6},{"id":2,...}],"meta":{"total":2}}
Checkpoint: GET /mahasiswa dan GET /mahasiswa/2 menjawab dengan benar. Mulai dari sini, perilaku API tidak berubah; yang kita ubah hanya cara kodenya ditata, lalu dilindungi dengan middleware.

Langkah 1 — Buat file router

$ mkdir -p src/routes

Buat file src/routes/mahasiswa.routes.js. Isinya rute-rute dari index.js, dengan dua perbedaan: dibuat lewat express.Router(), dan path-nya cukup '/' serta '/:id' (tanpa /mahasiswa). Helper kirimError ikut dipindah ke sini karena hanya dipakai di file ini.

import express from 'express';
import { mahasiswa } from '../data/mahasiswa.js';

const router = express.Router();

// Helper: semua error memakai bentuk { error: { pesan, kode } }
const kirimError = (res, status, kode, pesan) =>
    res.status(status).json({ error: { pesan, kode } });

// GET /mahasiswa  atau  GET /mahasiswa?semester=6
router.get('/', (req, res) => {
    const { semester } = req.query;
    const hasil = semester
        ? mahasiswa.filter(m => m.semester === Number(semester))
        : mahasiswa;
    res.json({ data: hasil, meta: { total: hasil.length } });
});

// GET /mahasiswa/:id
router.get('/:id', (req, res) => {
    const m = mahasiswa.find(x => x.id === Number(req.params.id));
    if (!m) {
        return kirimError(res, 404, 'NOT_FOUND', 'Mahasiswa tidak ditemukan');
    }
    res.json({ data: m });
});

// POST /mahasiswa
router.post('/', (req, res) => {
    const { nim, nama, ipk, semester } = req.body ?? {};
    if (!nim || !nama) {
        return kirimError(res, 422, 'VALIDATION_ERROR', 'nim dan nama wajib diisi');
    }
    const baru = { id: mahasiswa.length + 1, nim, nama, ipk: ipk ?? 0, semester: semester ?? 1 };
    mahasiswa.push(baru);
    res.status(201).json({ data: baru });
});

export default router;

Langkah 2 — Pasang router di index.js

Hapus semua app.get('/mahasiswa'...) dan app.post('/mahasiswa'...) beserta helper kirimError dari index.js, sehingga tinggal seperti ini:

import express from 'express';
import mahasiswaRoutes from './src/routes/mahasiswa.routes.js';

const app = express();
app.use(express.json());

app.get('/', (req, res) => {
    res.send('Halo dari Express!');
});

app.use('/mahasiswa', mahasiswaRoutes);   // router dipasang di sini, lengkap dengan awalannya

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, (err) => {
    if (err) {
        console.error('Gagal menjalankan server:', err.message);
        process.exit(1);
    }
    console.log(`Server jalan di http://localhost:${PORT}`);
});

Perhatikan baris app.use('/mahasiswa', mahasiswaRoutes): awalan /mahasiswa sekarang hanya ditulis di sini. Kalau suatu saat alamatnya berubah menjadi /api/v1/mahasiswa, hanya satu baris ini yang disunting.

Langkah 3 — Uji ulang

$ curl http://localhost:3000/mahasiswa/2 {"data":{"id":2,"nim":"F1D021002","nama":"Budi","ipk":3.2,"semester":6}} $ curl http://localhost:3000/mahasiswa/99 {"error":{"pesan":"Mahasiswa tidak ditemukan","kode":"NOT_FOUND"}}
Checkpoint: hasilnya sama persis dengan sebelum dipindah. Rute sudah berada di router, index.js tinggal mengatur aplikasi. Inilah wadah tempat middleware-middleware berikutnya kita pasang.

2. Middleware Indikator 3.4

Router di Section 1 sudah siap sebagai wadah. Sekarang kita menambahkan middleware ke proyek yang sama, mulai dari kondisi akhir Section 1: dijelaskan dulu apa itu middleware, lalu dipraktikkan satu per satu (logger, lalu cekApiKey).

2.1 Apa itu Middleware?

Middleware adalah fungsi yang berdiri di antara permintaan masuk dan handler akhir. Setiap middleware bisa memeriksa, mengubah, atau menolak permintaan sebelum diteruskan ke middleware berikutnya — persis seperti middleware di Laravel (auth, throttle, dsb), hanya saja di Express kalian menulis dan menyusun sendiri urutannya secara eksplisit.

Kalian sebenarnya sudah memakainya: app.use(express.json()) di Pertemuan 4 adalah middleware yang mengurai body JSON menjadi req.body.

Anatomi

function contohMiddleware(req, res, next) {
    console.log(`${req.method} ${req.path}`);   // lakukan sesuatu
    next();                                      // WAJIB dipanggil agar lanjut ke berikutnya
}

app.use(contohMiddleware);
Lupa memanggil next() adalah kesalahan nomor satu. Kalau next() tidak dipanggil (dan tidak ada tanggapan yang dikirim), permintaan menggantung selamanya — klien menunggu tanpa batas waktu sampai time out, tanpa pesan error yang jelas.

2.2 Alur Middleware: Sebuah Pipeline

Bayangkan permintaan sebagai bola yang menggelinding melewati serangkaian pos pemeriksaan. Setiap pos boleh meloloskan bola (next()) atau menghentikannya (mengirim tanggapan langsung).

express.json()

→
cek API key

→

→

logika utama

Kalau salah satu pos menolak (misalnya API key salah), bola berhenti di situ dan langsung mengirim tanggapan error — tidak pernah sampai ke route handler. Dua pos pertama kita buat di 2.4 dan 2.6.

2.4 Praktik: Middleware Pertama, logger

Saat ini api-mahasiswa sudah bisa melayani permintaan, tetapi terminal server sunyi. Kita tidak tahu endpoint mana yang dipanggil klien (Postman, curl, nanti aplikasi React), kapan, dan apa hasilnya. Kalau ada yang mengeluh “data saya tidak muncul”, kita hanya bisa menebak. Middleware logger menyelesaikannya: setiap permintaan ke API dicatat satu baris di terminal server.

Bagi api-mahasiswa, ini berarti GET /, GET /mahasiswa, GET /mahasiswa/2, POST /mahasiswa, dan permintaan lain, semuanya akan melewati logger sebelum sampai ke router.

Langkah 1 — Buat file logger

$ mkdir -p src/middleware
// src/middleware/logger.js
export function logger(req, res, next) {
    console.log(`${req.method} ${req.originalUrl}`);
    next();
}
Bagian kodeArtinya
(req, res, next)Tiga parameter middleware: permintaan masuk, alat menjawab, dan penyambung ke langkah berikutnya
req.methodMethod HTTP permintaan: GET, POST, dst.
req.originalUrlAlamat lengkap sebagaimana diminta klien, termasuk query string (/mahasiswa?semester=6). Dipilih daripada req.path yang tidak memuat query
next()Meneruskan permintaan ke langkah berikutnya (middleware lain atau router). Tanpa ini permintaan berhenti di sini

Langkah 2 — Pasang di index.js

Berikut index.js proyek kita sekarang, dengan dua baris baru (bertanda ← baru):

// index.js
import express from 'express';
import mahasiswaRoutes from './src/routes/mahasiswa.routes.js';
import { logger } from './src/middleware/logger.js';     // ← baru

const app = express();
app.use(express.json());
app.use(logger);                                         // ← baru: setelah express.json(), sebelum rute

app.get('/', (req, res) => {
    res.send('Halo dari Express!');
});

app.use('/mahasiswa', mahasiswaRoutes);

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, (err) => {
    if (err) {
        console.error('Gagal menjalankan server:', err.message);
        process.exit(1);
    }
    console.log(`Server jalan di http://localhost:${PORT}`);
});

app.use(logger) tanpa alamat berarti “jalankan untuk semua permintaan”. Posisinya disengaja: sesudah express.json() dan sebelum rute. Karena Express menjalankan middleware dari atas ke bawah, hanya yang berada di atas rute yang sempat berjalan sebelum rute menjawab (alasan lengkapnya di 2.5).

Langkah 3 — Uji

Pastikan server berjalan (npm run dev), lalu dari terminal lain kirim beberapa permintaan ke api-mahasiswa:

$ curl http://localhost:3000/ $ curl http://localhost:3000/mahasiswa $ curl "http://localhost:3000/mahasiswa?semester=6" $ curl http://localhost:3000/mahasiswa/2 $ curl http://localhost:3000/mahasiswa/99

Pindah ke terminal tempat server berjalan. Sekarang ada satu baris untuk tiap permintaan tadi:

Server jalan di http://localhost:3000 GET / GET /mahasiswa GET /mahasiswa?semester=6 GET /mahasiswa/2 GET /mahasiswa/99

Perhatikan dua hal. Query string ?semester=6 ikut tercatat berkat req.originalUrl. Dan GET /mahasiswa/99 (yang berujung 404) dicatat sama seperti yang berhasil, karena pada titik ini logger belum tahu hasilnya: ia dijalankan sebelum rute.

Percobaan: apa yang terjadi kalau next() dihapus?

Ini kesalahan nomor satu yang diperingatkan di 2.1. Coba sendiri: beri komentar pada baris next(); di logger.js, simpan, lalu kirim permintaan dengan batas waktu 3 detik:

$ curl -m 3 http://localhost:3000/mahasiswa curl: (28) Operation timed out after 3005 milliseconds with 0 bytes received

Di terminal server baris GET /mahasiswa tetap tercetak (logger-nya jalan), tetapi klien tidak pernah mendapat jawaban: permintaan berhenti di logger, router tidak pernah dipanggil, dan tidak ada pesan error apa pun. Kembalikan next(); sebelum lanjut.

Menambah status dan waktu

Log yang berguna biasanya memuat hasilnya (status) dan lama pemrosesannya. Masalahnya, status baru diketahui setelah handler menjawab, padahal logger berjalan sebelum handler. Solusinya mendaftarkan pendengar pada peristiwa finish milik res, yang dipicu saat jawaban selesai dikirim ke klien. Ganti isi logger.js:

// src/middleware/logger.js
export function logger(req, res, next) {
    const mulai = Date.now();                    // 1. catat jam saat permintaan masuk

    res.on('finish', () => {                     // 2. "pasang pengintai": dijalankan nanti, saat jawaban selesai dikirim
        const ms = Date.now() - mulai;
        console.log(`${req.method} ${req.originalUrl} -> ${res.statusCode} (${ms} ms)`);
    });

    next();                                      // 3. lanjutkan ke router tanpa menunggu
}

Ambil contoh GET /mahasiswa/99 di api-mahasiswa. Urutan kejadiannya:

  1. Permintaan masuk, express.json() selesai, logger dipanggil. Jam mulai disimpan.
  2. res.on('finish', ...) hanya mendaftarkan fungsi; isinya belum dijalankan.
  3. next() dipanggil, permintaan lanjut ke router. Handler tidak menemukan mahasiswa dan menjawab 404.
  4. Begitu jawaban selesai dikirim, peristiwa finish terpicu. Barulah baris log dicetak, kini dengan res.statusCode yang sudah pasti.

Kirim ulang permintaan tadi, dan log berubah menjadi:

GET /mahasiswa -> 200 (5 ms) GET /mahasiswa/99 -> 404 (1 ms)

logger tidak mengubah isi tanggapan dan selalu memanggil next(); tugasnya hanya mengamati. Itu pola khas middleware pencatat.

Checkpoint: setiap permintaan ke api-mahasiswa tercatat di terminal server lengkap dengan status dan waktunya, tanpa satu pun handler rute diubah. Inilah keuntungan middleware: satu fungsi berlaku untuk semua rute.

2.5 Urutan SANGAT Menentukan

Express menjalankan middleware sesuai urutan penulisan. Dua kesalahan paling umum, keduanya bisa kalian coba langsung di proyek ini:

// ❌ SALAH — express.json() terlambat: handler lebih dulu terdaftar
app.use('/mahasiswa', mahasiswaRoutes);
app.use(express.json());        // POST /mahasiswa → req.body undefined → 422 "nim dan nama wajib diisi"

// ❌ SALAH — logger terlambat: permintaan ke rute di atasnya tidak pernah tercatat
app.use('/mahasiswa', mahasiswaRoutes);
app.use(logger);                // router sudah menjawab, logger tidak sempat jalan

// ✅ BENAR — middleware yang berlaku untuk semua rute dipasang PALING AWAL
app.use(express.json());
app.use(logger);
app.use('/mahasiswa', mahasiswaRoutes);

Aturan praktisnya: Express mencocokkan dari atas ke bawah, dan begitu ada yang mengirim tanggapan, sisanya dilewati. Maka pasang yang bersifat umum (pengurai body, logger) di atas, rute di tengah, dan penanganan error di paling bawah (Section 2).

2.6 Praktik: Middleware Khusus Satu Rute, cekApiKey

Kebutuhan berikutnya: GET boleh dibuka siapa saja, tetapi menambah data (POST /mahasiswa) hanya untuk klien yang membawa kunci. Login sungguhan dibahas di Pertemuan 9; sementara kita pakai API key sederhana yang dikirim lewat header x-api-key.

// src/middleware/cekApiKey.js
export function cekApiKey(req, res, next) {
    const kunci = req.headers['x-api-key'];

    if (kunci !== 'rahasia123') {
        return res.status(401).json({
            error: { pesan: 'API key tidak valid', kode: 'UNAUTHORIZED' }
        });
    }
    next();   // kunci benar, lanjut ke handler
}

Bedanya dengan logger: middleware ini bisa menolak. Kalau kunci salah, ia menjawab sendiri dengan 401 lalu return, sehingga next() tidak pernah dipanggil dan handler tidak jalan. Kalau benar, next() meneruskan permintaan.

Middleware untuk satu rute disisipkan sebagai argumen di antara path dan handler. Buka src/routes/mahasiswa.routes.js, impor cekApiKey, lalu sisipkan pada rute POST saja:

// src/routes/mahasiswa.routes.js
import { cekApiKey } from '../middleware/cekApiKey.js';

// ...rute GET tidak berubah...

router.post('/', cekApiKey, (req, res) => {     // ← cekApiKey disisipkan di sini
    // isi handler sama seperti sebelumnya
});

Uji tiga skenario:

$ curl -i http://localhost:3000/mahasiswa/1 HTTP/1.1 200 OK # GET tetap terbuka $ curl -X POST http://localhost:3000/mahasiswa \ -H "Content-Type: application/json" \ -d '{"nim":"F1D021004","nama":"Dewi"}' {"error":{"pesan":"API key tidak valid","kode":"UNAUTHORIZED"}} # 401, ditolak $ curl -X POST http://localhost:3000/mahasiswa \ -H "Content-Type: application/json" \ -H "x-api-key: rahasia123" \ -d '{"nim":"F1D021004","nama":"Dewi"}' {"data":{"id":4,"nim":"F1D021004","nama":"Dewi","ipk":0,"semester":1}} # 201, lolos
Kunci yang ditulis langsung di kode hanya untuk latihan. Di aplikasi sungguhan, kunci atau token disimpan di environment variable dan diperiksa dengan cara yang lebih aman (Pertemuan 9 dan 10).

Perhatikan bahwa cekApiKey menulis format error-nya sendiri, begitu juga kirimError di router. Itu yang kita rapikan di Section 3.

2.7 Tingkat Aplikasi vs Tingkat Router

Sekarang kita punya dua tempat memasang middleware. Yang kita pasang dengan app.use(...) (express.json(), logger) disebut middleware tingkat aplikasi (application-level): berlaku untuk setiap permintaan. Yang dipasang di router dengan router.use(...) disebut middleware tingkat router (router-level): hanya berlaku bagi rute di dalam router itu.

 Tingkat aplikasiTingkat router
Dipasang padaapp.use(...)router.use(...)
Cakupanseluruh aplikasihanya rute di dalam router itu
Cocok untukparsing body, CORS, log, penanganan errorcek akses untuk satu modul, validasi khusus
Padanan Laravelglobal middleware di Kernel.phpRoute::group() dengan middleware

Coba tambahkan satu middleware tingkat router di src/routes/mahasiswa.routes.js, tepat setelah const router = ...:

const router = express.Router();

// Middleware tingkat router: hanya jalan untuk rute di file ini
router.use((req, res, next) => {
    console.log('[mahasiswa]', req.method, req.originalUrl);
    next();
});

Kirim GET /mahasiswa/2 dan GET /. Terminal server menampilkan:

[mahasiswa] GET /mahasiswa/2 GET /mahasiswa/2 -> 200 (3 ms) GET / -> 200 (1 ms)

Baris [mahasiswa] hanya muncul untuk alamat berawalan /mahasiswa, sedangkan logger mencatat semuanya. Perhatikan urutannya: baris router muncul lebih dulu karena middleware itu berjalan sebelum handler, sementara baris logger baru dicetak setelah tanggapan selesai.

Pemakaian paling berguna adalah mengurung middleware pada satu kelompok rute. Misalnya, kalau semua rute /mahasiswa (termasuk GET) harus butuh kunci, cukup satu baris router.use(cekApiKey) di router, tanpa menyentuh rute publik lain seperti / atau nanti /login. Di Pertemuan 9, middleware pemeriksa token akan dipasang dengan cara ini.

Kaitan dengan Section 5. Router sudah memisahkan rute dari index.js. Di Section 5 kita memisahkan lagi isi handler menjadi controller dan service, tetapi file router, folder src/middleware/, dan pola app.use('/mahasiswa', ...) tetap sama.

3. Penanganan Error Terpusat Indikator 3.5

3.1 Masalah: Error Tersebar di Mana-Mana

Lihat kembali kode di Section 1 dan 2. Setiap tempat yang menemukan masalah membentuk jawabannya sendiri: router memakai helper kirimError, sedangkan cekApiKey menulis JSON error secara manual. Ada tiga akibatnya:

  • Format error ditulis di banyak tempat. Kalau format { error: { pesan, kode } } berubah, semua tempat itu harus dicari dan disunting satu per satu.
  • Bug tak terduga tidak punya jawaban yang rapi. Kalau handler melempar TypeError karena salah ketik, Express menjawab dengan halaman HTML berisi jejak error, bukan JSON.
  • URL yang tidak dikenal dijawab teks Cannot GET /xyz, juga bukan JSON.

Solusinya memisahkan dua pekerjaan: tempat yang menemukan masalah cukup melempar error, dan satu fungsi khusus di paling bawah yang menjawab semua error. Fungsi itu disebut error-handling middleware.

rute / middleware

→

→

3.2 Kelas Error Kustom: AppError

Agar errorHandler tahu harus menjawab dengan status apa, error yang dilempar perlu membawa status dan kode. Caranya dengan kelas turunan Error, pola yang sama dengan kelas error kustom di Pertemuan 3 (sisi klien), kini dipakai di sisi server:

export class AppError extends Error {
    constructor(status, pesan, kode) {
        super(pesan);
        this.status = status;
        this.kode = kode;
    }
}

super(pesan) mengisi err.message. Dua properti tambahan membawa kebutuhan HTTP: status (kode status) dan kode (kode mesin yang stabil, misalnya NOT_FOUND, agar klien tidak perlu membaca kalimat pesan). Pemakaiannya satu baris: throw new AppError(404, 'Mahasiswa tidak ditemukan', 'NOT_FOUND').

3.3 Error-Handling Middleware

Bentuknya sama dengan middleware biasa, tetapi dengan empat parameter (err di depan). Express mengenalinya secara khusus dari jumlah parameter itu, sehingga keempatnya harus ditulis walaupun next tidak dipakai.

export function errorHandler(err, req, res, next) {
    const status = err.status ?? 500;

    if (status >= 500) console.error(err);   // hanya error server yang dicatat lengkap

    res.status(status).json({
        error: {
            pesan: status < 500 ? err.message : 'Terjadi kesalahan pada server',
            kode: err.kode ?? (status < 500 ? 'REQUEST_ERROR' : 'INTERNAL_ERROR')
        }
    });
}

Tiga keputusan di kode ini:

  • err.status ?? 500: error yang tidak membawa status (misalnya TypeError dari bug) dianggap kesalahan server, 500.
  • Pesan asli hanya dikirim ke klien kalau statusnya di bawah 500. Untuk error server, klien menerima kalimat umum, sedangkan detailnya dicatat di terminal dengan console.error. Pesan error internal (nama tabel, jalur file) tidak boleh bocor ke klien.
  • Error dari luar kita ikut tertangani. Misalnya JSON yang rusak ditolak express.json() dengan status 400, lalu diubah errorHandler ke format yang sama.

Satu middleware lagi melengkapinya: penangkap URL yang tidak dikenal. Ia dipasang setelah semua rute, dan tugasnya hanya mengubah “tidak ada rute yang cocok” menjadi AppError:

import { AppError } from '../utils/AppError.js';

export function notFound(req, res, next) {
    next(new AppError(404, `Rute ${req.method} ${req.originalUrl} tidak ada`, 'ROUTE_NOT_FOUND'));
}
Posisi sangat menentukan. notFound dan errorHandler harus didaftarkan setelah semua rute, dengan errorHandler paling akhir. Express mencari penangan error ke bawah dari titik kegagalan. Dan kalau memanggil next(err) di dalam middleware, jangan lupa return, supaya kode di bawahnya tidak ikut berjalan.

Langkah 2 — Ubah cekApiKey

3.5 Error pada Handler async

Pada Express 4, error yang dilempar dari handler async tidak otomatis ditangkap, sehingga tutorial lama membungkus tiap handler dengan try/catch atau fungsi pembungkus. Express 5, versi yang kita pasang di Pertemuan 4, sudah menanganinya: handler yang melempar error atau mengembalikan promise yang gagal otomatis diteruskan ke errorHandler.

// Express 5: aman tanpa try/catch dan tanpa pembungkus
router.get('/:id', async (req, res) => {
    const m = await cariMahasiswa(req.params.id);   // kalau promise ini gagal, errorHandler yang menjawab
    res.json({ data: m });
});

Pola ini kita pakai mulai Section 5, ketika service dan controller menjadi fungsi async.

Kalau menemukan kode seperti ini di tutorial atau proyek lama, itu penambal untuk Express 4: 
const asyncHandler = (fn) => (req, res, next) => {
    Promise.resolve(fn(req, res, next)).catch(next);
};
router.get('/:id', asyncHandler(async (req, res) => { /* ... */ }));
Di proyek kita tidak diperlukan. Cek versi Express dengan npm ls express.

4. Validasi Masukan Indikator 3.5

Lanjutkan proyek api-mahasiswa dari akhir Section 3. Error sudah terpusat, tetapi pemeriksaan isi kiriman klien masih lemah. Section ini menutup celah itu dengan middleware validasi.

4.1 Mengapa Validasi Dipisah dari Handler?

Pemeriksaan isi POST /mahasiswa sekarang hanya if (!nim || !nama) di dalam handler. Coba kirim data yang jelas keliru:

$ curl -X POST http://localhost:3000/mahasiswa -H "Content-Type: application/json" -H "x-api-key: rahasia123" -d '{"nim":"1","nama":"X","ipk":9,"semester":-3}' {"data":{"id":4,"nim":"1","nama":"X","ipk":9,"semester":-3}} $ curl -X POST http://localhost:3000/mahasiswa -H "Content-Type: application/json" -H "x-api-key: rahasia123" -d '{"nim":"F1D021004","nama":"Dewi","ipk":"bagus"}' {"data":{"id":5,"nim":"F1D021004","nama":"Dewi","ipk":"bagus","semester":1}}

Keduanya diterima dan masuk ke daftar: NIM “1”, IPK 9, semester −3, bahkan IPK berupa teks “bagus”. Data rusak seperti ini akan merepotkan semua yang memakai API nanti (React, laporan, database). Menambah if untuk setiap kemungkinan membuat handler panjang dan berulang di setiap rute.

Cara yang lebih rapi: jadikan validasi itu sendiri sebagai middleware yang dipasang sebelum handler. Handler hanya dijalankan kalau datanya sudah pasti benar.

cekApiKey

→

→

Ada dua jenis pemeriksaan yang perlu dibedakan, karena tempatnya berbeda:

JenisContoh di api-mahasiswaTempatnya

Menulis aturan bentuk data dengan if bertumpuk cepat panjang. Pustaka Joi menggantinya dengan skema, yaitu deskripsi bentuk data yang diharapkan. Skema ditulis sekali, lalu dipakai oleh satu middleware generik.

4.2 Praktik: Pasang Validasi di API Mahasiswa

Langkah 1 — Install Joi dan tulis skema

$ npm install joi
// src/validators/mahasiswa.validator.js
import Joi from 'joi';

export const skemaMahasiswa = Joi.object({
    nim:      Joi.string().length(9).required(),
    nama:     Joi.string().min(3).max(100).required(),
    ipk:      Joi.number().min(0).max(4).default(0),
    semester: Joi.number().integer().min(1).max(14).default(1)
});

Rantai method dibaca dari kiri ke kanan seperti kalimat: “nim adalah string, panjangnya 9, dan wajib diisi”. .default(0) berarti kalau ipk tidak dikirim, Joi mengisinya dengan 0. Ini menggantikan ipk ?? 0 di handler.

Langkah 2 — Bungkus skema menjadi middleware

// src/middleware/validasi.js
import { AppError } from '../utils/AppError.js';

export const validasi = (skema) => (req, res, next) => {
    const { error, value } = skema.validate(req.body ?? {}, { abortEarly: false });

    if (error) {
        const pesan = error.details.map(d => d.message).join('; ');
        return next(new AppError(422, pesan, 'VALIDATION_ERROR'));
    }

    req.body = value;   // pakai nilai yang sudah dibersihkan Joi (termasuk nilai bawaan)
    next();
};

Tiga hal yang perlu diperhatikan:

  • validasi bukan middleware, melainkan fungsi yang mengembalikan middleware. Karena itu satu file ini dipakai untuk skema apa pun.
  • abortEarly: false membuat Joi melaporkan semua kesalahan sekaligus, bukan berhenti di yang pertama. Bagi pengguna formulir, ini lebih ramah.
  • Kegagalan tidak dijawab langsung, melainkan diserahkan ke next(new AppError(...)), sehingga bentuk jawabannya tetap sama dengan error lain. req.body ?? {} menjaga agar request tanpa body tetap berujung 422, bukan error aneh.

Langkah 3 — Pasang di rute POST

Ganti rute POST di router. Handler jadi jauh lebih pendek karena pemeriksaan if dan nilai bawaan sudah ditangani middleware:

// src/routes/mahasiswa.routes.js
import { validasi } from '../middleware/validasi.js';
import { skemaMahasiswa } from '../validators/mahasiswa.validator.js';

// urutan: cek kunci dulu, baru validasi isi, baru handler
router.post('/', cekApiKey, validasi(skemaMahasiswa), (req, res) => {
    const baru = { id: mahasiswa.length + 1, ...req.body };
    mahasiswa.push(baru);
    res.status(201).json({ data: baru });
});

Urutan cekApiKey sebelum validasi disengaja: klien tanpa izin cukup ditolak, tidak perlu repot memeriksa isi kirimannya.

Langkah 4 — Uji

$ curl -X POST http://localhost:3000/mahasiswa -H "Content-Type: application/json" -H "x-api-key: rahasia123" -d '{"nim":"123","ipk":9}' {"error":{"pesan":"\"nim\" length must be 9 characters long; \"nama\" is required; \"ipk\" must be less than or equal to 4","kode":"VALIDATION_ERROR"}} $ curl -X POST http://localhost:3000/mahasiswa -H "Content-Type: application/json" -H "x-api-key: rahasia123" -d '{"nim":"F1D021004","nama":"Dewi"}' {"data":{"id":4,"nim":"F1D021004","nama":"Dewi","ipk":0,"semester":1}}

Ketiga kesalahan dilaporkan sekaligus, dan pada kiriman kedua ipk serta semester terisi nilai bawaan. Pesan Joi berbahasa Inggris; kalau ingin bahasa Indonesia, setiap aturan bisa diberi pesan sendiri dengan .messages({...}).

Checkpoint: kiriman yang keliru (seperti dua contoh di 4.1) kini ditolak dengan 422 dan semua alasannya dilaporkan sekaligus, sedangkan kiriman yang benar lolos dengan nilai bawaan terisi. Handler POST tinggal tiga baris.
Validasi sisi klien bukan pengganti. Pemeriksaan di formulir React (Pertemuan 11) hanya membantu pengguna; siapa pun tetap bisa mengirim permintaan langsung ke API lewat cURL atau REST Client. Validasi sisi server adalah satu-satunya yang benar-benar menjaga data. Ini diperdalam di Pertemuan 10 sebagai bagian dari OWASP.

Langkah 2 — Lapis service

Di sini aturan bisnis tinggal. Perhatikan aturan baru: NIM tidak boleh kembar, ditolak dengan status 409 (Conflict). Aturan ini tidak bisa diperiksa oleh Joi karena membutuhkan data.

import * as data from '../data/mahasiswa.data.js';
import { AppError } from '../utils/AppError.js';

export async function daftarMahasiswa({ semester }) {
    const semua = data.semua();
    return semester
        ? semua.filter(m => m.semester === Number(semester))
        : semua;
}

export async function detailMahasiswa(id) {
    const m = data.cariById(Number(id));
    if (!m) {
        throw new AppError(404, 'Mahasiswa tidak ditemukan', 'NOT_FOUND');
    }
    return m;
}

export async function buatMahasiswa(input) {
    if (data.cariByNim(input.nim)) {
        throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
    }
    return data.simpan(input);
}

Semua fungsi dibuat async sejak sekarang. Pekerjaan data di Pertemuan 6 berupa query database yang asinkron, dan dengan begini controller tidak perlu diubah. Karena Express 5 menangani error async (Section 3.5), throw new AppError(...) di sini langsung sampai ke errorHandler.

Langkah 3 — Lapis controller

import * as service from '../services/mahasiswa.service.js';

export async function daftar(req, res) {
    const hasil = await service.daftarMahasiswa(req.query);
    res.json({ data: hasil, meta: { total: hasil.length } });
}

export async function detail(req, res) {
    const m = await service.detailMahasiswa(req.params.id);
    res.json({ data: m });
}

export async function buat(req, res) {
    const baru = await service.buatMahasiswa(req.body);
    res.status(201).json({ data: baru });
}

Controller sangat tipis: ambil masukan dari req, minta service bekerja, kirim hasilnya. Tidak ada if untuk kasus gagal, karena itu urusan service dan errorHandler.

Langkah 4 — Rapikan router

Ganti seluruh isi src/routes/mahasiswa.routes.js. Router kini hanya peta: URL, middleware, controller.

import express from 'express';

  • Rekan satu kelompok bisa memakai koleksi permintaan yang sama tanpa menyusun ulang
  • Berfungsi sebagai dokumentasi hidup: bisa dibaca dan dijalankan, bukan sekadar teks

Kebiasaan yang wajib dibangun mulai sekarang: setiap kali menambah endpoint baru, tambahkan juga permintaan ujinya di requests.http, termasuk minimal satu kasus yang sengaja gagal (data tidak valid, id tidak ada). Kebiasaan ini langsung terpakai lagi saat menyusun pengujian otomatis di Pertemuan 13.

Latihan

  1. PUT dan DELETE. Tambahkan PUT /mahasiswa/:id (200) dan DELETE /mahasiswa/:id (204) dari Pertemuan 4 ke struktur berlapis: routes → controller → service → data. Pasang cekApiKey pada keduanya, dan validasi pada PUT. Tambahkan permintaan ujinya, termasuk yang gagal, ke requests.http.
  2. Router kedua. Buat router /mata-kuliah (field kode, nama, sks) dengan GET daftar dan GET detail, lalu pasang di index.js. Kirim permintaan ke /mata-kuliah dan amati terminal: baris logger muncul, baris [mahasiswa] tidak. Jelaskan mengapa.
  3. Error tak terduga. Sengaja salah ketik di lapis data (misalnya mahasiswa.push menjadi mahasiswa.dorong), lalu kirim POST yang valid. Pastikan klien menerima 500 dengan pesan umum “Terjadi kesalahan pada server” (bukan nama method yang salah), sementara jejak lengkapnya muncul di terminal server. Kembalikan kodenya.
  4. Kunci dari environment. Ubah cekApiKey agar membaca kunci dari process.env.API_KEY, bukan teks tetap di kode. Jalankan dengan API_KEY=rahasia123 npm run dev. Apa yang terjadi kalau variabelnya tidak diset? Putuskan perilaku yang paling aman.
