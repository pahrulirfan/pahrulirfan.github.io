1. Password: Hash, Bukan Enkripsi Indikator 5.1

Sebelum membahas login, ada satu hal yang harus benar sejak awal: bagaimana password disimpan. Kalau tabel users bocor, yang bocor adalah isi kolom password. Kalau isinya password asli, semua akun ikut jatuh, termasuk akun di website lain yang memakai password yang sama.

Jangan
Simpan rahasia123 apa adanya, atau simpan hasil MD5/SHA-256 saja. Keduanya cepat dihitung, sehingga penyerang bisa mencoba miliaran tebakan per detik.
Lakukan
Simpan hash dari bcrypt: satu arah (tidak bisa dibalik) dan sengaja lambat, sehingga tebakan massal jadi mahal.

Hash adalah fungsi satu arah: dari password kita bisa menghitung hash-nya, tetapi dari hash tidak ada jalan kembali ke password. Saat login, server tidak “membuka” hash. Server menghitung hash dari password yang baru diketik, lalu membandingkannya dengan hash yang tersimpan.

1.1 Buat Proyek Baru untuk Percobaan

Kita tidak langsung mengubah api-mahasiswa. Mulai dari proyek kecil auth-uji supaya setiap konsep bisa dicoba tanpa gangguan: tanpa database, tanpa Prisma. Setelah semuanya jelas, baru kita pindahkan ke api-mahasiswa di Section 4.

1.2 Hash Pertama

Buat file hash.js. Kita hash password yang sama dua kali, lalu bandingkan hasilnya:

// hash.js
import bcrypt from 'bcrypt';

const password = 'rahasia123';

const hash1 = await bcrypt.hash(password, 10);
const hash2 = await bcrypt.hash(password, 10);

console.log('hash 1:', hash1);
console.log('hash 2:', hash2);
console.log('hash 1 sama dengan hash 2?', hash1 === hash2);

console.log('compare password benar:', await bcrypt.compare('rahasia123', hash1));
console.log('compare password salah:', await bcrypt.compare('salahketik', hash1));
$ node hash.js hash 1: $2b$10$mMhE1PhRx0c98vCtPl6SeO6p244MqrMrE/DcGMn6oSe1fC7g1OIWW hash 2: $2b$10$GnCJOvjq7zYmHFk.9pW5TOTdb/xKNvE7D1OtNhn7xatAKHEo7PJr2 hash 1 sama dengan hash 2? false compare password benar: true compare password salah: false

Hash di komputer kalian akan berbeda dari di atas, dan itu memang yang diharapkan. Ada tiga hal yang bisa diamati dari percobaan ini:

  • Password sama, hash berbeda. bcrypt menambahkan salt (teks acak) di setiap pemanggilan, jadi dua user dengan password sama tidak punya hash yang sama, dan penyerang tidak bisa memakai tabel hash yang sudah dihitung sebelumnya (rainbow table).
  • $2b$10$... adalah awalan yang memuat versi algoritma (2b) dan cost factor (10). Salt ikut tersimpan di dalam string hash, jadi tidak perlu kolom tambahan.
  • Memeriksa password = bcrypt.compare, bukan membandingkan teks. Fungsi ini membaca salt dari hash, menghitung ulang, lalu mencocokkan.

1.3 Cost Factor: Sengaja Lambat

Angka 10 pada bcrypt.hash(password, 10) adalah cost factor: setiap kenaikan 1 menggandakan waktu hitung. Nilai 10 membuat satu hash butuh sekitar puluhan milidetik. Bagi pengguna yang login sekali, itu tidak terasa. Bagi penyerang yang mencoba jutaan tebakan, itu sangat mahal.

Plain textTidak perlu dibalik, sudah terbaca—Tidak
Enkripsi (AES)Ya, dengan kunciKunci bocor = semua terbukaTidak (password tidak perlu dibaca ulang)
Hash cepat (MD5, SHA-256)TidakMiliaran tebakan per detikTidak

Padanan di Laravel: Hash::make($password) dan Hash::check($password, $hash) memakai bcrypt juga. Konsepnya sama, hanya sintaksnya berbeda.
Batas bcrypt: hanya 72 byte pertama password yang dihitung. Itu sebabnya validasi di Section 4 membatasi password maksimal 72 karakter.

2. Sesi vs Token Indikator 5.2

Setelah login berhasil, ada masalah baru: HTTP itu stateless. Setiap request berdiri sendiri, server tidak otomatis ingat bahwa request kedua datang dari orang yang sama dengan request pertama. Kalau tidak ada yang kita lakukan, user harus mengirim email dan password di setiap request.

2.1 Dua Cara Mengingat User

Solusinya: setelah login, server memberi client sebuah tanda pengenal, dan client menyertakannya di setiap request berikutnya. Yang membedakan hanyalah siapa yang menyimpan catatan identitasnya:

  • Sesi (session) seperti karcis parkir. Karcis hanya berisi nomor. Data lengkapnya (plat nomor, jam masuk) dicatat petugas di buku. Setiap keluar, petugas mencari nomor itu di bukunya. Server menyimpan catatan, client hanya memegang nomor.
  • Token (JWT) seperti gelang konser dengan segel. Gelang itu sendiri sudah memuat informasinya (jenis tiket, tanggal berlaku) dan segelnya tidak bisa dipalsukan. Penjaga cukup memeriksa segelnya, tanpa membuka buku apa pun. Client memegang datanya, server hanya memeriksa signature.

2.4 Anatomi JWT

Token JWT terdiri dari tiga bagian yang dipisah titik. Header dan payload hanyalah JSON yang di-encode dengan Base64, bukan dienkripsi. Bagian ketiga, signature, dihitung dari dua bagian pertama ditambah JWT_SECRET:

2.5 Tiga Skema Autentikasi pada HTTP

                
JWT bukan satu-satunya cara menitipkan bukti identitas. Tiga skema berikut sama-sama dikirim lewat header Authorization:

                

                    
SkemaBentuk headerKelemahan

                    
BasicAuthorization: Basic ZGljb2Rpbmc6cjRoYXNpYQ==Isinya user:password yang hanya di-Base64, siapa pun bisa membukanya

                    
API KeyAuthorization: Apikey 4a6eac5979a6...Tidak punya masa berlaku; sekali bocor, berlaku selamanya

                    
Bearer (token)Authorization: Bearer eyJhbGciOi...Skema yang kita pakai

                

                
Mungkin terasa janggal: proses autentikasi memakai header bernama Authorization. Itu warisan spesifikasi HTTP dan berlaku di semua bahasa dan framework. Bearer unggul karena yang dikirim bukan password, dan token punya masa expired, jadi kalaupun dicuri hanya berguna dalam jangka waktu terbatas.

                

                    Ingat x-api-key dari Pertemuan 5? Itu adalah skema API Key versi sederhana (satu kunci untuk semua orang). Di Section 4 kita menggantinya dengan Bearer token, sehingga server tahu siapa pemilik request, bukan hanya “request ini membawa kunci yang benar”.
                

            


            

                
3. Token di Proyek Percobaan Indikator 5.2


                
Kembali ke auth-uji. Kita bangun versi token langkah demi langkah: buat dan periksa token, lalu buat satu endpoint yang memerlukan password dan satu endpoint yang terbuka. Versi lengkap — register, password ter-hash sungguhan, dan otorisasi berbasis role — baru dipasang ke data asli di Section 4.


                
3.1 Siapkan Secret di .env

                
Signature dibuat dari JWT_SECRET. Nilai ini tidak boleh ada di kode, jadi simpan di .env (seperti DATABASE_URL di Pertemuan 6). Buat file .env di folder auth-uji:


JWT_SECRET=rahasia-belajar-pwl-ganti-di-produksi

                
Untuk percobaan, kalimat ini cukup. Di Section 4 kita membuat secret yang benar-benar acak.


                
3.2 Buat, Baca, dan Periksa Token

                
Buat token.js. Lima percobaan dalam satu file: membuat token, membacanya tanpa secret, memverifikasinya, memalsukannya, dan menunggunya expired.


// token.js
import 'dotenv/config';
import jwt from 'jsonwebtoken';

const secret = process.env.JWT_SECRET;

// 1. Buat token
const token = jwt.sign({ id: 1, role: 'mahasiswa' }, secret, { expiresIn: '2h' });
console.log('token:', token);

// 2. Isi token bisa dibaca siapa saja, tanpa secret
console.log('decode:', jwt.decode(token));

// 3. Verifikasi dengan secret yang benar
console.log('verify:', jwt.verify(token, secret));

// 4. Token dipalsukan: payload diganti, signature dibiarkan
const [header, , signature] = token.split('.');
const payloadPalsu = Buffer.from(JSON.stringify({ id: 1, role: 'admin' })).toString('base64url');
const tokenPalsu = `${header}.${payloadPalsu}.${signature}`;
try {
    jwt.verify(tokenPalsu, secret);
} catch (err) {
    console.log('token palsu ditolak:', err.message);
}

// 5. Token expired
const singkat = jwt.sign({ id: 1 }, secret, { expiresIn: '1s' });
await new Promise((r) => setTimeout(r, 1500));
try {
    jwt.verify(singkat, secret);
} catch (err) {
    console.log('token expired ditolak:', err.name, '-', err.message);
}

3.3 Satu Endpoint Memerlukan Password, Satu Endpoint Terbuka

                
Sekarang implementasikan sebagai server. Buat server.js. Supaya fokusnya murni pada mekanisme token, password-nya untuk sementara ditulis langsung di kode (satu nilai tetap, bukan per user) — Section 4 baru menggantinya dengan hash sungguhan yang tersimpan di database:


// server.js
import 'dotenv/config';
import express from 'express';
import jwt from 'jsonwebtoken';

const app = express();
app.use(express.json());

const PASSWORD = 'rahasia123';   // sementara satu nilai tetap, bukan per user

app.post('/login', (req, res) => {
    if (req.body.password !== PASSWORD) {
        return res.status(401).json({ error: 'Password salah' });
    }

    const token = jwt.sign({ user: 'andi' }, process.env.JWT_SECRET, { expiresIn: '2h' });
    res.json({ token });
});

function butuhLogin(req, res, next) {
    const header = req.headers.authorization;           // "Bearer eyJhbGci..."

    if (!header?.startsWith('Bearer ')) {
        return res.status(401).json({ error: 'Token diperlukan' });
    }

    try {
        req.user = jwt.verify(header.slice(7), process.env.JWT_SECRET);   // { user, iat, exp }
        next();
    } catch (err) {
        res.status(401).json({ error: 'Token tidak valid atau expired' });
    }
}

app.get('/rahasia', butuhLogin, (req, res) => {
    res.json({ pesan: `Halo ${req.user.user}, ini isi yang butuh password.` });
});

app.get('/publik', (req, res) => {
    res.json({ pesan: 'Siapa pun boleh baca ini, tanpa password.' });
});

app.listen(3100, () => console.log('Server jalan di http://localhost:3100'));

                
Dua hal yang perlu dipahami dari kode ini:

                
    
                    
  • butuhLogin adalah middleware (Pertemuan 5). Ia membaca header, memanggil jwt.verify, lalu menaruh hasilnya di req.user supaya handler berikutnya tahu siapa pemilik request. header.slice(7) membuang awalan Bearer  (7 karakter).
    • 
                    
  • Bedanya ada di /publik: tidak dipasangi butuhLogin sama sekali. /rahasia memasangnya sebagai argumen kedua, sebelum handler.
    •

3.4 Bukti: Token Tidak Perlu Catatan di Server

                
Ingat simulator di 2.2: pada mode sesi (memori), restart Server A membuat sesinya hilang. Sekarang buktikan token tidak begitu. Simpan token hasil login, hentikan server, jalankan lagi, lalu pakai token yang sama:


Tampilan Postman (ilustrasi; Authorization: Bearer eyJhbGci...(token sebelum restart))
GEThttp://localhost:3100/rahasiaSend
Response200 OK
{
  "pesan": "Halo andi, ini isi yang butuh password."
}

                
Server yang baru tidak kehilangan apa pun (bahkan PASSWORD dan logikanya sama, karena ditulis di kode, bukan disimpan saat runtime), tetapi yang membuktikan stateless sebenarnya adalah ini: /rahasia tidak mencatat token siapa pun di mana pun — ia hanya membutuhkan JWT_SECRET untuk memeriksa signature-nya. Token lama tetap diterima tanpa server perlu "mengingat" pernah menerbitkannya.


                

                    Checkpoint: kalian sudah punya hash.js, token.js, dan server.js yang berjalan: /publik bisa diakses siapa saja, /login menolak password salah dengan 401 dan menerbitkan token kalau benar, /rahasia menolak request tanpa token dengan 401 tapi menerima token yang valid. 4.4 Lapis Data, Validasi, Service

                
Lapis data hanya berbicara dengan Prisma. Di simpan, select sengaja tidak memuat passwordHash, supaya hash tidak pernah ikut terkirim ke client:


// src/data/user.data.js
import { prisma } from '../lib/prisma.js';

export function cariByEmail(email) {
    return prisma.user.findUnique({ where: { email } });
}

export function simpan({ email, passwordHash }) {
    return prisma.user.create({
        data: { email, passwordHash },
        select: { id: true, email: true, role: true },   // passwordHash tidak ikut dikembalikan
    });
}

                
Validator memakai Joi seperti di Pertemuan 5. Hanya email dan password yang diizinkan. Field lain, termasuk role, akan ditolak, sehingga user tidak bisa menjadikan dirinya admin saat register:


// src/validators/auth.validator.js
import Joi from 'joi';

export const skemaAuth = Joi.object({
    email:    Joi.string().email().max(100).required(),
    password: Joi.string().min(8).max(72).required()
});

                
register adalah fungsi baru — pada percobaan, password-nya satu nilai tetap di kode, tidak pernah di-hash atau disimpan per user. login memakai pola yang sama dengan server.js tadi (periksa dulu, baru terbitkan token), hanya sekarang dibandingkan ke hash di database lewat bcrypt.compare, bukan ke satu nilai tetap, dan payload tokennya menyertakan role karena akan dipakai middleware otorisasi di 4.6. Keduanya memakai AppError (Pertemuan 5) dan lapis data:


// src/services/auth.service.js
import bcrypt from 'bcrypt';
import jwt from 'jsonwebtoken';
import * as data from '../data/user.data.js';
import { AppError } from '../utils/AppError.js';

export async function register({ email, password }) {
    if (await data.cariByEmail(email)) {
        throw new AppError(409, 'Email sudah terdaftar', 'EMAIL_DUPLIKAT');
    }

    const passwordHash = await bcrypt.hash(password, 10);
    return data.simpan({ email, passwordHash });
}

export async function login({ email, password }) {
    const user = await data.cariByEmail(email);
    const cocok = user && (await bcrypt.compare(password, user.passwordHash));

    if (!cocok) {
        throw new AppError(401, 'Email atau password salah', 'LOGIN_GAGAL');
    }

    const token = jwt.sign(
        { id: user.id, role: user.role },
        process.env.JWT_SECRET,
        { expiresIn: '2h' },
    );
    return { token };
}

4.6 Autentikasi vs Otorisasi: Middleware butuhRole

                
Satu middleware lagi diperlukan di sini, dan sebelum menulisnya ada satu bedanya dulu yang wajib jelas. Dua istilah ini sering tertukar, padahal menjawab pertanyaan berbeda dan menghasilkan status berbeda:

                

                    
IstilahPertanyaanGagal berarti

                    
Autentikasi“Siapa kamu?”401 Unauthorized: token tidak ada, rusak, atau expired

                    
Otorisasi“Kamu boleh melakukan ini?”403 Forbidden: sudah dikenali, tapi tidak berhak

                

                
butuhLogin (dari Section 3) hanya menjawab yang pertama. Untuk yang kedua kita tulis middleware baru, butuhRole, dengan satu perbedaan dari percobaan: error dikirim lewat next(new AppError(...)) supaya format jawabannya sama dengan error lain di API (lewat errorHandler Pertemuan 5).


// src/middleware/auth.js
import jwt from 'jsonwebtoken';
import { AppError } from '../utils/AppError.js';

export function butuhLogin(req, res, next) {
    const header = req.headers.authorization;             // "Bearer eyJhbGci..."

    if (!header?.startsWith('Bearer ')) {
        return next(new AppError(401, 'Token diperlukan', 'TOKEN_DIPERLUKAN'));
    }

    try {
        req.user = jwt.verify(header.slice(7), process.env.JWT_SECRET);   // { id, role, iat, exp }
        next();
    } catch (err) {
        next(new AppError(401, 'Token tidak valid atau expired', 'TOKEN_TIDAK_VALID'));
    }
}

export function butuhRole(...roleDiizinkan) {
    return (req, res, next) => {
        if (!roleDiizinkan.includes(req.user.role)) {
            return next(new AppError(403, 'Tidak punya izin untuk aksi ini', 'DILARANG'));
        }
        next();
    };
}

                
butuhRole adalah fungsi yang mengembalikan middleware: kita memberi daftar role yang diizinkan (misalnya butuhRole('admin')), dan hasilnya middleware biasa. Urutan pemasangannya penting, karena butuhRole membaca req.user yang baru diisi oleh butuhLogin:


                

                    
RequestDELETE /mahasiswa/5

                    
→

                    
butuhLogintoken valid?tidak → 401

                    
→

                    
butuhRole('admin')role = admin?tidak → 403

                    
→

                    
Handler204 No Content

5. Pengayaan: Access Token dan Refresh Token Opsional


                

                    Bagian ini tidak wajib. Untuk tugas dan proyek, satu access token (Section 4) sudah memenuhi kriteria. Pola dua token tetap wajib dipahami, karena ini yang akan kalian temui di API produksi, dan boleh diterapkan sebagai nilai tambah pada proyek akhir. Kerjakan setelah Section 4 berjalan; Pertemuan 10 dan seterusnya mengasumsikan versi satu token.
                


                
5.1 Masalah yang Diselesaikan

                
Dari simulator kita tahu token tidak bisa dicabut, jadi masa berlakunya sebaiknya pendek. Tetapi masa berlaku pendek (misalnya 15 menit) memaksa user login ulang berulang kali. Solusi standar (mengikuti OAuth2): terbitkan dua token sekaligus.


                

                    
Refresh token (7 hari)

                    
Access token (15 menit)

                

                
Tanda ↻ di atas menunjukkan saat access token habis dan client menukarkan refresh token untuk mendapat access token baru, tanpa meminta user mengetik password lagi.


                

                    
 Access tokenRefresh token

                    
FungsiDikirim di setiap request ke endpoint terproteksiHanya ditukar dengan access token baru

                    
Masa berlakuPendek (menit)Panjang (hari)

                    
Dikirim keSemua endpointHanya POST /auth/refresh dan /auth/logout

                    
Dicatat di server?Tidak (tetap stateless)Ya, di database, supaya bisa dicabut

4. Service. Ganti fungsi login di auth.service.js dan tambahkan refresh serta logout:


function terbitkanToken(user) {
    const accessToken = jwt.sign(
        { id: user.id, role: user.role },
        process.env.JWT_ACCESS_SECRET,
        { expiresIn: '15m' },
    );
    const refreshToken = jwt.sign(
        { id: user.id },                                   // cukup id: tugasnya hanya menerbitkan token baru
        process.env.JWT_REFRESH_SECRET,
        { expiresIn: '7d' },
    );
    return { accessToken, refreshToken };
}

export async function login({ email, password }) {
    const user = await data.cariByEmail(email);
    const cocok = user && (await bcrypt.compare(password, user.passwordHash));

    if (!cocok) {
        throw new AppError(401, 'Email atau password salah', 'LOGIN_GAGAL');
    }

    const { accessToken, refreshToken } = terbitkanToken(user);
    await data.simpanRefresh(refreshToken, user.id);       // dicatat agar bisa dicabut
    return { accessToken, refreshToken };
}

export async function refresh(refreshToken) {
    // 1. Masih tercatat di database? (belum dicabut lewat logout)
    const tersimpan = await data.cariRefresh(refreshToken);
    if (!tersimpan) {
        throw new AppError(401, 'Refresh token tidak dikenali', 'REFRESH_TIDAK_VALID');
    }

    // 2. Signature asli dan belum expired?
    let payload;
    try {
        payload = jwt.verify(refreshToken, process.env.JWT_REFRESH_SECRET);
    } catch {
        throw new AppError(401, 'Refresh token tidak valid atau expired', 'REFRESH_TIDAK_VALID');
    }

    // 3. Ambil role TERBARU dari database, lalu terbitkan access token baru
    const user = await data.cariById(payload.id);
    return {
        accessToken: jwt.sign({ id: user.id, role: user.role }, process.env.JWT_ACCESS_SECRET, { expiresIn: '15m' }),
    };
}

export async function logout(refreshToken) {
    await data.hapusRefresh(refreshToken);
}

                
Pemeriksaan di refresh ada dua lapis, dan urutannya disengaja. Database diperiksa dulu karena hanya itu cara mengetahui token sudah dicabut: jwt.verify tidak tahu soal logout, selama signature cocok dan belum expired ia selalu meloloskan. Langkah 3 juga penting: role dibaca ulang dari database, bukan dari refresh token, sehingga perubahan role (seperti kasus admin di 4.8) langsung berlaku di access token berikutnya.
