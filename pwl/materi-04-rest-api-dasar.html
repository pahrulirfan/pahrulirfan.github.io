2. Apa Itu REST? Indikator 3.1

REST (Representational State Transfer) bukan teknologi, melainkan kesepakatan gaya penulisan API. Intinya: setiap URL mewakili sebuah sumber daya (resource) — benda, bukan aksi — dan metode HTTP yang menentukan aksi apa yang dilakukan terhadap sumber daya itu.

REST dalam tiga potong:
  • URL menjawab "sumber daya apa?" — contoh /mahasiswa/1
  • Metode HTTP menjawab "mau diapakan?" — contoh GET (ambil), POST (buat)
  • Kode status + JSON menjawab "hasilnya bagaimana?" — contoh 200 dan data mahasiswa

Satu permintaan dan jawabannya, dalam bentuk mentahnya, terlihat seperti ini:

$ GET /mahasiswa/1 200 OK { "id": 1, "nama": "Andi", "semester": 6 }

Sisa bagian ini membahas aturan main di balik tiga potong itu. Setelah itu, kita langsung memasang Express dan mempraktikkannya.

2.1 Kata Benda, Bukan Kata Kerja

❌ Gaya lama (RPC-ish)✅ Gaya REST
/getMahasiswa?id=1GET /mahasiswa/1
/createMahasiswaPOST /mahasiswa
/updateMahasiswa?id=1PUT /mahasiswa/1
/deleteMahasiswa?id=1DELETE /mahasiswa/1

URL menjawab pertanyaan "sumber daya apa". Metode HTTP menjawab "aksi apa". Jangan mencampur keduanya di dalam URL.

Padanan di GraphQL

GraphQL tidak punya "kata benda di URL". Semua permintaan masuk ke satu URL (/graphql), dan yang dipilih klien adalah nama operasi di schema. Karena itu nama operasi GraphQL justru lazim memakai kata kerja untuk perubahan data, misalnya tambahMahasiswa. Detailnya di Section 8.

Idempoten artinya: memanggil sekali atau sepuluh kali hasilnya sama. PUT /mahasiswa/1 dengan data yang sama menghasilkan keadaan akhir yang sama walau dipanggil berkali-kali. POST /mahasiswa tidak idempoten — dipanggil dua kali membuat dua data baru.
Padanan di GraphQL

GraphQL tidak memakai kelima metode ini untuk membedakan aksi. Semuanya POST /graphql, dan aksinya ditentukan oleh jenis operasi di dalam query:

Jenis operasiFungsinyaPadanan REST

mutationMengubah data (tambah, ganti, hapus)POST PUT PATCH DELETE

Akibatnya, sifat idempoten tidak dijamin oleh protokol. Setiap mutation harus dirancang sendiri agar aman dipanggil ulang.

3. Memasang dan Menjalankan Express Praktik

Express adalah pustaka untuk membangun server web di Node.js. Ia berperan seperti Laravel: menerima permintaan HTTP, mencocokkannya dengan rute yang terdaftar, lalu menjalankan fungsi yang menjawabnya. Bedanya, Express jauh lebih minimal. Hampir semua hal yang di Laravel sudah tersedia (validasi, ORM, autentikasi) harus ditambahkan sendiri lewat pustaka terpisah.

3.1 Persiapan: Periksa Node.js

$ node -v v22.22.0

Versi kalian boleh berbeda, asalkan 18 ke atas. Kalau perintahnya tidak dikenali atau versinya lebih rendah, pasang Node.js versi LTS terbaru dari nodejs.org dulu.

3.2 Buat Proyek dan Pasang Express

Proyek baru bernama api-mahasiswa. Proyek inilah yang kita kembangkan sepanjang Pertemuan 4 (dan dilanjutkan di Pertemuan 5). Jalankan perintah berikut satu per satu:

$ mkdir api-mahasiswa $ cd api-mahasiswa $ npm init -y $ npm pkg set type=module $ npm pkg set scripts.dev="node --watch index.js" $ npm install express
PerintahFungsinya
npm init -yMembuat package.json (KTP proyek)
npm pkg set type=moduleMengaktifkan ESM agar boleh memakai import (lihat Pertemuan 3, Section 1.2)
npm pkg set scripts.dev=...Membuat skrip npm run dev yang menjalankan server dengan --watch (dijelaskan di 3.4)
npm install expressMengunduh Express ke folder node_modules dan mencatatnya di dependencies

Sekarang package.json kalian kira-kira berisi seperti ini (nomor versi Express boleh berbeda):

{
  "name": "api-mahasiswa",
  "version": "1.0.0",
  "main": "index.js",
  "type": "module",
  "scripts": {
    "dev": "node --watch index.js"
  },
  "dependencies": {
    "express": "^5.2.1"
  }
}
Jangan unggah node_modules ke Git. Foldernya besar dan bisa dibuat ulang kapan saja dengan npm install. Kalau memakai Git, buat file .gitignore yang berisi satu baris: node_modules.

3.3 Server Pertama: index.js

Buat file index.js di folder api-mahasiswa:

// index.js
import express from 'express';

const app = express();

app.get('/', (req, res) => {
    res.send('Halo dari Express!');
});

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, (err) => {
    if (err) {
        console.error('Gagal menjalankan server:', err.message);
        process.exit(1);
    }
    console.log(`Server jalan di http://localhost:${PORT}`);
});
Bagian kodeArtinya
express()Membuat aplikasi server, kita simpan di app
app.get('/', handler)"Kalau ada permintaan GET ke alamat /, jalankan fungsi ini." Padanan Route::get di Laravel
(req, res)req = permintaan yang masuk, res = alat untuk menjawabnya
res.send(...)Mengirim jawaban berupa teks
process.env.PORT ?? 3000Port diambil dari environment kalau ada, kalau tidak pakai 3000
app.listen(PORT, ...)Mulai "mendengarkan" permintaan di port itu. Fungsi di dalamnya dipanggil setelah server siap, atau membawa err kalau gagal
Kenapa ada if (err) di listen? Di Express 5, kalau port sudah dipakai program lain, fungsi itu tetap dipanggil dan membawa error. Tanpa pemeriksaan, yang tercetak justru Server jalan di ... padahal server tidak hidup, dan program berhenti diam-diam. Dengan pemeriksaan di atas, kalian langsung melihat penyebab sebenarnya.

3.4 Jalankan dan Buka di Browser

$ npm run dev > api-mahasiswa@1.0.0 dev > node --watch index.js Server jalan di http://localhost:3000

Terminalnya tidak kembali ke prompt. Itu normal: server sedang hidup dan menunggu permintaan. Buka browser ke http://localhost:3000 dan kalian akan melihat:

Halo dari Express!

Coba juga alamat yang tidak terdaftar, misalnya http://localhost:3000/xyz. Express menjawab dengan status 404 dan teks Cannot GET /xyz, karena belum ada rute untuk alamat itu.

Untuk menghentikan server, tekan Ctrl + C di terminal.

Apa bedanya npm run dev dan node index.js?

Keduanya menjalankan server yang sama. Bedanya, npm run dev memakai node --watch: setiap kali kalian menyimpan perubahan di file, server restart sendiri. Tanpa --watch, setiap ubah kode kalian harus menghentikan dan menjalankan ulang server secara manual. Kalau kalian menyimpan file, terminal menampilkan:

Restarting 'index.js' Server jalan di http://localhost:3000

4. Studi Kasus: API Mahasiswa Praktik

Server "Halo" tadi belum berguna. Sekarang kita beri tugas nyata. Skenarionya: program studi butuh sebuah layanan yang menyimpan dan melayani data mahasiswa. Nantinya aplikasi React (Pertemuan 11) dan aplikasi lain akan memanggil layanan ini lewat HTTP. Kita bangun layanannya bertahap, dimulai dari data yang disimpan di memori (database sungguhan baru masuk di Pertemuan 6).

4.3 Endpoint Pertama: Daftar Mahasiswa

Ubah index.js agar mengimpor data itu dan menyediakan GET /mahasiswa. Bagian yang baru adalah baris import dan blok app.get('/mahasiswa', ...):

// index.js
import express from 'express';
import { mahasiswa } from './src/data/mahasiswa.js';

const app = express();

app.get('/', (req, res) => {
    res.send('Halo dari Express!');
});

app.get('/mahasiswa', (req, res) => {
    res.json(mahasiswa);
});

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, (err) => {
    if (err) {
        console.error('Gagal menjalankan server:', err.message);
        process.exit(1);
    }
    console.log(`Server jalan di http://localhost:${PORT}`);
});

Kalau npm run dev masih menyala, server sudah restart otomatis. Buka http://localhost:3000/mahasiswa di browser:

[{"id":1,"nim":"F1D021001","nama":"Andi","ipk":3.75,"semester":6},{"id":2,"nim":"F1D021002","nama":"Budi","ipk":3.2,"semester":6},{"id":3,"nim":"F1D021003","nama":"Citra","ipk":3.9,"semester":4}]

res.json(...) mengubah array JavaScript menjadi teks JSON, menambahkan header Content-Type: application/json, dan mengirimnya sebagai jawaban dengan status 200.

Masalahnya: browser hanya bisa mengirim GET lewat address bar. Bagaimana kita menguji POST, PUT, dan DELETE? Untuk itu kita butuh alat khusus: Postman, yang dibahas di section berikut.

5. Menguji API dengan Postman Praktik

Postman adalah aplikasi untuk mengirim permintaan HTTP apa saja ke sebuah server dan melihat jawabannya dengan rapi. Anggap saja sebagai browser khusus untuk developer API: kita memilih metode, menulis alamat, mengisi data yang mau dikirim, menekan Send, lalu membaca status dan isi jawabannya.

5.2 Pasang Postman

  1. Unduh dari postman.com/downloads, pasang seperti aplikasi biasa. Tersedia juga versi web di browser.
  2. Kalau diminta masuk (sign in), ikuti petunjuk di layar. Untuk latihan ini cukup memakai permintaan tunggal di dalam aplikasi.
  3. Buka Postman dan buat permintaan baru: klik New (atau tanda + untuk tab baru) lalu pilih HTTP Request.
Tampilan Postman bisa berubah antarversi. Letak tombol mungkin sedikit berbeda, tetapi istilahnya tetap sama (Method, URL, Params, Headers, Body, Send). Panduan resminya ada di Postman Learning Center.

6. Routing dengan Express Indikator 3.2 & 3.3

Routing adalah cara menentukan fungsi mana yang menjawab permintaan tertentu, berdasarkan kombinasi metode HTTP dan alamat. Di Section 3 kita sudah membuat satu rute (GET /). Sekarang kita membuat banyak rute untuk API Mahasiswa.

6.1 Mendaftarkan Rute

import express from 'express';
const app = express();

app.use(express.json());     // wajib, agar req.body bisa dibaca

app.get('/mahasiswa', (req, res) => { /* daftar semua */ });
app.get('/mahasiswa/:id', (req, res) => { /* satu data */ });
app.post('/mahasiswa', (req, res) => { /* buat baru */ });
app.put('/mahasiswa/:id', (req, res) => { /* ganti semua field */ });
app.delete('/mahasiswa/:id', (req, res) => { /* hapus */ });
Padanan LaravelExpress
Route::get('/mahasiswa', [Ctrl::class,'index'])app.get('/mahasiswa', handler)
{id} pada URL Laravel:id pada URL Express

6.2 Tiga Sumber Data pada Permintaan

Ini indikator 3.3 — kesalahan paling sering mahasiswa baru Express adalah bingung membedakan tiga tempat data bisa datang:

SumberDiakses lewatContoh URLDipakai untuk
Parameter jalurreq.params/mahasiswa/:idMengidentifikasi satu sumber daya
Parameter kuerireq.query/mahasiswa?semester=6Menyaring/mengurutkan koleksi
Badan permintaanreq.bodyTerpisah dari URL, JSONData baru dari POST/PUT/PATCH
app.get('/mahasiswa/:id', (req, res) => {
    const { id } = req.params;             // dari /mahasiswa/12  → id = "12" (STRING!)
    res.json({ id });
});

app.get('/mahasiswa', (req, res) => {
    const { semester } = req.query;         // dari ?semester=6 → juga STRING
    res.json({ semester });
});

app.post('/mahasiswa', (req, res) => {
    const { nama, nim, ipk } = req.body;   // butuh express.json()
    res.status(201).json({ nama, nim, ipk });
});
Jebakan tipe data: req.params dan req.query selalu berupa string, walau terlihat seperti angka di URL. ?semester=6 menghasilkan "6", bukan 6. Kalau langsung dibandingkan req.query.semester === 6, hasilnya selalu false. Konversi dulu: Number(req.query.semester).
Padanan di GraphQL
RESTGraphQL
req.params (/mahasiswa/12)Argumen wajib, mahasiswa(id: 12), dibaca lewat args.id
req.query (?semester=6)Argumen opsional, daftarMahasiswa(semester: 6), dibaca lewat args.semester
req.body (data dari POST)Argumen mutation, atau variabel yang dikirim terpisah dari teks query

Bedanya, argumen GraphQL punya tipe di schema. semester: Int sudah diubah menjadi angka sebelum sampai ke resolver, jadi tidak ada jebakan string seperti "6" di atas. Pengecualiannya tipe ID, yang tetap berupa teks.

6.3 Praktik: Tambah Rute ke API Mahasiswa

Kesalahan pemula paling umum: mengembalikan 200 OK untuk segala sesuatu, termasuk saat data tidak ditemukan atau validasi gagal, lalu menaruh pesan error di dalam body. Klien (termasuk React nanti) sangat bergantung pada kode status yang benar untuk memutuskan alur logikanya — jangan menyembunyikan kegagalan di balik status 200.
Padanan di GraphQL

Di GraphQL, status HTTP biasanya tetap 200 walau query-nya gagal, dan kegagalan dilaporkan di field errors pada isi jawaban. Jadi klien GraphQL memeriksa errors, bukan kode status. Kalau id tidak ditemukan, hasilnya null (bukan 404). Contoh nyatanya ada di Section 8.7.

7.2 Format Tanggapan yang Konsisten

Setiap endpoint sebaiknya mengembalikan bentuk yang seragam, sehingga klien tidak perlu menebak-nebak struktur tanggapan tiap kali memanggil endpoint berbeda.

// Berhasil — data langsung, atau dibungkus "data"
res.status(200).json({
    data: { id: 1, nama: "Andi", ipk: 3.75 }
});

// Daftar — sertakan metadata paginasi (dipakai lagi di Pertemuan 7)
res.status(200).json({
    data: [ /* ... */ ],
    meta: { total: 42, halaman: 1 }
});

// Gagal — format konsisten untuk SEMUA error
res.status(404).json({
    error: {
        pesan: "Mahasiswa dengan id 99 tidak ditemukan",
        kode: "MAHASISWA_NOT_FOUND"
    }
});
Aturan mata kuliah ini: tanggapan berhasil selalu dibungkus { data: ... } (dan meta untuk daftar), tanggapan gagal selalu dibungkus { error: { pesan, kode } }. Konsistensi ini akan sangat memudahkan penanganan error terpusat di Pertemuan 5 dan integrasi React di Pertemuan 12.
Padanan di GraphQL

Format ini kita rancang sendiri. Di GraphQL formatnya sudah ditetapkan spesifikasi: jawaban berisi data yang bentuknya mengikuti query, dan errors kalau ada yang gagal. Tidak ada pembungkus meta atau kode buatan sendiri yang perlu disepakati.

7.3 Praktik: Rapikan API Mahasiswa

Rute di Section 6 sudah jalan, tetapi tanggapannya belum seragam (kadang array langsung, kadang { pesan }) dan POST belum divalidasi. Sekarang kita terapkan aturan 7.2. Ganti isi index.js dengan versi berikut. Bagian yang berubah: pembantu kirimError, pembungkus { data } dan meta, serta validasi pada POST.

// index.js
import express from 'express';
import { mahasiswa } from './src/data/mahasiswa.js';

const app = express();
app.use(express.json());

// Pembantu: semua error memakai bentuk { error: { pesan, kode } }
const kirimError = (res, status, kode, pesan) =>
    res.status(status).json({ error: { pesan, kode } });

app.get('/', (req, res) => {
    res.send('Halo dari Express!');
});

// GET /mahasiswa — daftar, mendukung ?semester=6
app.get('/mahasiswa', (req, res) => {
    const { semester } = req.query;
    const hasil = semester
        ? mahasiswa.filter(m => m.semester === Number(semester))
        : mahasiswa;
    res.json({ data: hasil, meta: { total: hasil.length } });
});

// GET /mahasiswa/:id — satu data, 404 kalau tidak ada
app.get('/mahasiswa/:id', (req, res) => {
    const m = mahasiswa.find(x => x.id === Number(req.params.id));
    if (!m) {
        return kirimError(res, 404, 'NOT_FOUND', 'Mahasiswa tidak ditemukan');
    }
    res.json({ data: m });
});

// POST /mahasiswa — buat baru, validasi sederhana
app.post('/mahasiswa', (req, res) => {
    const { nim, nama, ipk, semester } = req.body ?? {};
    if (!nim || !nama) {
        return kirimError(res, 422, 'VALIDATION_ERROR', 'nim dan nama wajib diisi');
    }
    const baru = { id: mahasiswa.length + 1, nim, nama, ipk: ipk ?? 0, semester: semester ?? 1 };
    mahasiswa.push(baru);
    res.status(201).json({ data: baru });
});

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, (err) => {
    if (err) {
        console.error('Gagal menjalankan server:', err.message);
        process.exit(1);
    }
    console.log(`Server jalan di http://localhost:${PORT}`);
});

Kenapa req.body ?? {}? Kalau badan permintaan tidak terbaca, req.body bernilai undefined. Dengan ?? {} kita memberi object kosong sebagai cadangan, sehingga kodenya lanjut ke validasi dan mengembalikan 422 yang jelas, bukan error 500 yang membingungkan.
Selesai kalau: keempat endpoint (daftar, detail, saring, tambah) mengembalikan kode status dan format tanggapan yang benar untuk kondisi berhasil maupun gagal, dan kalian sudah mengujinya di Postman.

8. Pengenalan GraphQL Pengayaan

GraphQL adalah cara lain merancang API. Pada REST, server yang menentukan isi jawaban tiap endpoint. Pada GraphQL, klien yang menulis sendiri data apa saja yang diminta, lewat satu endpoint saja. Kita praktikkan langsung di proyek api-mahasiswa: REST yang sudah jadi tetap berjalan, GraphQL ditambahkan di sebelahnya.

Cari kotak merah muda "Padanan di GraphQL" di Section 2, 4, 5, 6, dan 7. Setiap konsep REST yang baru kalian pelajari diberi pasangannya di GraphQL, supaya perbandingannya langsung terlihat.
Posisi bagian ini: pengayaan, bukan bagian indikator 3.1–3.3. Pertemuan 5 sampai 12 tetap memakai REST. Tujuannya supaya kalian tahu pilihan lain yang banyak dipakai di industri, dan paham kapan masing-masing cocok.

8.2 Apa Itu GraphQL?

GraphQL punya satu endpoint (biasanya POST /graphql). Klien mengirim sebuah query yang menyebutkan field yang diinginkan, dan server menjawab dengan JSON yang bentuknya persis sama dengan query itu. Tiga istilah yang perlu diingat:

ResolverFungsi yang mengisi data untuk satu fieldHandler (req, res)
RESTGraphQL
EndpointBanyak URL (/mahasiswa, /mahasiswa/1/nilai, ...)Satu URL (/graphql)

8.4 Schema: Kontrak API

Buat folder src/graphql dan file schema.js. Bagian atas file ini, typeDefs, adalah schema-nya: daftar tipe data dan operasi yang boleh dipanggil klien. Bagian resolvers di bawahnya dijelaskan di 8.5.

$ mkdir -p src/graphql
// src/graphql/schema.js
import { createSchema } from 'graphql-yoga';
import { mahasiswa } from '../data/mahasiswa.js';
import { nilai } from '../data/nilai.js';

const typeDefs = /* GraphQL */ `
    type Mahasiswa {
        id: ID!
        nim: String!
        nama: String!
        ipk: Float!
        semester: Int!
        nilai: [Nilai!]!
    }

    type Nilai {
        id: ID!
        matkul: String!
        huruf: String!
    }

    type Query {
        daftarMahasiswa(semester: Int): [Mahasiswa!]!
        mahasiswa(id: ID!): Mahasiswa
    }

    type Mutation {
        tambahMahasiswa(nim: String!, nama: String!, ipk: Float, semester: Int): Mahasiswa!
    }
`;

const resolvers = {
    Query: {
        daftarMahasiswa: (parent, args) =>
            args.semester
                ? mahasiswa.filter(m => m.semester === args.semester)
                : mahasiswa,
        mahasiswa: (parent, args) =>
            mahasiswa.find(m => m.id === Number(args.id)) ?? null
    },
    Mutation: {
        tambahMahasiswa: (parent, args) => {
            const baru = {
                id: mahasiswa.length + 1,
                nim: args.nim,
                nama: args.nama,
                ipk: args.ipk ?? 0,
                semester: args.semester ?? 1
            };
            mahasiswa.push(baru);
            return baru;
        }
    },
    Mahasiswa: {
        nilai: (parent) => nilai.filter(n => n.mahasiswaId === parent.id)
    }
};

export const schema = createSchema({ typeDefs, resolvers });

Perhatikan typeDefs-nya dulu. Isinya ditulis dalam bahasa schema GraphQL, bukan JavaScript:

PenulisanArtinya
type Mahasiswa { ... }Mendefinisikan bentuk satu jenis data beserta field-nya
String, Int, Float, IDTipe dasar: teks, bilangan bulat, bilangan desimal, dan pengenal unik (dikirim sebagai teks)
nama: String!Tanda ! berarti wajib ada (tidak boleh null). Tanpa !, nilainya boleh null
nilai: [Nilai!]!Tanda [ ] berarti daftar. Ini daftar berisi Nilai yang wajib ada, dan daftarnya sendiri wajib ada (boleh kosong)
type QueryDaftar operasi baca yang boleh dipanggil klien. Ini pintu masuk untuk semua query
daftarMahasiswa(semester: Int)Operasi dengan argumen opsional semester (tanpa !), padanan ?semester=6 di REST
mahasiswa(id: ID!): MahasiswaArgumen id wajib. Hasilnya Mahasiswa tanpa !, artinya boleh null (kalau id tidak ada)
type MutationDaftar operasi yang mengubah data

Perhatikan juga bahwa Mahasiswa punya field nilai bertipe daftar Nilai. Relasi antar data ditulis langsung di schema, dan inilah yang memungkinkan satu query mengambil mahasiswa sekaligus nilainya.

8.5 Resolver: Pengisi Data

Schema hanya menyatakan apa yang tersedia. Resolver adalah fungsi yang menyatakan bagaimana data diambil, satu fungsi per field. Strukturnya mengikuti schema: Query.daftarMahasiswa mengisi query daftarMahasiswa, dan seterusnya.

ResolverYang dilakukanPadanan REST
Query.daftarMahasiswaMengembalikan semua mahasiswa, atau yang disaring per semester kalau argumen semester adaGET /mahasiswa?semester=6
Query.mahasiswaMencari satu mahasiswa berdasarkan id. Kalau tidak ada, mengembalikan nullGET /mahasiswa/:id
Mutation.tambahMahasiswaMembuat mahasiswa baru dan mengembalikannyaPOST /mahasiswa
Mahasiswa.nilaiMengambil nilai milik satu mahasiswaGET /mahasiswa/:id/nilai

Setiap resolver menerima dua parameter pertama:

  • parent — data dari tingkat di atasnya. Di Mahasiswa.nilai, parent adalah mahasiswa yang sedang diproses, sehingga kita bisa memakai parent.id
  • args — argumen yang ditulis klien di query, misalnya args.semester
Satu hal penting: resolver Mahasiswa.nilai hanya dijalankan kalau klien memintanya di query. Kalau klien hanya meminta nama, data nilai tidak diambil sama sekali.

8.7 Mencoba Query

Semua permintaan GraphQL berupa POST ke /graphql dengan body JSON berisi kunci query. Dari terminal:

{ "data": { "mahasiswa": { "nama": "Budi", "ipk": 3.2 } } }

Mutation

Menambah data memakai kata kunci mutation. Query di bawah menambah Dewi, dan kita minta langsung id, nama, dan semester hasilnya:

Tampilan Postman (ilustrasi)
POST{{baseUrl}}/graphqlSend
ParamsHeadersBody
GraphQL QUERY mutation { tambahMahasiswa(nim: "F1D021004", nama: "Dewi", ipk: 3.5, semester: 2) { id nama semester } }
Response200 OK
{ "data": { "tambahMahasiswa": { "id": "4", "nama": "Dewi", "semester": 2 } } }

Perhatikan id berbentuk teks ("4"), bukan angka, karena tipe ID di GraphQL selalu dikirim sebagai teks. Buktikan datanya benar-benar bertambah, juga lewat GraphQL:

$ curl -X POST http://localhost:3000/graphql \ -H "Content-Type: application/json" \ -d '{"query":"{ daftarMahasiswa { id nama } }"}' {"data":{"daftarMahasiswa":[{"id":"1","nama":"Andi"},{"id":"2","nama":"Budi"},{"id":"3","nama":"Citra"},{"id":"4","nama":"Dewi"}]}}

Karena GraphQL dan REST memakai array mahasiswa yang sama, Dewi juga muncul di GET /mahasiswa.

Kalau query salah

Coba minta field yang tidak ada di schema, yaitu alamat:

Tampilan Postman (ilustrasi)
POST{{baseUrl}}/graphqlSend
ParamsHeadersBody
GraphQL QUERY { mahasiswa(id: 1) { nama alamat } }
Response200 OK
{ "errors": [ { "message": "Cannot query field \"alamat\" on type \"Mahasiswa\". Did you mean \"nama\"?", "locations": [ { "line": 4, "column": 5 } ], "extensions": { "code": "GRAPHQL_VALIDATION_FAILED" } } ] }

Perhatikan dua hal. Pertama, statusnya tetap 200, padahal permintaannya gagal. Bandingkan dengan Section 7.1: di REST, kegagalan harus dinyatakan lewat kode status, sedangkan di GraphQL klien harus memeriksa apakah ada field errors pada jawaban. Kedua, pesan errornya informatif: server memberi tahu field mana yang salah dan menyarankan nama. Karena schema adalah kontrak, server bisa memeriksa query sebelum menjalankan resolver apa pun.

Bagaimana dengan id yang tidak ada?

Tampilan Postman (ilustrasi)
POST{{baseUrl}}/graphqlSend
ParamsHeadersBody
GraphQL QUERY { mahasiswa(id: 99) { nama } }
Response200 OK
{ "data": { "mahasiswa": null } }

Tidak ada error: mahasiswa bernilai null, karena di schema tipenya Mahasiswa tanpa !. Berbeda dengan REST yang akan menjawab 404.

8.8 REST atau GraphQL?

Keduanya bukan saling menggantikan. Pilihan tergantung kebutuhan:

SituasiLebih cocok
API sederhana dengan operasi CRUD yang jelasREST
Memanfaatkan cache HTTP, CDN, atau alat standar yang sudah mengenal URL dan kode statusREST
Banyak jenis klien (web, Android, iOS) yang masing-masing butuh data berbeda dari sumber yang samaGraphQL
Data saling berelasi dan satu layar sering butuh gabungan beberapa sumber dayaGraphQL
Tim kecil dan waktu terbatasREST (lebih sedikit konsep yang perlu dipelajari)
GraphQL bukan tanpa harga. Klien bisa menulis query yang sangat dalam atau sangat berat, sehingga server perlu dibatasi (kedalaman dan biaya query). Resolver juga mudah menjadi lambat kalau tiap item di daftar memicu pengambilan data tambahan ke database sendiri-sendiri (masalah N+1, dibahas di Pertemuan 7). Untuk proyek mata kuliah ini, REST sudah cukup, dan itu yang kita pakai ke depan.

9. Latihan Mandiri: Lengkapi API Mahasiswa Latihan

Dua endpoint dari rancangan di Section 4.1 belum dibuat: PUT dan DELETE. Lengkapi sendiri di proyek api-mahasiswa, lalu uji semuanya di Postman. Gunakan pola GET /mahasiswa/:id sebagai contoh, dan format tanggapan dari Section 7.

Tugas

  1. Tambahkan PUT /mahasiswa/:id untuk mengganti seluruh data satu mahasiswa. Kembalikan 404 kalau id tidak ada.
  2. Tambahkan DELETE /mahasiswa/:id. Kembalikan 204 No Content (tanpa body) kalau berhasil.
  3. Tambahkan validasi: ipk harus di antara 0 dan 4, kalau tidak kembalikan 422.
  4. Tambahkan dukungan ?urutkan=ipk pada GET /mahasiswa yang mengurutkan hasil berdasarkan IPK menurun.
  5. (GraphQL) Tambahkan field jumlahMatkul: Int! pada type Mahasiswa yang menghitung banyaknya nilai milik mahasiswa itu (resolver di Mahasiswa, seperti nilai). Uji dengan query yang meminta nama dan jumlahMatkul.
  6. (GraphQL) Tambahkan mutation hapusMahasiswa(id: ID!): Boolean! yang menghapus mahasiswa dan mengembalikan true kalau berhasil, false kalau id tidak ada. Uji lewat Postman atau GraphiQL.
Menuju Pertemuan 5: kalian akan sadar kode di atas mulai berulang — setiap handler mengecek error secara manual. Pertemuan 5 memperkenalkan middleware dan penanganan error terpusat untuk merapikan ini.
