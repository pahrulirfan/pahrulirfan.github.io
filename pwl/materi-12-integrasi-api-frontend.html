2. CORS Indikator 6.6

Di Pertemuan 10 (Section 2.2) kita sudah menambahkan cors() ke API. Sekarang kita lihat sendiri mengapa itu diperlukan, dari sisi browser.

Origin = protokol + host + port. http://localhost:5173 dan http://localhost:3000 berbeda origin (port beda). Aturan bawaan browser (Same-Origin Policy): JavaScript dari satu origin tidak boleh membaca respons dari origin lain, kecuali origin tujuan mengizinkan lewat header Access-Control-Allow-Origin. CORS adalah mekanisme izin itu.

Yang memblokir adalah browser, bukan server. Request tetap sampai ke API dan API tetap menjawab. Browser-lah yang menolak menyerahkan jawabannya ke JavaScript. Itu sebabnya curl dan Postman tidak pernah kena CORS.

2.1 Lihat Error-nya Sendiri

Untuk percobaan, hapus (atau beri komentar) baris app.use(cors(...)) di api-mahasiswa dan jalankan ulang API. Dengan front end berjalan di localhost:5173, buka DevTools → Console dan ketik:

Console di localhost:5173
fetch('http://localhost:3000/mahasiswa')

Chrome menampilkan error seperti ini (tulisan persisnya bisa sedikit berbeda antar browser):

Access to fetch at 'http://localhost:3000/mahasiswa' from origin 'http://localhost:5173' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Cek di sisi API dengan curl (menyamar sebagai browser dari 5173 lewat header Origin). Perhatikan: tidak ada header Access-Control-Allow-Origin di respons:

$ curl -i http://localhost:3000/mahasiswa -H "Origin: http://localhost:5173"
HTTP/1.1 401 Unauthorized Content-Type: application/json; charset=utf-8 {"error":{"pesan":"Token diperlukan","kode":"TOKEN_DIPERLUKAN"}}

Respons 401 itu sendiri benar (belum login). Tetapi karena headernya tidak ada, browser menyembunyikannya, dan JavaScript hanya menerima kegagalan umum. Bahkan error yang seharusnya bermakna (401, 404, 500) ikut tertutup oleh error CORS.

2.2 Perbaikan di API

Kembalikan cors() di index.js (npm install cors bila belum). Letakkan sebelum semua route dan middleware autentikasi, supaya setiap respons, termasuk respons error, memuat header CORS (urutan middleware, Pertemuan 5):

api-mahasiswa/index.js
import cors from 'cors';

app.use(cors({ origin: 'http://localhost:5173' }));   // sebelum route dan auth
app.use(express.json());

Jalankan ulang API, ulangi curl yang sama:

HTTP/1.1 401 Unauthorized Access-Control-Allow-Origin: http://localhost:5173 Vary: Origin Content-Type: application/json; charset=utf-8 {"error":{"pesan":"Token diperlukan","kode":"TOKEN_DIPERLUKAN"}}

Sekarang ada Access-Control-Allow-Origin: http://localhost:5173. Ulangi fetch(...) di Console: tidak ada error CORS, dan respons 401 sudah bisa dibaca:

Console di localhost:5173
const r = await fetch('http://localhost:3000/mahasiswa')
await r.json()
// { error: { pesan: 'Token diperlukan', kode: 'TOKEN_DIPERLUKAN' } }

Untuk request yang “tidak sederhana” (memakai header Authorization, atau method seperti DELETE), browser mengirim dulu request OPTIONS untuk bertanya “boleh nggak saya kirim request ini?”. Hanya jika jawabannya mengizinkan, request sebenarnya dikirim.

2.4 Origin Lain Tetap Ditolak

Dengan origin: 'http://localhost:5173', header yang dikembalikan selalu 5173. Halaman dari origin lain (misalnya 4000) menerima header yang tidak cocok dengan origin-nya, sehingga browser tetap memblokir:

$ curl -i http://localhost:3000/mahasiswa -H "Origin: http://localhost:4000"
HTTP/1.1 401 Unauthorized Access-Control-Allow-Origin: http://localhost:5173 Vary: Origin Content-Type: application/json; charset=utf-8

3. Helper API: fetch + .env Indikator 6.5

Setiap halaman akan memanggil API. Jika fetch ditulis berulang di tiap halaman, kita menyalin hal yang sama: alamat API, header token, membaca JSON, memeriksa error. Lebih rapi dibuat satu fungsi yang dipakai semua. Fungsi ini murni JavaScript dan identik untuk Vue dan React.

3.1 Alamat API di .env

Alamat API jangan ditulis di banyak tempat (nanti berbeda di produksi). Simpan di file .env di akar project (sejajar dengan package.json), di kedua project:

.env (file baru, di akar project)
VITE_API_URL=http://localhost:3000
  • Vite hanya membuka variabel yang diawali VITE_ ke kode front end, dibaca dengan import.meta.env.VITE_API_URL. (Ini mirip process.env di Node dengan dotenv di Pertemuan 6, tetapi untuk browser.)
  • Semua yang berawalan VITE_ ikut terkirim ke browser dan bisa dibaca siapa saja. Jangan pernah menaruh secret di sini; hanya alamat dan pengaturan non-rahasia. Secret (seperti JWT_SECRET) tetap di .env API.
  • Perubahan .env baru terbaca setelah npm run dev dijalankan ulang.

3.2 Fungsi api()

Fungsi ini dibuat bertahap dalam enam langkah, dan setiap langkah bisa dicoba di Console. Buat src/api.js di kedua project (isi sama persis). Setelah menyimpan, refresh halaman dulu supaya Console memakai versi terbaru. Baris berlatar hijau adalah baris yang baru atau diubah pada langkah itu.

Langkah 1: Panggil API dan Baca JSON

src/api.js (file baru)
const BASE_URL = import.meta.env.VITE_API_URL

export async function api(path) {
  const res = await fetch(BASE_URL + path)
  return res.json()
}

src/auth.js (file baru)
import { ref, computed } from 'vue'
import { api, ambilToken, simpanToken, hapusToken } from './api.js'

const token = ref(ambilToken())

export const sudahLogin = computed(() => token.value !== null)

export async function login(email, password) {
  const hasil = await api('/auth/login', { method: 'POST', body: { email, password } })
  simpanToken(hasil.data.token)
  token.value = hasil.data.token
}

export function logout() {
  hapusToken()
  token.value = null
}

Belum ada perubahan di browser; auth.js dipakai di langkah berikut.

}

10.2 Code Review Antar Kelompok

Sub-CPMK 6 juga dinilai lewat code review antar kelompok (RPS Catatan B). Setiap kelompok meninjau kode kelompok lain dan memberi masukan yang membangun. Membaca kode orang lain adalah keterampilan yang sama pentingnya dengan menulis kode sendiri di dunia kerja.

Daftar Periksa Review

  • Keempat state (loading, error, kosong, data) ditangani pada setiap pengambilan data?
  • Respons error diperiksa lewat res.ok (bukan mengandalkan fetch gagal sendiri)?
  • Request memakai satu helper (api.js), bukan fetch yang disalin di banyak tempat?
  • Alamat API dibaca dari .env, tidak di-hardcode, dan tidak ada secret di variabel VITE_?
  • Token disertakan otomatis dan dihapus saat logout atau ditolak (401)?
  • Pesan error dari API sampai ke pengguna, dan input form tidak hilang saat server menolak?
  • Tidak ada state yang diubah langsung (React: selalu lewat setter dengan salinan baru), dan key / :key unik?
  • Form memvalidasi input sebelum dikirim, dan backend tetap memvalidasi?
  • CORS hanya mengizinkan origin front end yang sebenarnya (bukan * di produksi)?
Cara memberi masukan yang membangun: fokus pada apa yang bisa diperbaiki dan mengapa, bukan menghakimi. Misalnya: “Di halaman Detail, bagian ini belum menangani kalau fetch gagal. Mungkin bisa ditambahkan catch seperti di DaftarView?” jauh lebih membantu daripada “kodenya salah”.

10.3 Tugas Kelompok

Terapkan semuanya pada backend kelompok (pengembangan dari API individu Pertemuan 1–10), dengan framework pilihan kelompok (Vue atau React):

  1. Front end tersambung ke API kelompok lewat api.js dan .env; CORS dikonfigurasi dengan origin yang benar.
  2. Minimal: halaman daftar (dengan empat state), detail, login/logout dengan rute dilindungi, tambah, dan hapus.
  3. Lulus seluruh matriks 10.1 dan dapat dijelaskan setiap anggota kelompok saat wawancara kode.
  4. Memberi review tertulis (daftar periksa di atas) untuk satu kelompok lain.
