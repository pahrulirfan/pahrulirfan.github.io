1. Jenis dan Tingkatan Pengujian Pengantar

Sejauh ini kalian menguji secara manual: curl, REST client (Pertemuan 5), klik-klik di antarmuka React (Pertemuan 11–12). Cara ini tidak bisa diulang secara konsisten setiap kali kode berubah. Pengujian otomatis menjalankan pemeriksaan yang sama, berkali-kali, tanpa campur tangan manusia.

1.1 Piramida Pengujian

E2Esedikit, lambat, mahal — Playwright
Integrasisedang — API + basis data
Unitbanyak, cepat, murah — Vitest
TingkatanMengujiKecepatanPerkakas kita
UnitSatu fungsi berdiri sendiri, terisolasiSangat cepat (ms)Vitest
IntegrasiBeberapa bagian bekerja sama (service + basis data)SedangVitest + database uji
End-to-End (E2E)Alur pengguna utuh, lewat browser sungguhanLambat (detik)Playwright
Mengapa piramida, bukan kotak sama besar? Pengujian unit murah dan cepat — tulis banyak. Pengujian E2E mahal (butuh browser, server, database sungguhan berjalan) — tulis hanya untuk alur paling kritis. Piramida terbalik (E2E lebih banyak dari unit) membuat pipeline CI menjadi sangat lambat dan rapuh.

2. Pengujian Unit dengan Vitest Indikator 7.1

$ npm install -D vitest

2.1 Menguji Fungsi Murni

Yang paling mudah diuji: fungsi yang tidak bergantung apa pun di luar dirinya — ingat konsep "fungsi sebagai nilai" dari Materi 1.

// src/utils/hitung.js
export function hitungRataRata(nilai) {
    if (nilai.length === 0) return 0;
    return nilai.reduce((a, b) => a + b, 0) / nilai.length;
}
// src/utils/hitung.test.js
import { describe, it, expect } from 'vitest';
import { hitungRataRata } from './hitung.js';

describe('hitungRataRata', () => {
    it('menghitung rata-rata dengan benar', () => {
        expect(hitungRataRata([80, 90, 70])).toBe(80);
    });

    it('mengembalikan 0 untuk larik kosong', () => {
        expect(hitungRataRata([])).toBe(0);
    });

    it('menangani satu elemen', () => {
        expect(hitungRataRata([100])).toBe(100);
    });
});

2.2 Menguji Service (Ingat Pemisahan Lapis dari Pertemuan 5!)

Inilah manfaat nyata memisahkan service dari controller: service bisa diuji tanpa menjalankan server HTTP sungguhan.

// src/services/mahasiswa.service.test.js
import { describe, it, expect } from 'vitest';
import { buatMahasiswa } from './mahasiswa.service.js';
import { AppError } from '../utils/AppError.js';

describe('buatMahasiswa', () => {
    it('menolak input tanpa nama', async () => {
        await expect(buatMahasiswa({ nim: 'F1D021099' }))
            .rejects.toThrow(AppError);
    });
});

3. Pengujian End-to-End dengan Playwright Indikator 7.2

Pengujian E2E menjalankan browser sungguhan dan mensimulasikan alur pengguna nyata — login, mengisi form, melihat hasilnya — menguji frontend dan backend sekaligus, persis seperti yang kalian bangun di Pertemuan 11–12.

$ npm install -D @playwright/test $ npx playwright install
// e2e/login.spec.js
import { test, expect } from '@playwright/test';

test('mahasiswa bisa login dan melihat daftar', async ({ page }) => {
    await page.goto('http://localhost:5173/login');

    await page.fill('input[name="email"]', 'dosen@unram.ac.id');
    await page.fill('input[name="password"]', 'rahasia123');
    await page.click('button[type="submit"]');

    // Setelah login berhasil, halaman berpindah ke daftar mahasiswa
    await expect(page).toHaveURL('http://localhost:5173/');
    await expect(page.getByText('Andi')).toBeVisible();
});

test('login gagal menampilkan pesan galat', async ({ page }) => {
    await page.goto('http://localhost:5173/login');
    await page.fill('input[name="email"]', 'salah@unram.ac.id');
    await page.fill('input[name="password"]', 'salahjuga');
    await page.click('button[type="submit"]');

    await expect(page.getByText('Email atau kata sandi salah')).toBeVisible();
});

3.3 Menguji API dengan Postman Collection dan Newman

Vitest dan Supertest menguji API dari dalam kode. Ada satu lapis lagi yang berguna: menguji API dari luar, sebagai klien HTTP sungguhan, tanpa menyentuh kode sumbernya sama sekali. Ini berguna untuk memverifikasi API yang sudah dirilis di server, dan menjadi jembatan alami dari berkas requests.http yang kalian pakai sejak Pertemuan 5.

Alurnya tiga langkah: susun permintaan sebagai Collection di Postman → tambahkan pemeriksaan pada tab Tests → jalankan seluruh Collection dari terminal dengan Newman.

Menulis pemeriksaan di tab Tests

Setiap permintaan di Postman punya tab Tests, berisi JavaScript yang dijalankan setelah tanggapan diterima.

// Tests untuk POST /mahasiswa
pm.test('status code 201', () => {
    pm.response.to.have.status(201);
});

pm.test('Content-Type adalah application/json', () => {
    pm.expect(pm.response.headers.get('Content-Type')).to.include('application/json');
});

pm.test('tanggapan memuat id mahasiswa baru', () => {
    const { data } = pm.response.json();
    pm.expect(data).to.be.an('object');
    pm.expect(data.id).to.not.be.empty;

    // Simpan untuk dipakai permintaan berikutnya dalam Collection yang sama
    pm.environment.set('mahasiswaId', data.id);
});

Baris terakhir itu kuncinya. pm.environment.set() menyimpan nilai dari satu tanggapan ke dalam environment variable, sehingga permintaan berikutnya bisa memakainya sebagai {{mahasiswaId}} di URL. Dengan begitu satu Collection bisa menguji alur utuh — buat, baca, ubah, hapus — secara berurutan, tanpa id yang ditulis manual.

Menjalankan tanpa membuka Postman

Ekspor Collection (format v2.1) dan Environment menjadi dua berkas JSON, simpan di dalam repositori proyek, lalu jalankan dengan Newman.

$ npm install --save-dev newman $ npx newman run mahasiswa-api.postman_collection.json \ --environment lokal.postman_environment.json

Newman mengembalikan exit code bukan-nol bila ada pemeriksaan yang gagal — syarat agar sebuah perintah bisa dipakai di pipeline CI. Karena itu ia bisa ditambahkan sebagai satu langkah lagi pada alur kerja GitHub Actions di Section 5.

# .github/workflows/ci.yml — potongan tambahan
      - name: Jalankan server di latar belakang
        run: npm start &

      - name: Tunggu server siap
        run: npx wait-on http://localhost:3000/health

      - name: Uji API dengan Newman
        run: npx newman run mahasiswa-api.postman_collection.json \
               --environment ci.postman_environment.json

4. Uji Regresi Keamanan Indikator 7.3

Ingat kerentanan yang ditemukan dan diperbaiki di Pertemuan 10? Perbaikan manual bisa rusak lagi tanpa sengaja saat kode terus dikembangkan — misalnya seseorang di kelompok menghapus middleware butuhPeran tanpa sadar. Uji regresi keamanan mengubah temuan itu menjadi test otomatis yang gagal kalau kerentanan itu muncul kembali.

// src/routes/mahasiswa.security.test.js
import { describe, it, expect } from 'vitest';
import request from 'supertest';
import app from '../app.js';

describe('Regresi keamanan — Broken Access Control (temuan Pertemuan 10)', () => {
    it('DELETE /mahasiswa/:id HARUS ditolak untuk peran mahasiswa', async () => {
        const tokenMahasiswa = await loginSebagai('mahasiswa');

        const respons = await request(app)
            .delete('/mahasiswa/1')
            .set('Authorization', `Bearer ${tokenMahasiswa}`);

        expect(respons.status).toBe(403);   // kalau ini pernah 200 lagi → BUG kambuh
    });

    it('GET /pesanan/:id HARUS ditolak untuk data milik user lain (IDOR)', async () => {
        const tokenUserA = await loginSebagai('userA');

        const respons = await request(app)
            .get('/pesanan/99')   // pesanan #99 milik userB
            .set('Authorization', `Bearer ${tokenUserA}`);

        expect(respons.status).toBe(403);
    });
});
Ini kewajiban minimum: setiap kelompok wajib mengubah minimal satu temuan dari SECURITY.md (Pertemuan 10) menjadi test otomatis seperti contoh di atas. Test ini menjadi jaring pengaman permanen sampai akhir semester.

5. Integrasi Berkelanjutan (CI) Indikator 7.4

Continuous Integration menjalankan seluruh pengujian secara otomatis setiap kali ada perubahan kode di-push ke repositori — tidak lagi bergantung pada seseorang mengingat untuk menjalankan test secara manual.

5.1 Alur Pipeline

git push
memicu pipeline
→
npm ci
pasang dependensi
→
npm audit
cek kerentanan (Pert. 10)
→
vitest run
unit + regresi keamanan
→
playwright test
E2E

5.2 GitHub Actions

# .github/workflows/ci.yml
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_PASSWORD: postgres
        ports: ['5432:5432']

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'

      - run: npm ci
      - run: npm audit --audit-level=high
      - run: npx prisma migrate deploy
      - run: npx vitest run
      - run: npx playwright install --with-deps
      - run: npx playwright test
BagianFungsi
on: [push, pull_request]Pipeline jalan setiap push DAN setiap pull request
services: postgresMenyediakan basis data uji sungguhan untuk pipeline (bukan mock)
npm ciPasang dependensi PERSIS sesuai package-lock.json (Materi 1)
npm audit --audit-level=highPipeline GAGAL kalau ada kerentanan tingkat tinggi (Pertemuan 10)
Ini penyambungan langsung dengan Pertemuan 10: npm audit yang dulu dijalankan manual sekali, sekarang berjalan otomatis pada setiap perubahan sampai akhir semester — sesuai RPS Catatan D.10.

6. Batas Kemampuan Pengujian Otomatis Indikator 7.6

Pengujian otomatis sangat berguna, tetapi bukan jaminan mutlak tidak ada bug. Penting memahami batasnya agar tidak salah percaya diri.

Yang BISA dijamin pengujian otomatisYang TIDAK BISA dijamin
Fungsi menghasilkan output yang benar untuk kasus yang DIUJIKasus yang tidak terpikirkan untuk ditulis testnya
Perilaku yang sudah benar tidak rusak diam-diam (regresi)Aplikasi "terasa" enak dipakai (UX)
Endpoint mengembalikan status code yang benarPerforma di bawah beban ribuan pengguna sungguhan
Alur login-CRUD-logout berjalan (E2E)Semua kombinasi input yang mungkin (ruang kemungkinan tak terbatas)
"Semua test hijau" ≠ "aplikasi bebas bug". Test hanya menjamin apa yang ditulis untuk diuji. Aspek seperti kejelasan pesan galat bagi pengguna awam, kenyamanan alur, atau kerentanan yang belum pernah terpikirkan tetap butuh penilaian manusia — termasuk tinjauan kode antar kelompok (Pertemuan 12) dan audit manual (Pertemuan 10).

7. Praktik: Susun Pipeline Lengkap Latihan

Lengkapi proyek kelompok dengan pengujian otomatis dan pipeline CI, menyatukan seluruh materi hari ini.

Langkah 1 — Pasang Vitest & Supertest

$ npm install -D vitest supertest

Langkah 2 — Uji Unit untuk Service

Tulis minimal 3 test unit untuk fungsi service yang sudah ada (validasi, perhitungan) mengikuti pola Section 2.2.

Langkah 3 — Uji Regresi Keamanan

Ambil minimal satu temuan dari SECURITY.md milik kelompok (Pertemuan 10), ubah menjadi test otomatis mengikuti pola Section 4.

Langkah 4 — Uji E2E untuk Satu Alur Utuh

$ npm install -D @playwright/test $ npx playwright install

Tulis satu test E2E untuk alur paling penting di aplikasi kalian (login → lihat data → tambah data, mengikuti pola Section 3).

Langkah 5 — Buat Pipeline CI

Buat .github/workflows/ci.yml mengikuti Section 5.2, sesuaikan dengan struktur proyek kalian.

Langkah 6 — Push dan Verifikasi

$ git add . $ git commit -m "Tambah pengujian otomatis dan pipeline CI" $ git push

Buka tab Actions di repositori GitHub, pastikan pipeline berjalan dan seluruh langkah berhasil (centang hijau).

Selesai kalau: pipeline CI di GitHub Actions berjalan otomatis setelah push, menjalankan npm audit, test unit, uji regresi keamanan, dan minimal satu test E2E — semuanya lulus (atau, kalau sengaja dibuat gagal untuk latihan, kalian bisa menjelaskan mengapa).

Latihan Mandiri

  1. Sengaja rusak salah satu middleware otorisasi (hapus butuhPeran dari satu rute), push, dan amati pipeline CI gagal pada test regresi keamanan. Kembalikan lagi, buktikan pipeline hijau kembali.
  2. Tambahkan badge status CI ("build passing") di README repositori.
  3. Diskusikan dalam kelompok: sebutkan satu skenario nyata yang tidak tercakup test kalian saat ini, dan mengapa itu penting (Section 6).
Menuju Pertemuan 14–15: dengan pipeline CI yang hijau sebagai jaring pengaman, kelompok kalian siap merilis aplikasi ke layanan hosting publik.
