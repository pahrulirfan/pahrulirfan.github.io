1. Core Web Vitals Indikator 8.5

Aplikasi kalian sudah live sejak Pertemuan 14. Sekarang saatnya mengukur seberapa baik pengalaman pengguna sungguhan — bukan lagi "apakah berfungsi", tetapi "seberapa cepat dan nyaman dipakai". Core Web Vitals adalah tiga metrik resmi dari Google untuk mengukur ini.

1.1 Tiga Metrik Utama

LCP
Largest Contentful Paint — seberapa cepat elemen terbesar (biasanya gambar/judul utama) selesai tampil
≤2.5s baik≤4s cukup>4s buruk
INP
Interaction to Next Paint — seberapa cepat halaman merespons setelah pengguna klik/ketik
≤200ms baik≤500ms cukup>500ms buruk
CLS
Cumulative Layout Shift — seberapa banyak elemen "meloncat" tanpa diinginkan saat halaman dimuat
≤0.1 baik≤0.25 cukup>0.25 buruk

1.2 Penyebab Umum dan Kaitannya dengan Materi Sebelumnya

MetrikPenyebab umum burukKaitan dengan pertemuan sebelumnya
LCP tinggiGambar besar tidak dioptimasi, JS bundle besar diblokirBuild produksi (Pertemuan 14) meminifikasi, tapi gambar tetap perlu dikompres manual
INP tinggiPerhitungan berat di thread utama saat klikIngat event loop & blocking (Pertemuan 3) — hal yang sama berlaku di browser
CLS tinggiGambar tanpa ukuran, data async yang tiba-tiba mengubah tinggi elemenLoading state (Pertemuan 12) yang baik mencegah "loncatan" saat data tiba

2. Audit Aksesibilitas WCAG 2.2 Indikator 8.6

Aksesibilitas berarti aplikasi bisa dipakai oleh pengguna dengan keterbatasan — penglihatan, pendengaran, motorik, kognitif. WCAG 2.2 adalah standar internasional yang menjadi acuan.

2.1 Empat Prinsip WCAG (POUR)

PrinsipArtinyaContoh pada aplikasi kalian
PerceivableBisa dipersepsikanGambar punya teks alternatif (alt), kontras warna cukup
OperableBisa dioperasikanSemua fungsi bisa dicapai lewat keyboard, bukan hanya mouse
UnderstandableBisa dipahamiPesan galat form jelas (ingat Pertemuan 11), label input jelas
RobustKokohHTML semantik yang benar, kompatibel dengan pembaca layar

2.2 Temuan Umum pada Proyek React Mahasiswa

🖼️
Gambar tanpa alt
<img src="foto.jpg" /> → pembaca layar tidak tahu ini gambar apa.
Perbaikan: <img src="foto.jpg" alt="Foto profil mahasiswa" />
⌨️
Elemen interaktif dari <div>, bukan <button>
<div onClick={hapus}>Hapus</div> → tidak bisa dijangkau lewat tombol Tab di keyboard.
Perbaikan: <button onClick={hapus}>Hapus</button>
🏷️
Input tanpa <label>
<input placeholder="Nama" /> saja → placeholder hilang saat mulai mengetik, dan tidak terbaca pembaca layar.
Perbaikan: <label htmlFor="nama">Nama</label><input id="nama" />
🎨
Kontras warna kurang
Teks abu-abu terang di atas latar putih — sulit dibaca pengguna low-vision.
Perbaikan: rasio kontras minimal 4.5:1 untuk teks biasa (WCAG AA)

2.3 Mengaudit dengan Lighthouse / axe DevTools

$ npx lighthouse https://antarmuka-mahasiswa.contoh-hosting.app --only-categories=accessibility --view Accessibility: 78 Failing audits: ✗ Image elements do not have [alt] attributes ✗ Buttons do not have an accessible name ✗ Background and foreground colors do not have sufficient contrast ratio
Lighthouse/axe hanya mendeteksi sekitar 30-40% masalah aksesibilitas yang bisa dideteksi otomatis (mirip batas pengujian otomatis pada Pertemuan 13). Uji manual sederhana: coba navigasi seluruh aplikasi hanya dengan keyboard (Tab, Enter, Escape) tanpa menyentuh mouse sama sekali.

3. Uji Jalur Cadangan Indikator 8.7

Ingat Section 5 dan 7 dari Pertemuan 14? Sekarang saatnya benar-benar membuktikan jalur cadangan bekerja, bukan hanya berasumsi.

Protokol Pembuktian

$ # Di komputer LAIN (atau folder benar-benar baru), bukan folder kerja biasa
git clone https://github.com/kelompok-kalian/proyek-pwl.git
cd proyek-pwl
# Ikuti README.md PERSIS seperti tertulis, tanpa bertanya ke anggota lain
Yang dicekKriteria lulus
Kelengkapan READMETidak ada langkah yang "diasumsikan sudah tahu"
.env.exampleSemua variabel yang dibutuhkan tercantum namanya
Migrasi & seednpx prisma migrate deploy dan db seed berjalan tanpa galat
Aplikasi berjalan penuhBackend dan frontend bisa dijalankan lokal, terhubung satu sama lain
Ini indikator yang sangat sering gagal bukan karena aplikasinya rusak, melainkan karena README ditulis dengan asumsi pembacanya "sudah tahu" sesuatu yang sebenarnya hanya diketahui anggota kelompok. Uji dengan orang yang benar-benar belum pernah menyentuh proyek kalian.

4. Gladi Demonstrasi Persiapan EAS

EAS (Minggu 16) berupa demonstrasi produk kelompok disertai wawancara kode per individu — setiap anggota harus bisa menjelaskan bagian kode yang menjadi tanggung jawabnya. Pertemuan 15 adalah kesempatan terakhir berlatih sebelum itu.

Struktur Demonstrasi yang Disarankan

  1. Alur pengguna utuh (5 menit) — login → lihat data → tambah/ubah data → logout, langsung di aplikasi yang live
  2. Bukti keamanan (2 menit) — tunjukkan SECURITY.md, jelaskan satu temuan dan mitigasinya
  3. Bukti pengujian (2 menit) — tunjukkan pipeline CI hijau di GitHub Actions
  4. Wawancara kode per individu — setiap anggota menjelaskan bagian yang dikerjakan sendiri
Siapkan jalur cadangan untuk demonstrasi itu sendiri. Kalau layanan hosting bermasalah tepat saat presentasi, siapkan aplikasi berjalan lokal (Section 3) sebagai cadangan — jangan sampai seluruh demonstrasi bergantung pada satu titik kegagalan.

5. Praktik: Klinik Audit & Uji Jalur Cadangan Latihan

Sesi studio hari ini: audit menyeluruh terhadap aplikasi kelompok, ditambah pendampingan menyelesaikan proyek akhir.

Langkah 1 — Audit Performa

$ npx lighthouse https://alamat-aplikasi-kelompok.app --view

Catat skor LCP, INP, CLS. Untuk setiap metrik yang "cukup" atau "buruk" (Section 1.1), identifikasi satu penyebab konkret dan perbaiki (kompres gambar, tambahkan width/height eksplisit pada <img>, dst).

Langkah 2 — Audit Aksesibilitas

$ npx lighthouse https://alamat-aplikasi-kelompok.app --only-categories=accessibility --view

Perbaiki minimal 3 temuan (Section 2.2). Uji navigasi keyboard secara manual di halaman utama.

Langkah 3 — Uji Jalur Cadangan

Jalankan protokol pembuktian Section 3 dengan anggota kelompok yang belum familiar dengan bagian setup.

Langkah 4 — Daftar Periksa Penyerahan Akhir

Selesai kalau: seluruh daftar periksa di atas tercentang. Proyek kelompok kalian sekarang siap untuk EAS di Minggu 16.
