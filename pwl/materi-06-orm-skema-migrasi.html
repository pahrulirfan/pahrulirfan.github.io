Karena itu kita rasakan dulu tanpa ORM. Dari awal sampai akhir, controller dan routes tidak berubah; yang diganti hanya lapis data (dan service hanya menambah await).

1.3 Buat Tabel mahasiswa

SQL adalah bahasa untuk berbicara dengan database. Perintah CREATE TABLE membuat tabel baru. Pilih database api_mahasiswa di sisi kiri, klik tab SQL, ketik perintah berikut, lalu klik Go (Kirim):

CREATE TABLE mahasiswa (

1.4 Mengisi dan Mengelola Data dengan SQL

Empat operasi dasar data (CRUD) masing-masing punya satu perintah SQL. Keempatnya akan terus kita temui sampai akhir pertemuan, dengan wujud yang berbeda-beda:

OperasiPerintah SQLContoh
Create (tambah)INSERT INTOINSERT INTO mahasiswa (nim, nama) VALUES ('F1D021050', 'Gita')
Read (baca)SELECTSELECT * FROM mahasiswa WHERE semester = 6
Update (ubah)UPDATEUPDATE mahasiswa SET ipk = 4 WHERE id = 1
Delete (hapus)DELETE FROMDELETE FROM mahasiswa WHERE id = 1

a. Isi data awal (INSERT)

Tab SQL, ketik, lalu Go. Kolom id dan createdAt sengaja tidak ditulis karena terisi otomatis:

INSERT INTO mahasiswa (nim, nama, ipk, semester) VALUES
('F1D021001', 'Andi',  3.75, 6),
('F1D021002', 'Budi',  3.20, 6),
('F1D021003', 'Citra', 3.90, 4);

Buka tab Browse; seharusnya tampil tiga baris:

idnimnamaipksemestercreatedAt
1F1D021001Andi3.7562026-11-04 22:24:29.463
2F1D021002Budi3.262026-11-04 22:24:29.463
3F1D021003Citra3.942026-11-04 22:24:29.463

Kolom createdAt kalian akan berisi waktu saat kalian menjalankan perintah.

b. Baca data (SELECT)

Jalankan satu per satu di tab SQL dan amati hasilnya:

SELECT * FROM mahasiswa;                              -- semua kolom, semua baris
SELECT nama, ipk FROM mahasiswa WHERE semester = 6;   -- dua kolom, hanya semester 6
SELECT * FROM mahasiswa ORDER BY ipk DESC;            -- IPK tertinggi lebih dulu

c. Ubah data (UPDATE)

UPDATE mahasiswa SET ipk = 4.00 WHERE id = 1;
SELECT id, nama, ipk FROM mahasiswa WHERE id = 1;     -- IPK Andi sekarang 4
UPDATE mahasiswa SET ipk = 3.75 WHERE id = 1;         -- kembalikan

d. Hapus data (DELETE)

Tambah satu baris percobaan, lalu hapus:

INSERT INTO mahasiswa (nim, nama) VALUES ('F1D021099', 'Sementara');
DELETE FROM mahasiswa WHERE nim = 'F1D021099';
SELECT id, nim, nama FROM mahasiswa;                  -- kembali tiga baris

nim dan nama saja yang diisi, jadi ipk dan semester terisi nilai bawaan (0 dan 1). Setelah dihapus, tabel kembali berisi tiga baris. Satu hal yang perlu diperhatikan: baris percobaan tadi mendapat id 4, dan nomor 4 tidak dipakai lagi. Mahasiswa berikutnya akan mendapat id 5. MySQL tidak mendaur ulang nomor yang sudah terpakai, jadi id boleh punya “lubang” dan itu normal.

Jangan lupa WHERE. UPDATE mahasiswa SET ipk = 4 tanpa WHERE mengubah IPK semua mahasiswa, dan DELETE FROM mahasiswa tanpa WHERE menghapus semua baris. Tidak ada tombol undo.
Checkpoint: database api_mahasiswa berisi tabel mahasiswa dengan struktur sesuai rencana dan tiga baris (Andi, Budi, Citra), dan kalian sudah mencoba keempat perintah CRUD. Tabel inilah yang akan dibaca oleh API di section berikutnya.

2. Menampilkan dan Menambah Data dari JavaScript (Tanpa ORM) Praktik

Tabel sudah ada dan terisi. Sekarang JavaScript harus bisa membacanya. Kita mulai dari proyek Node.js baru yang kecil, mysql-mahasiswa, supaya setiap hal baru (koneksi, file .env, SQL dari JavaScript) bisa dilihat sendiri tanpa terganggu kode API. Setelah semuanya jelas, tabel yang sama kita sambungkan ke api-mahasiswa di 2.6.

2.3 Menyambung ke MySQL dan Menampilkan Data

File kecil yang membuat koneksi, dipisah supaya bisa dipakai dari banyak file:

// db.js
import 'dotenv/config';
import mysql from 'mysql2/promise';

export const db = mysql.createPool(process.env.DATABASE_URL);

createPool membuat kolam koneksi: beberapa koneksi ke MySQL yang dipakai bergantian, jadi tidak perlu membuka koneksi baru setiap kali. Import dari mysql2/promise membuat semua fungsinya mengembalikan promise, sehingga bisa dipakai dengan await seperti di Pertemuan 3. Sekarang buktikan JavaScript bisa membaca tabel. Buat tes-koneksi.js:

// tes-koneksi.js
import { db } from './db.js';

const [baris] = await db.execute('SELECT * FROM mahasiswa');
console.log(baris);

await db.end();

Tiga baris dari phpMyAdmin kini menjadi array berisi tiga objek JavaScript. db.execute() menjalankan SQL dan mengembalikan dua hal (baris hasil, dan keterangan kolom), karena itu ditulis const [baris] = ... untuk mengambil yang pertama. Perhatikan juga ipk sudah berupa angka, dan createdAt berupa objek tanggal (nanti diubah menjadi teks saat dikirim sebagai JSON). await db.end() menutup kolam koneksi supaya program bisa selesai.

console.log('Semua mahasiswa:', semua);

Dua hal baru di sini. Pertama, SELECT id, nama, semester hanya mengambil kolom yang disebut, bukan semuanya. Kedua, bentuk lengkap db.execute(sql, [nilai, ...]): perintah SQL ditulis dengan tanda ? sebagai tempat nilai, dan nilainya diberikan terpisah di dalam array (di sini semester menggantikan ?). Mengapa nilai tidak ditulis langsung di dalam teks SQL dijelaskan di 2.5, dan itu penting.

2.4 Menambah Data

Perintah INSERT dari 1.4, kini dari JavaScript. Buat tambah.js:

// tambah.js
import { db } from './db.js';

const [hasil] = await db.execute(
    'INSERT INTO mahasiswa (nim, nama) VALUES (?, ?)',
    ['F1D021004', 'Dewi']
);
console.log('id baru        :', hasil.insertId);
console.log('baris tertambah:', hasil.affectedRows);

await db.end();
$ node tambah.js id baru : 5 baris tertambah: 1

Dua tanda ? diisi oleh isi array sesuai urutannya (nim, lalu nama). Hasil INSERT berupa keterangan, bukan baris: insertId adalah id yang diberikan MySQL untuk baris baru, dan affectedRows jumlah baris yang tertambah. Buka phpMyAdmin (tab Browse): Dewi ada di tabel dengan ipk 0 dan semester 1, nilai DEFAULT dari 1.3. id-nya 5, bukan 4, karena nomor 4 sudah terpakai oleh baris percobaan di 1.4.

Jangan jalankan tambah.js dua kali. Pada percobaan kedua MySQL menolak karena nim sudah ada (kita memasang UNIQUE di 1.3), dan nomor id berikutnya ikut melompat satu. Itu wajar, tetapi angka id di bagian selanjutnya akan berbeda dari contoh.
Checkpoint: JavaScript membaca tabel (tes-koneksi.js, tampil.js) dan menambah baris (tambah.js) yang langsung terlihat di phpMyAdmin. Tabel kini berisi empat mahasiswa, termasuk Dewi.

2.5 Bahaya Menggabungkan Input ke Teks SQL: SQL Injection

Di tampil.js dan tambah.js, nilai dikirim lewat tanda ?, bukan ditulis langsung ke dalam teks SQL. Itu bukan sekadar gaya. Kita buktikan dengan sqli-uji.js, berisi dua cara mencari mahasiswa berdasarkan nama. Cara pertama sengaja salah: nama digabung ke teks SQL, dan dijalankan dengan db.query (fungsi yang menjalankan teks SQL apa adanya). Cara kedua memakai db.execute dengan ?, seperti di tampil.js:

// sqli-uji.js
import { db } from './db.js';

async function cariRentan(nama) {
    // nama pengguna DIGABUNG ke dalam teks SQL
    const sql = `SELECT id, nim, nama, ipk FROM mahasiswa WHERE nama = '${nama}'`;
    console.log('SQL:', sql);
    try {
        const [baris] = await db.query(sql);
        console.log('Hasil:', JSON.stringify(baris));
    } catch (err) {
        console.log('Error:', err.code);
    }
    console.log();
}

async function cariAman(nama) {
    // nama pengguna dikirim TERPISAH lewat tanda ?
    const [baris] = await db.execute('SELECT id, nim, nama, ipk FROM mahasiswa WHERE nama = ?', [nama]);
    console.log('Hasil:', JSON.stringify(baris));
}

await cariRentan('Andi');
await cariRentan("' OR '1'='1");
await cariRentan("x'; DROP TABLE mahasiswa; #");
await cariAman("' OR '1'='1");

await db.end();

Pemanggilan pertama adalah pencarian biasa. Pemanggilan kedua dan ketiga adalah masukan penyerang. Jalankan:

$ node sqli-uji.js SQL: SELECT id, nim, nama, ipk FROM mahasiswa WHERE nama = 'Andi' Hasil: [{"id":1,"nim":"F1D021001","nama":"Andi","ipk":3.75}] SQL: SELECT id, nim, nama, ipk FROM mahasiswa WHERE nama = '' OR '1'='1' Hasil: [{"id":1,"nim":"F1D021001","nama":"Andi","ipk":3.75},{"id":2,"nim":"F1D021002","nama":"Budi","ipk":3.2},{"id":3,"nim":"F1D021003","nama":"Citra","ipk":3.9},{"id":5,"nim":"F1D021004","nama":"Dewi","ipk":0}] SQL: SELECT id, nim, nama, ipk FROM mahasiswa WHERE nama = 'x'; DROP TABLE mahasiswa; #' Error: ER_PARSE_ERROR Hasil: []

Serangan 1: input yang “bukan nama”

Penyerang mengetik ' OR '1'='1 di kolom pencarian. Semua mahasiswa keluar, padahal tidak ada yang bernama kosong. Penyebabnya: tanda kutip ' di awal input menutup string lebih awal, sehingga sisa input menjadi bagian dari perintah SQL. Syarat '1'='1' selalu benar, jadi WHERE meloloskan setiap baris. Penyerang tidak perlu menembus server atau password; cukup mengetik di kolom pencarian.

Serangan 2: menyisipkan perintah baru

Input x'; DROP TABLE mahasiswa; # mencoba menyelipkan perintah kedua (DROP TABLE menghapus tabel). Tanda # adalah komentar di MySQL, dipakai untuk membuang sisa kutip penutup. Pada percobaan di atas serangan ini gagal (ER_PARSE_ERROR) karena mysql2 secara bawaan menolak beberapa perintah dalam satu kiriman. Tetapi itu hanya pengaman bawaan: kalau koneksi dibuat dengan opsi multipleStatements: true (opsi ini ada, dan kadang diaktifkan demi kemudahan), perintah kedua dijalankan dan tabel benar-benar hilang. Kita tidak mengaktifkannya, tetapi kita juga tidak boleh bergantung pada itu.

Di MySQL, komentar gaya -- harus diikuti spasi (-- ), sedangkan # tidak. Karena itu contoh di atas memakai #.
Akar masalahnya: data (apa yang diketik pengguna) dan perintah (SQL) dicampur dalam satu teks, sehingga database tidak bisa membedakan keduanya. Kedua serangan di atas hanya menyebabkan masalah itu.

Perbaikan: pisahkan perintah dan data

Baris terakhir di percobaan tadi, cariAman, memberi hasil [] untuk input jahat yang sama. Perintah SQL ditulis dengan penanda ? dan nilainya dikirim terpisah. Dengan db.execute, MySQL menerima kerangka perintahnya dan nilainya secara terpisah, sehingga kutip di dalam nilai tidak pernah bisa menutup apa pun. Input jahat tadi hanya dianggap nama seseorang yang aneh; karena tidak ada mahasiswa dengan nama itu, hasilnya kosong.

Aturannya: jangan pernah menggabungkan input pengguna ke dalam teks SQL. Hapus sqli-uji.js setelah dicoba.

2.6 Sambungkan ke api-mahasiswa

Semua yang tadi dipelajari kini dipakai di API dari Pertemuan 5. Karena sudah dibagi empat lapis, yang diganti hanya lapis data (src/data/mahasiswa.data.js): array diganti perintah SQL. Controller, routes, middleware, dan validator tidak disentuh. Pindah ke folder api-mahasiswa (yang sejajar dengan mysql-mahasiswa) dan ulangi persiapannya (paket dari 2.1, .env dari 2.2, koneksi dari 2.3):

$ cd ../api-mahasiswa $ npm install mysql2 dotenv
  • .env: buat file baru di akar api-mahasiswa, isi sama persis dengan .env di mysql-mahasiswa.
  • .gitignore: buat file ini di akar api-mahasiswa kalau belum ada, isi dengan node_modules dan .env (seperti di 2.2).
  • src/lib/db.js: buat folder src/lib, lalu file db.js dengan isi yang sama seperti db.js di 2.3.

Buka src/data/mahasiswa.data.js. Isinya masih array dengan empat fungsi (enam kalau kalian sudah mengerjakan PUT dan DELETE dari Latihan 1 Pertemuan 5). Ganti seluruhnya dengan versi SQL; untuk sementara hanya tiga fungsi baca, simpan() menyusul sebentar lagi:

// src/data/mahasiswa.data.js
import { db } from '../lib/db.js';

export async function semua() {
    const [baris] = await db.execute('SELECT * FROM mahasiswa');
    return baris;
}

export async function cariById(id) {
    const [baris] = await db.execute('SELECT * FROM mahasiswa WHERE id = ?', [id]);
    return baris[0];
}

export async function cariByNim(nim) {
    const [baris] = await db.execute('SELECT * FROM mahasiswa WHERE nim = ?', [nim]);
    return baris[0];
}
  • baris[0] mengambil baris pertama, atau undefined kalau tidak ada. Persis perilaku array.find() di versi sebelumnya.
  • Nama dan bentuk fungsi sama dengan versi array. Hanya isinya yang berubah, dan kini semuanya async.

Satu hal harus disesuaikan di service: fungsi data kini mengembalikan promise, bukan nilai langsung. Tanpa await, service bekerja dengan promise, bukan dengan datanya. Tambahkan tiga await:

// src/services/mahasiswa.service.js
import * as data from '../data/mahasiswa.data.js';
import { AppError } from '../utils/AppError.js';

export async function daftarMahasiswa({ semester }) {
    const semua = await data.semua();                          // ← await
    return semester
        ? semua.filter(m => m.semester === Number(semester))
        : semua;
}

export async function detailMahasiswa(id) {
    const m = await data.cariById(Number(id));                 // ← await
    if (!m) {
        throw new AppError(404, 'Mahasiswa tidak ditemukan', 'NOT_FOUND');
    }
    return m;
}

export async function buatMahasiswa(input) {
    if (await data.cariByNim(input.nim)) {                     // ← await
        throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
    }
    return data.simpan(input);
}

Kalau satu await terlewat, error-nya licin: semua.filter gagal karena promise tidak punya filter (GET /mahasiswa?semester=4 menjawab 500 dengan TypeError: semua.filter is not a function di terminal), dan if (data.cariByNim(...)) selalu benar karena promise adalah objek, sehingga setiap POST dianggap NIM kembar.

Kalau api-mahasiswa kalian sudah punya PUT dan DELETE (Latihan 1 Pertemuan 5): fungsi ubah() dan hapus() ikut hilang bersama array, jadi untuk sementara PUT menjawab 409 yang keliru (pemeriksaan NIM di ubahMahasiswa belum memakai await) dan DELETE menjawab 500 (data.hapus is not a function). 3. Masuk ke ORM: Prisma Indikator 4.1

Di Section 2, setiap operasi data adalah sepotong teks SQL. ORM (Object-Relational Mapper) menggantinya dengan pemanggilan fungsi JavaScript biasa, lalu menerjemahkannya menjadi SQL untuk kita.

3.7 Bagaimana dengan SQL Injection?

Prisma selalu mengirim nilai sebagai parameter, tanpa pernah menggabungkannya ke teks SQL, jadi kita tidak perlu ingat untuk memakai ?. Input jahat dari 2.5 diperlakukan sebagai data:

// AMAN: Prisma selalu mengirim nilai sebagai parameter
const hasil = await prisma.mahasiswa.findMany({ where: { nama: "' OR '1'='1" } });
// hasil: []   (tidak ada mahasiswa bernama aneh itu)
CaraInput ' OR '1'='1 dianggap...Hasil
SQL mentah, digabung stringperintah SQLsemua baris bocor
SQL mentah, berparameter (?)data (sebuah nama)kosong
Prisma findMany({ where })data (sebuah nama)kosong
ORM bukan jaminan otomatis. Prisma menyediakan jalur SQL mentah, dan pemakaiannya bisa membuka lubang yang sama kembali: 
// RENTAN lagi: $queryRawUnsafe + template string = SQL mentah yang digabung
await prisma.$queryRawUnsafe(`SELECT * FROM mahasiswa WHERE nama = '${nama}'`);

// AMAN: $queryRaw dengan tagged template, ${nama} otomatis menjadi parameter

Dengan input ' OR '1'='1, versi $queryRawUnsafe mengembalikan semua baris tabel, sedangkan $queryRaw dan findMany mengembalikan kosong. Aturannya sama seperti di 2.5: jangan pernah menggabungkan input pengguna ke dalam string SQL, di ORM mana pun. Validasi masukan seperti di Pertemuan 5 tetap dipakai sebagai lapisan tambahan, bukan pengganti.

4.2 Lapis Service, Controller, dan Routes

Di src/services/mahasiswa.service.js, tambahkan dua fungsi di akhir (atau ganti ubahMahasiswa dan hapusMahasiswa yang sudah ada dari Latihan 1):

export async function ubahMahasiswa(id, input) {
    const lama = await detailMahasiswa(id);                    // 400 / 404 bila id keliru atau tidak ada

    const bentrok = await data.cariByNim(input.nim);
    if (bentrok && bentrok.id !== lama.id) {                   // NIM dipakai mahasiswa LAIN
        throw new AppError(409, `NIM ${input.nim} sudah dipakai mahasiswa lain`, 'NIM_DUPLIKAT');
    }

    return data.ubah(lama.id, input);
}

export async function hapusMahasiswa(id) {
    const m = await detailMahasiswa(id);
    await data.hapus(m.id);
}
  • detailMahasiswa() dipakai ulang, jadi urusan id yang bukan angka (400) dan id yang tidak ada (404) cukup ditulis satu kali.
  • bentrok.id !== lama.id: mahasiswa boleh mengirim ulang NIM-nya sendiri. Yang ditolak hanya NIM milik orang lain.
  • Alternatifnya, langsung memanggil update atau delete dan menangkap error P2025 (“baris tidak ditemukan”) yang dilempar Prisma. Pemeriksaan di muka memberi pesan yang lebih rapi dan kendali penuh atas kode statusnya.

4.4 Tiga Lapis Penjaga Data

Joi sudah memeriksa bentuk data sejak Pertemuan 5, Section 4 dan tetap berlaku setelah memakai database. Database menambah satu lapis pengaman lagi. Ketiganya punya tugas berbeda:

Mengapa database tetap perlu menjaga?

Service sudah memeriksa NIM kembar sebelum menyimpan. Tetapi bayangkan dua permintaan dengan NIM yang sama tiba bersamaan: keduanya memeriksa, keduanya belum menemukan NIM itu, lalu keduanya menyimpan. Yang menyelamatkan data adalah UNIQUE di tabel (yang kita tulis sendiri di 1.3): penyimpanan kedua ditolak. Kita tiru situasinya dengan melewati pemeriksaan service. Di buatMahasiswa, ubah sementara barisnya menjadi if (false && await data.cariByNim(input.nim)) {, lalu kirim POST dengan NIM yang sudah ada (misalnya F1D021001):

$ curl -X POST http://localhost:3000/mahasiswa -H "Content-Type: application/json" -H "x-api-key: rahasia123" -d '{"nim":"F1D021001","nama":"Kembar"}' {"error":{"pesan":"Terjadi kesalahan pada server","kode":"INTERNAL_ERROR"}}

Data memang selamat, tetapi klien menerima 500. Di terminal server terlihat penyebabnya:

PrismaClientKnownRequestError: ... code: 'P2002',

P2002 adalah kode Prisma untuk pelanggaran UNIQUE. Ini kesalahan klien (409), bukan kesalahan server (500). Tangkap dan terjemahkan di service, sehingga buatMahasiswa menjadi:

export async function buatMahasiswa(input) {
    if (await data.cariByNim(input.nim)) {
        throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
    }

    try {
        return await data.simpan(input);
    } catch (err) {
        if (err.code === 'P2002') {   // kode Prisma untuk pelanggaran UNIQUE
            throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
        }
        throw err;   // error lain diteruskan ke errorHandler (Pertemuan 5)
    }
}

Kirim ulang POST yang sama (pemeriksaan false && masih aktif): kini jawabannya 409 NIM_DUPLIKAT. Kembalikan barisnya menjadi if (await data.cariByNim(input.nim)) { setelah selesai mencoba. Prisma juga menolak tipe data yang salah, misalnya teks untuk kolom Float: Argument `ipk`: Invalid value provided. Expected Float, provided String. Karena Joi sudah menyaringnya lebih awal, error ini hampir tidak pernah sampai ke Prisma.

Pembagian tanggung jawab: Joi memberi pesan yang ramah dan lengkap sebelum permintaan menyentuh database. Constraint database (UNIQUE, NOT NULL) adalah jaring pengaman terakhir, bukan satu-satunya validasi.

5. Skema dan Migrasi Indikator 4.2

Tabel mahasiswa kita buat dengan tangan di phpMyAdmin. Selama tabelnya tidak pernah berubah, tidak ada masalah. Tetapi kebutuhan berubah: sekarang mahasiswa perlu punya email. Kalau kolom itu ditambahkan dengan klik-klik di phpMyAdmin, apa yang terjadi pada teman satu tim, pada komputer kalian yang lain, atau pada server tempat aplikasi nanti dipasang? Mereka tidak tahu ada kolom baru, dan tidak ada catatan yang bisa mereka jalankan.

Migrasi menjawab hal ini: setiap perubahan struktur tabel ditulis sebagai file SQL yang bernomor urut waktu dan disimpan di proyek. Menjalankan semua migrasi berurutan menghasilkan struktur tabel yang persis sama di komputer mana pun.

Sekarang kebutuhan email tadi. Alurnya selalu sama: edit skema, buat migrasi baru. Tambahkan satu baris di model Mahasiswa pada prisma/schema.prisma, tepat di bawah createdAt:

6. Relasi dan Normalisasi Indikator 4.3

Sampai sekarang kita hanya punya satu tabel. Aplikasi sungguhan hampir selalu punya beberapa tabel yang saling berhubungan. Bagian ini membahas cara memodelkan hubungan itu di Prisma dan kenapa tabel perlu dipecah. Contoh di sini untuk dipahami dan diskemakan dulu; Pertemuan 7 membangun relasi banyak-ke-banyak sungguhan.

6.1 Relasi Satu-ke-Banyak (1–N)

Satu mahasiswa punya banyak nilai. Satu nilai hanya milik satu mahasiswa.

model Mahasiswa {
  id     Int     @id @default(autoincrement())
  nim    String  @unique
  nama   String
  nilai  Nilai[]              // sisi "banyak" — array
}

model Nilai {
  id          Int       @id @default(autoincrement())
  mataKuliah  String
  skor        Float
  mahasiswa   Mahasiswa @relation(fields: [mahasiswaId], references: [id])
  mahasiswaId Int                                          // foreign key
}

Dua baris kuncinya: mahasiswaId Int adalah kolom foreign key yang benar-benar ada di tabel Nilai, dan @relation(fields: [mahasiswaId], references: [id]) menyatakan “kolom itu menunjuk ke id di Mahasiswa”. Baris nilai Nilai[] di sisi lain hanya penanda, tidak membuat kolom.

// Mengambil mahasiswa BESERTA seluruh nilainya
const mhs = await prisma.mahasiswa.findUnique({
    where: { id: 1 },
    include: { nilai: true }         // padanan Eloquent: ->load('nilai')
});
// { id: 1, nim: "...", nama: "...", nilai: [{ id:1, mataKuliah:"PWL", skor:88 }, ...] }

6.2 Relasi Banyak-ke-Banyak (N–N)

Satu mahasiswa mengikuti banyak kelas. Satu kelas diikuti banyak mahasiswa. Butuh tabel penghubung di antara keduanya.

Prisma membuat tabel penghubung _KelasToMahasiswa secara otomatis (relasi implisit), atau kalian bisa mendefinisikan sendiri (relasi eksplisit) kalau tabel penghubung butuh kolom tambahan — misalnya tanggal pendaftaran.

// Relasi EKSPLISIT — dipakai kalau tabel penghubung butuh field tambahan
model Mahasiswa {
  id          Int           @id @default(autoincrement())
  nama        String
  pendaftaran Pendaftaran[]
}

model Kelas {
  id          Int           @id @default(autoincrement())
  nama        String
  pendaftaran Pendaftaran[]
}

// Tabel penghubung — punya field TAMBAHAN: tanggalDaftar
model Pendaftaran {
  id            Int       @id @default(autoincrement())
  mahasiswa     Mahasiswa @relation(fields: [mahasiswaId], references: [id])
  mahasiswaId   Int
  kelas         Kelas     @relation(fields: [kelasId], references: [id])
  kelasId       Int
  tanggalDaftar DateTime  @default(now())

  @@unique([mahasiswaId, kelasId])   // satu mahasiswa tak bisa daftar 2x di kelas sama
}
Kapan pakai relasi implisit vs eksplisit? Implisit (Kelas[] langsung di kedua sisi) cukup kalau tabel penghubung hanya berisi dua foreign key. Begitu butuh field tambahan (tanggal daftar, status, nilai akhir) — wajib eksplisit seperti contoh di atas. Pertemuan 7 memakai pola eksplisit ini untuk pendaftaran mahasiswa ke kelas.

6.3 Normalisasi: Mengapa Tabel Harus Dipecah

Dua bagian sebelumnya menunjukkan cara menulis relasi di Prisma. Sekarang pertanyaan yang lebih mendasar: bagaimana kita tahu sebuah tabel perlu dipecah? Jawabannya adalah normalisasi — serangkaian aturan untuk menata tabel agar tidak ada data yang tersimpan berulang.

Mulai dari tabel mentah seperti yang biasa kalian temui di spreadsheet:

namaprodinama_dosen_walimata_kuliah
DimasInformatikaBudi SantosoPWL, Basis Data, Mobile
SariInformatikaBudi SantosoPWL
GilangElektroRina WijayaBasis Data

Tabel ini terlihat wajar, sampai kalian diminta mengganti nama mata kuliah “PWL” menjadi “Pemrograman Web Lanjut”. Nilainya ada di dua baris, dan pada baris pertama ia terjepit di antara koma. Kueri untuk mengubahnya menjadi rumit, dan setiap kali ada penambahan baris, masalahnya bertambah. Inilah yang disebut redundansi.

1NF — satu sel, satu nilai

Aturan pertama: tidak boleh ada kolom yang menampung lebih dari satu nilai. Kolom mata_kuliah yang berisi “PWL, Basis Data, Mobile” melanggar aturan ini, sehingga barisnya dipecah — Dimas menjadi tiga baris, masing-masing satu mata kuliah.

2NF — setiap entitas punya kunci sendiri

Aturan kedua: penuhi 1NF, lalu pastikan setiap kolom bergantung penuh pada satu primary key. Di tabel kita jelas ada dua hal berbeda yang tercampur: mahasiswa dan mata kuliah. Keduanya dipisah menjadi tabel sendiri-sendiri, masing-masing dengan id. Karena hubungan keduanya banyak-ke-banyak, muncul tabel ketiga sebagai penghubung — persis tabel Pendaftaran pada bagian 6.2.

3NF — buang ketergantungan berantai

Aturan ketiga: penuhi 2NF, lalu buang kolom yang bergantung pada kolom non-kunci lain. Lihat nama_dosen_wali: ia sebenarnya tidak bergantung pada mahasiswa, melainkan pada prodi — prodi menentukan dosen wali. Rantai seperti ini (mahasiswa → prodi → dosen_wali) yang harus diputus, dengan memindahkan nama_dosen_wali ke tabel Prodi.

BentukAturanGejala kalau dilanggar
1NFSatu sel hanya boleh berisi satu nilaiAda kolom berisi daftar dipisah koma
2NF1NF + setiap kolom bergantung penuh pada primary keyDua entitas berbeda tercampur di satu tabel
3NF2NF + tidak ada ketergantungan berantaiMengubah satu nilai memaksa mengubah banyak baris
3NF sudah cukup untuk mata kuliah ini. Masih ada BCNF, 4NF, dan seterusnya, tetapi untuk aplikasi berskala tugas dan proyek akhir, skema yang memenuhi 3NF sudah bebas dari masalah redundansi yang praktis. Yang penting kalian bisa menunjukkan di laporan mengapa sebuah tabel dipecah.
Prisma tidak menormalkan skema untuk kalian. ORM hanya menerjemahkan skema yang kalian tulis. Kalau schema.prisma berisi satu model raksasa dengan kolom mataKuliah String berisi daftar dipisah koma, Prisma akan membuat tabel itu apa adanya. Normalisasi adalah keputusan perancangan yang tetap ada di tangan kalian.

7. Latihan Mandiri Latihan

Selesai kalau: api-mahasiswa tersambung ke MySQL lewat Prisma dengan CRUD lengkap (GET daftar, GET detail, POST, PUT, DELETE); data bertahan setelah restart dan terlihat di phpMyAdmin; folder prisma/migrations berisi migrasi tabel dan kolom email; dan requests.http memuat kasus berhasil serta gagal untuk setiap endpoint.

Latihan

  1. Email lewat API. Kolom email sudah ada di database, tetapi API belum menerimanya. Tambahkan field email (opsional, harus berbentuk email) ke skema Joi, lalu buktikan POST dan PUT bisa menyimpannya dan GET menampilkannya. Tambahkan permintaan ujinya, termasuk email yang tidak valid, ke requests.http.
  2. Kolom baru lewat migrasi. Tambahkan kolom angkatan (bilangan bulat, boleh kosong) lewat jalur yang benar: edit skema, migrate dev, generate. Buka file migration.sql yang dihasilkan dan jelaskan satu baris SQL di dalamnya.
  3. Model relasi. Tambahkan model Nilai dengan relasi satu-ke-banyak ke Mahasiswa (Section 6.1), lalu jalankan migrasi baru.
  4. Mahasiswa beserta nilai. Tambahkan endpoint GET /mahasiswa/:id/nilai yang mengembalikan mahasiswa beserta seluruh nilainya (pakai include). Isi beberapa nilai lewat phpMyAdmin untuk mengujinya.
  5. Normalisasi. Seorang teman membuat tabel krs dengan kolom nim, nama_mahasiswa, kode_mk, nama_mk, sks, nama_dosen. Tunjukkan bagian mana yang melanggar 1NF, 2NF, atau 3NF, lalu gambarkan tabel hasil pemecahannya.
Menuju Pertemuan 7: pertemuan berikutnya melanjutkan api-mahasiswa dari titik ini. Ia mengharapkan tabel mahasiswa berisi tepat tiga baris (Andi, Budi, Citra dengan id 1 sampai 3), lalu menambah relasi banyak-ke-banyak sungguhan (pendaftaran mahasiswa ke kelas), kueri lanjutan (paginasi, filter, urut), dan transaksi. Kalau ada baris tambahan dari percobaan kalian, bersihkan dulu di phpMyAdmin (tab SQL): 
TRUNCATE TABLE mahasiswa;
INSERT INTO mahasiswa (nim, nama, ipk, semester) VALUES
('F1D021001', 'Andi',  3.75, 6),
('F1D021002', 'Budi',  3.20, 6),
('F1D021003', 'Citra', 3.90, 4);
TRUNCATE mengosongkan tabel dan mengembalikan penomoran id ke 1, hal yang tidak dilakukan DELETE (ingat “lubang” di 1.4).
Kalau kalian mengerjakan Latihan 3 (tabel Nilai): MySQL menolak TRUNCATE dengan error Cannot truncate a table referenced in a foreign key constraint, karena tabel mahasiswa kini dirujuk tabel lain. Pakai cara ini sebagai gantinya (kosongkan tabel anak lebih dulu, lalu hapus baris selebihnya dan atur ulang penomoran): 
DELETE FROM Nilai;
DELETE FROM mahasiswa WHERE id > 3;
ALTER TABLE mahasiswa AUTO_INCREMENT = 4;
