1. ORM dan Padanannya dengan Eloquent Pengantar

Sejak Pertemuan 4, data mahasiswa masih berupa array biasa yang hilang setiap kali server di-restart. Sekarang saatnya menyambungkan API ke MySQL yang sudah kalian siapkan di Pertemuan 1, lewat sebuah ORM (Object-Relational Mapper).

ORM itu apa? Jembatan antara objek JavaScript dan baris tabel SQL. Alih-alih menulis SELECT * FROM mahasiswa WHERE id = 1, kalian menulis prisma.mahasiswa.findUnique({ where: { id: 1 } }) — persis seperti Eloquent menggantikan query SQL mentah di Laravel.

Perbedaan filosofis penting: Eloquent bersifat active record — model class-nya sendiri tahu cara query dirinya. Prisma bersifat lebih terpisah: skema hanya mendefinisikan bentuk data, sedangkan Prisma Client (yang di-generate otomatis dari skema) adalah objek terpisah yang dipakai untuk semua query. Tidak ada "class Mahasiswa extends Model" — hanya prisma.mahasiswa.

Contoh: Apa Itu SQL Injection?

Baris pertama di tabel itu perlu dilihat langsung supaya terasa. SQL injection adalah serangan ketika input dari pengguna ikut dibaca sebagai perintah SQL, bukan sebagai data. Kita buktikan dengan data yang sama seperti di Pertemuan 4: tabel mahasiswa berisi Andi, Budi, dan Citra.

Skenario: fitur pencarian tanpa ORM

Misalkan kita menambah endpoint pencarian ke api-mahasiswa, ditulis dengan SQL mentah yang menggabungkan input ke dalam teks query:

// ❌ RENTAN: input pengguna digabung langsung ke teks SQL
app.get('/mahasiswa/cari', async (req, res) => {
    const { nama } = req.query;
    const hasil = await db.query(`SELECT * FROM mahasiswa WHERE nama = '${nama}'`);
    res.json({ data: hasil.rows });
});

Pencarian biasa bekerja seperti yang diharapkan. Untuk GET /mahasiswa/cari?nama=Andi, SQL yang terbentuk dan hasilnya:

SQL yang dijalankan: SELECT * FROM mahasiswa WHERE nama = 'Andi' Hasil: [{"id":1,"nim":"F1D021001","nama":"Andi","ipk":3.75}]

Serangan: input yang “bukan nama”

Sekarang penyerang tidak mengetik nama, melainkan ' OR '1'='1 di kolom pencarian:

SQL yang dijalankan: SELECT * FROM mahasiswa WHERE nama = '' OR '1'='1' Hasil: [{"id":1,"nim":"F1D021001","nama":"Andi","ipk":3.75}, {"id":2,"nim":"F1D021002","nama":"Budi","ipk":3.2}, {"id":3,"nim":"F1D021003","nama":"Citra","ipk":3.9}]

Semua mahasiswa keluar, padahal tidak ada yang bernama “” (kosong). Penyebabnya: tanda kutip ' di awal input menutup string lebih awal, sehingga sisa input menjadi bagian dari perintah SQL. Syarat '1'='1' selalu benar, jadi WHERE meloloskan setiap baris. Penyerang tidak perlu menembus server atau password; cukup mengetik di kolom pencarian.

Yang lebih merusak: kalau driver mengizinkan beberapa perintah sekaligus (beberapa driver atau pengaturan mengizinkannya, misalnya PostgreSQL pg pada query biasa atau MySQL dengan opsi multipleStatements), input x'; DROP TABLE mahasiswa; -- menyisipkan perintah baru:

SQL yang dijalankan: SELECT * FROM mahasiswa WHERE nama = 'x'; DROP TABLE mahasiswa; --' Setelah itu, SELECT * FROM mahasiswa: no such table: mahasiswa

Tabel hilang. Tanda -- adalah komentar SQL, dipakai untuk membuang sisa kutip penutup yang tidak diperlukan.

Akar masalahnya: data (apa yang diketik pengguna) dan perintah (SQL) dicampur dalam satu teks, sehingga database tidak bisa membedakan keduanya. Semua serangan di atas hanya menyebabkan masalah itu.

Perbaikan: pisahkan perintah dan data

Solusinya query berparameter. Perintah SQL ditulis dengan penanda (? di MySQL, $1 di PostgreSQL), nilainya dikirim terpisah:

// ✅ AMAN: perintah SQL dan nilainya dikirim terpisah
const hasil = await db.query('SELECT * FROM mahasiswa WHERE nama = ?', [nama]);
SQL yang dijalankan: SELECT * FROM mahasiswa WHERE nama = ? parameter: "' OR '1'='1" Hasil: []

Input jahat yang sama kini hanya dianggap nama seseorang yang aneh. Karena tidak ada mahasiswa dengan nama itu, hasilnya kosong. Tanda kutip di dalamnya tidak lagi bisa menutup apa pun.

Catatan: keluaran pada bagian ini berasal dari database SQLite di memori, yang menandai parameter dengan ?, sama seperti MySQL. PostgreSQL memakai $1, $2, dst.; perilakunya sama.

Di mana ORM berperan?

Prisma selalu memakai cara kedua: nilai yang kita berikan di where dikirim ke database sebagai parameter, tanpa pernah digabung ke teks SQL. Kita tidak perlu ingat melakukannya, jadi tidak bisa lupa:

// ✅ AMAN: Prisma selalu mengirim nilai sebagai parameter
const hasil = await prisma.mahasiswa.findMany({ where: { nama } });
CaraInput ' OR '1'='1 dianggap...Hasil
SQL mentah, digabung stringperintah SQLsemua baris bocor
SQL mentah, berparameterdata (sebuah nama)kosong
Prisma findMany({ where })data (sebuah nama)kosong
ORM bukan jaminan otomatis. Prisma menyediakan jalur SQL mentah, dan pemakaiannya bisa membuat lubang yang sama kembali: 
// ❌ RENTAN lagi: $queryRawUnsafe + template string = SQL mentah yang digabung
await prisma.$queryRawUnsafe(`SELECT * FROM "Mahasiswa" WHERE nama = '${nama}'`);

// ✅ AMAN: $queryRaw dengan tagged template, ${nama} otomatis menjadi parameter
await prisma.$queryRaw`SELECT * FROM "Mahasiswa" WHERE nama = ${nama}`;
Aturannya: jangan pernah menggabungkan input pengguna ke dalam string SQL, di ORM mana pun. Validasi masukan seperti di Pertemuan 5 tetap dipakai sebagai lapisan tambahan, bukan pengganti.

Satu perintah mengubah skema tadi menjadi tabel sungguhan di MySQL:

Angka di depan nama folder adalah waktu migrasi dibuat, jadi milik kalian akan berbeda. Prisma membuat file prisma/migrations/.../migration.sql lalu langsung menjalankannya. Isinya SQL biasa, silakan dibaca:

-- CreateTable
CREATE TABLE `mahasiswa` (
    `id` INTEGER NOT NULL AUTO_INCREMENT,
    `nim` VARCHAR(191) NOT NULL,
    `nama` VARCHAR(191) NOT NULL,
    `ipk` DOUBLE NOT NULL DEFAULT 0,
    `semester` INTEGER NOT NULL DEFAULT 1,
    `createdAt` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    UNIQUE INDEX `mahasiswa_nim_key`(`nim`),
    PRIMARY KEY (`id`)
) DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

Kenapa Pakai Migrasi? (Dan Apakah Wajib?)

Tidak wajib. Tabel tadi bisa saja dibuat langsung di phpMyAdmin dengan klik-klik. Migrasi dipilih karena beberapa kelebihan, yang terasa ketika proyek mulai dikerjakan lebih dari satu orang atau berumur lebih dari satu minggu:

 Dengan migrasiTabel dibuat manual di phpMyAdmin

Teman satu tim / komputer lainCukup npx prisma migrate dev, strukturnya persis samaMengulang klik-klik, mudah beda satu kolom
Menambah kolom nantiEdit skema, buat migrasi tambahanUbah di phpMyAdmin, lalu harus ingat dan menyamakan skema

Kalau memilih membuat tabel manual: buat tabelnya di phpMyAdmin, lalu minta Prisma membaca tabel itu dan menuliskan skemanya sendiri (arah kebalikan dari migrasi):
$ npx prisma db pull Introspected 1 model and wrote it into prisma/schema.prisma $ npx prisma generate
Skema hasil db pull berisi model mahasiswa dengan tipe sesuai tabel kalian. Setelah itu kode di 2.7 bisa dipakai apa adanya. Pilih satu jalur per proyek: kalau sudah memakai migrasi, jangan ubah struktur tabel lewat phpMyAdmin, karena skema dan database jadi berbeda dan Prisma akan meminta database di-reset. Materi ini memakai jalur migrasi.

2.7 Praktik: Menampilkan Data dari Database

Saatnya JavaScript membaca tabel itu. Pertama, minta Prisma membuat client, yaitu kode yang tahu bentuk tabel kita (hasilnya masuk folder generated/). Ulangi perintah ini setiap kali skema berubah:

$ npx prisma generate ✔ Generated Prisma Client (7.10.1) to ./generated/prisma in 12ms

Kedua, file kecil yang membuat koneksi. Dipisah supaya bisa dipakai dari banyak file nanti:

// src/prisma.js
import 'dotenv/config';
import { PrismaMariaDb } from '@prisma/adapter-mariadb';
import { PrismaClient } from '../generated/prisma/client.ts';

const adapter = new PrismaMariaDb(process.env.DATABASE_URL);

export const prisma = new PrismaClient({ adapter });

Ketiga, server dengan satu endpoint. prisma.mahasiswa.findMany() artinya “ambil semua baris tabel mahasiswa” (SQL: SELECT * FROM mahasiswa; Eloquent: Mahasiswa::all()). Karena membaca database butuh waktu, dipakai await seperti di Pertemuan 3.

// index.js
import express from 'express';
import { prisma } from './src/prisma.js';

const app = express();

app.get('/mahasiswa', async (req, res) => {
    const data = await prisma.mahasiswa.findMany();
    res.json({ data });
});

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, () => console.log(`Server jalan di http://localhost:${PORT}`));

Jalankan server, lalu uji di Postman: GET http://localhost:3000/mahasiswa.

2.8 Mengubah Skema: Menambah Kolom

Kebutuhan berubah: mahasiswa perlu punya email. Alurnya selalu sama: edit skema, buat migrasi baru. Tambahkan satu baris di model Mahasiswa:

  email     String?

Tanda ? berarti kolom boleh kosong. Ini perlu karena tabel sudah berisi tiga baris yang belum punya email; kolom wajib tanpa nilai bawaan tidak bisa ditambahkan ke tabel yang sudah berisi data.

$ npx prisma migrate dev --name tambah_kolom_email Applying migration `20261028223801_tambah_kolom_email` The following migration(s) have been created and applied from new schema changes: prisma/migrations/ └─ 20261028223801_tambah_kolom_email/ └─ migration.sql Your database is now in sync with your schema. $ npx prisma generate

Prisma membuat migrasi tambahan, bukan menimpa yang lama. Isinya hanya perubahan yang diperlukan:

-- AlterTable
ALTER TABLE `mahasiswa` ADD COLUMN `email` VARCHAR(191) NULL;

Cek di phpMyAdmin: tabel mahasiswa kini punya kolom email (kosong), dan request Postman tadi sekarang ikut menampilkan "email": null.

Selama memakai migrasi, ubah struktur lewat skema, bukan lewat phpMyAdmin. Kalau kolom ditambah manual di phpMyAdmin, skema dan database menjadi berbeda, dan Prisma baru memberi tahu belakangan dengan pesan yang membingungkan. Folder prisma/migrations wajib di-commit ke Git, sama seperti package-lock.json. Untuk melihat data tanpa phpMyAdmin tersedia juga npx prisma studio.

3.1 Relasi Satu-ke-Banyak (1–N)

Satu mahasiswa punya banyak nilai. Satu nilai hanya milik satu mahasiswa.

model Mahasiswa {
  id     Int     @id @default(autoincrement())
  nim    String  @unique
  nama   String
  nilai  Nilai[]              // sisi "banyak" — array
}

model Nilai {
  id          Int       @id @default(autoincrement())
  mataKuliah  String
  skor        Float
  mahasiswa   Mahasiswa @relation(fields: [mahasiswaId], references: [id])
  mahasiswaId Int                                          // foreign key
}
// Mengambil mahasiswa BESERTA seluruh nilainya
const mhs = await prisma.mahasiswa.findUnique({
    where: { id: 1 },
    include: { nilai: true }         // padanan Eloquent: ->load('nilai')
});
// { id: 1, nim: "...", nama: "...", nilai: [{ id:1, mataKuliah:"PWL", skor:88 }, ...] }

3.2 Relasi Banyak-ke-Banyak (N–N)

Satu mahasiswa mengikuti banyak kelas. Satu kelas diikuti banyak mahasiswa. Butuh tabel penghubung di antara keduanya.

N

Prisma membuat tabel penghubung _KelasToMahasiswa secara otomatis (relasi implisit), atau kalian bisa mendefinisikan sendiri (relasi eksplisit) kalau tabel penghubung butuh kolom tambahan — misalnya tanggal pendaftaran.

// Relasi EKSPLISIT — dipakai kalau tabel penghubung butuh field tambahan
model Mahasiswa {
  id         Int          @id @default(autoincrement())
  nama       String
  pendaftaran Pendaftaran[]
}

model Kelas {
  id          Int           @id @default(autoincrement())
  nama        String
  pendaftaran Pendaftaran[]
}

// Tabel penghubung — punya field TAMBAHAN: tanggalDaftar
model Pendaftaran {
  id            Int       @id @default(autoincrement())
  mahasiswa     Mahasiswa @relation(fields: [mahasiswaId], references: [id])
  mahasiswaId   Int
  kelas         Kelas     @relation(fields: [kelasId], references: [id])
  kelasId       Int
  tanggalDaftar DateTime  @default(now())

  @@unique([mahasiswaId, kelasId])   // satu mahasiswa tak bisa daftar 2x di kelas sama
}
Kapan pakai relasi implisit vs eksplisit? Implisit (Kelas[] langsung di kedua sisi) cukup kalau tabel penghubung hanya berisi dua foreign key. Begitu butuh field tambahan (tanggal daftar, status, nilai akhir) — wajib eksplisit seperti contoh di atas.

3.3 Normalisasi: Mengapa Tabel Harus Dipecah

Dua bagian sebelumnya menunjukkan cara menulis relasi di Prisma. Sekarang pertanyaan yang lebih mendasar: bagaimana kita tahu sebuah tabel perlu dipecah? Jawabannya adalah normalisasi — serangkaian aturan untuk menata tabel agar tidak ada data yang tersimpan berulang.

Mulai dari tabel mentah seperti yang biasa kalian temui di spreadsheet:

namaprodinama_dosen_walimata_kuliah
DimasInformatikaBudi SantosoPWL, Basis Data, Mobile
SariInformatikaBudi SantosoPWL
GilangElektroRina WijayaBasis Data

Tabel ini terlihat wajar, sampai kalian diminta mengganti nama mata kuliah “PWL” menjadi “Pemrograman Web Lanjut”. Nilainya ada di dua baris, dan pada baris pertama ia terjepit di antara koma. Kueri untuk mengubahnya menjadi rumit, dan setiap kali ada penambahan baris, masalahnya bertambah. Inilah yang disebut redundansi.

1NF — satu sel, satu nilai

Aturan pertama: tidak boleh ada kolom yang menampung lebih dari satu nilai. Kolom mata_kuliah yang berisi “PWL, Basis Data, Mobile” melanggar aturan ini, sehingga barisnya dipecah — Dimas menjadi tiga baris, masing-masing satu mata kuliah.

2NF — setiap entitas punya kunci sendiri

Aturan kedua: penuhi 1NF, lalu pastikan setiap kolom bergantung penuh pada satu primary key. Di tabel kita jelas ada dua hal berbeda yang tercampur: mahasiswa dan mata kuliah. Keduanya dipisah menjadi tabel sendiri-sendiri, masing-masing dengan id. Karena hubungan keduanya banyak-ke-banyak, muncul tabel ketiga sebagai penghubung — persis tabel KRS pada bagian 3.2.

3NF — buang ketergantungan berantai

Aturan ketiga: penuhi 2NF, lalu buang kolom yang bergantung pada kolom non-kunci lain. Lihat nama_dosen_wali: ia sebenarnya tidak bergantung pada mahasiswa, melainkan pada prodi — prodi menentukan dosen wali. Rantai seperti ini (mahasiswa → prodi → dosen_wali) yang harus diputus, dengan memindahkan nama_dosen_wali ke tabel Prodi.

BentukAturanGejala kalau dilanggar
1NFSatu sel hanya boleh berisi satu nilaiAda kolom berisi daftar dipisah koma
2NF1NF + setiap kolom bergantung penuh pada primary keyDua entitas berbeda tercampur di satu tabel
3NF2NF + tidak ada ketergantungan berantaiMengubah satu nilai memaksa mengubah banyak baris
3NF sudah cukup untuk mata kuliah ini. Masih ada BCNF, 4NF, dan seterusnya, tetapi untuk aplikasi berskala tugas dan proyek akhir, skema yang memenuhi 3NF sudah bebas dari masalah redundansi yang praktis. Yang penting kalian bisa menunjukkan di laporan mengapa sebuah tabel dipecah.
Prisma tidak menormalkan skema untuk kalian. ORM hanya menerjemahkan skema yang kalian tulis. Kalau schema.prisma berisi satu model raksasa dengan kolom mataKuliah String berisi daftar dipisah koma, Prisma akan membuat tabel itu apa adanya. Normalisasi adalah keputusan perancangan yang tetap ada di tangan kalian.
Latihan pada Pertemuan 7 memakai pola eksplisit ini.

4. Validasi Masukan Sebelum Disimpan Indikator 4.4

Validasi bentuk data (NIM 9 karakter, IPK 0–4, nama wajib ada) sudah dikerjakan oleh Joi di Pertemuan 5, Section 4 dan tetap berlaku setelah memakai database. Database menambah satu lapis pengaman lagi. Ketiganya punya tugas berbeda:

LapisMemeriksaContohHasil bila gagal
Joi (middleware)Bentuk dataNIM bukan 9 karakter, IPK 9422
ServiceAturan bisnisNIM sudah dipakai mahasiswa lain409
DatabaseConstraint tabelUNIQUE pada nimerror Prisma

Mengapa Database Tetap Perlu Menjaga?

Service sudah memeriksa NIM kembar sebelum menyimpan. Tetapi bayangkan dua permintaan dengan NIM yang sama tiba bersamaan: keduanya memeriksa, keduanya belum menemukan NIM itu, lalu keduanya menyimpan. Yang menyelamatkan data adalah UNIQUE di database: penyimpanan kedua ditolak. Prisma melaporkannya sebagai error dengan kode P2002:

code: P2002 | name: PrismaClientKnownRequestError

Kalau dibiarkan, error ini akan sampai ke errorHandler sebagai error tak dikenal dan dijawab 500, padahal ini kesalahan klien (409). Tangkap dan terjemahkan di service:

// src/services/mahasiswa.service.js
export async function buatMahasiswa(input) {
    if (await data.cariByNim(input.nim)) {
        throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
    }

    try {
        return await data.simpan(input);
    } catch (err) {
        if (err.code === 'P2002') {   // kode Prisma untuk pelanggaran UNIQUE
            throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
        }
        throw err;   // error lain diteruskan ke errorHandler (Pertemuan 5)
    }
}

Prisma juga menolak tipe data yang salah, misalnya teks untuk kolom Float: Argument `ipk`: Invalid value provided. Expected Float, provided String. Karena Joi sudah menyaringnya lebih awal, error ini hampir tidak pernah sampai ke Prisma.

Pembagian tanggung jawab: Joi memberi pesan yang ramah dan lengkap sebelum permintaan menyentuh database. Constraint database (UNIQUE, NOT NULL) adalah jaring pengaman terakhir, bukan satu-satunya validasi.

Sekarang api-mahasiswa dari Pertemuan 5 kita sambungkan ke database, memakai langkah yang sudah dilatih di Section 2. Idenya: ganti lapis data/mahasiswa.data.js (array di memori) menjadi Prisma. Yang berubah dan tidak berubah:

Langkah 5 — Ganti lapis data (bukan service!)

// src/data/mahasiswa.data.js — SEKARANG memakai Prisma
import { prisma } from '../lib/prisma.js';

export function semua() {
    return prisma.mahasiswa.findMany();
}

export function cariById(id) {
    return prisma.mahasiswa.findUnique({ where: { id } });
}

export function cariByNim(nim) {
    return prisma.mahasiswa.findUnique({ where: { nim } });
}

export function simpan(input) {
    return prisma.mahasiswa.create({ data: input });
}
Perhatikan: nama dan bentuk fungsi (semua(), cariById(), cariByNim(), simpan()) sama persis dengan versi array. Controller dan routes tidak tahu bahwa data kini berasal dari database. Inilah manfaat memisahkan lapis data sejak Pertemuan 5.

Langkah 6 — Tambahkan await di service

Satu hal yang memang harus disesuaikan: Prisma selalu mengembalikan promise, sedangkan fungsi data versi array mengembalikan nilai langsung. Tanpa await, service bekerja dengan promise, bukan dengan datanya:

  • semua.filter(...) gagal karena promise tidak punya filter: GET /mahasiswa?semester=4 menjawab 500.
  • if (data.cariByNim(...)) selalu benar karena promise adalah objek: setiap POST dianggap NIM kembar.
// src/services/mahasiswa.service.js
import * as data from '../data/mahasiswa.data.js';
import { AppError } from '../utils/AppError.js';

export async function daftarMahasiswa({ semester }) {
    const semua = await data.semua();                       // ← await
    return semester
        ? semua.filter(m => m.semester === Number(semester))
        : semua;
}

export async function detailMahasiswa(id) {
    const m = await data.cariById(Number(id));              // ← await
    if (!m) {
        throw new AppError(404, 'Mahasiswa tidak ditemukan', 'NOT_FOUND');
    }
    return m;
}

export async function buatMahasiswa(input) {
    if (await data.cariByNim(input.nim)) {                  // ← await
        throw new AppError(409, `NIM ${input.nim} sudah terdaftar`, 'NIM_DUPLIKAT');
    }
    return data.simpan(input);
}

Langkah 7 — Uji

Jalankan npm run dev, lalu ulangi seluruh permintaan di requests.http dari Pertemuan 5 (atau Postman). Hasil yang diharapkan:

PermintaanHasil
GET /mahasiswa?semester=4200, hanya Citra
GET /mahasiswa/99404 NOT_FOUND
POST /mahasiswa dengan NIM baru + x-api-key201
POST /mahasiswa dengan NIM yang sudah ada409 NIM_DUPLIKAT

Lalu dua pembuktian: (1) matikan dan nyalakan ulang server, GET /mahasiswa masih menampilkan mahasiswa yang baru ditambah; (2) buka phpMyAdmin, mahasiswa itu ada di tabel mahasiswa.

Kolom createdAt untuk baris yang ditambah lewat API bisa berselisih beberapa jam dengan baris yang diisi lewat phpMyAdmin. Prisma menyimpan waktu dalam UTC, sedangkan CURRENT_TIMESTAMP di MySQL mengikuti zona waktu server MySQL. Ini wajar dan belum perlu dikhawatirkan sekarang.
Selesai kalau: semua permintaan memberi hasil seperti tabel di atas, data bertahan setelah restart, dan kalian bisa menunjukkan datanya di phpMyAdmin.

Latihan Mandiri

  1. Tambahkan model Nilai dengan relasi satu-ke-banyak ke Mahasiswa (Section 3.1), lalu jalankan migrasi baru.
  2. Tambahkan endpoint GET /mahasiswa/:id/nilai yang mengembalikan mahasiswa beserta seluruh nilainya (pakai include).
  3. Sementara matikan pemeriksaan cariByNim di service, kirim NIM kembar, lalu pastikan error P2002 tetap menjadi 409 (Section 4). Kembalikan pemeriksaannya.
  4. Ubah IPK seorang mahasiswa langsung di phpMyAdmin, lalu buktikan perubahannya muncul lewat GET /mahasiswa/:id.
Menuju Pertemuan 7: pertemuan berikutnya menambahkan relasi banyak-ke-banyak sungguhan (pendaftaran mahasiswa ke kelas), kueri lanjutan (paginasi, filter, urut), dan transaksi, supaya operasi yang menyentuh lebih dari satu tabel aman dari kegagalan sebagian.
