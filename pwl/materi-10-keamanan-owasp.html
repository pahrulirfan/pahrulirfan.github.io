1. OWASP Top 10 Indikator 5.4

Minggu lalu kalian membangun autentikasi. Minggu ini kalian menyerang dan memperbaiki API kalian sendiri, sekaligus berkenalan dengan tool yang dipakai orang keamanan sungguhan untuk pekerjaan semacam ini. Yang penting bukan menghafal namanya, melainkan tahu apa yang sebenarnya diperiksa masing-masing tool, dan di mana batas kemampuannya.

Aturan etika yang wajib dipahami: seluruh latihan penyerangan pada mata kuliah ini hanya boleh dilakukan terhadap API buatan sendiri atau OWASP Juice Shop (Section 4) yang memang dirancang untuk diserang. Menyerang sistem milik pihak lain tanpa izin adalah tindak pidana menurut UU ITE.

1.1 Apa Itu OWASP, dan Bagaimana Top 10 Disusun

OWASP (Open Worldwide Application Security Project) adalah yayasan nonprofit yang menaungi ratusan proyek keamanan aplikasi secara terbuka — bukan vendor yang menjual produk. Selain daftar Top 10, OWASP juga menaungi ZAP (Section 3.1), Juice Shop (Section 4), Cheat Sheet Series (dirujuk sejak Pertemuan 9), ASVS (Application Security Verification Standard, daftar kontrol keamanan yang jauh lebih rinci dari Top 10), dan Dependency-Check (sepupu npm audit untuk ekosistem Java/.NET). Semuanya open source, ditulis dan direview oleh komunitas praktisi keamanan di seluruh dunia secara sukarela.

Top 10 itu sendiri bukan opini tim penulisnya. Edisi 2021 (yang jadi acuan utama di pertemuan ini) disusun dari sekitar 125.000 CVE (celah yang tercatat resmi) yang dipetakan ke hampir 400 CWE (Common Weakness Enumeration, katalog jenis kesalahan kode generik; satu CWE bisa melahirkan ribuan CVE berbeda). Delapan dari sepuluh kategori dipilih murni dari data itu — diberi skor Exploitability (seberapa mudah dieksploitasi) dan Impact (seberapa parah akibatnya) berdasarkan CVSS pada CVE-CVE yang terpetakan ke CWE-nya. Dua kategori sisanya dipilih dari survei terhadap ratusan praktisi keamanan, untuk menangkap risiko yang baru muncul tetapi belum banyak tercatat sebagai CVE. Karena disusun dari data sebanyak itu, daftarnya terasa representatif — bukan cuma opini sepihak tim penulisnya.

Kenapa dikelompokkan per kategori, bukan per CVE? Satu CWE (misalnya “tidak memeriksa otorisasi”) bisa muncul di ribuan aplikasi berbeda dengan detail yang berbeda-beda. Mengelompokkan per akar masalah (root cause) membuat satu pelajaran bisa dipakai mencegah banyak celah sekaligus, bukan menghafal daftar insiden satu per satu.

1.4 Contoh Konkret: Broken Access Control (A01)

Ini kategori vulnerability paling sering ditemukan mahasiswa pada API mereka sendiri — sering karena lupa, bukan karena tidak tahu caranya. A01 juga kategori dengan insidensi tertinggi di data CVE 2021: hampir 94% aplikasi yang diuji OWASP punya setidaknya satu bentuk broken access control.

// ❌ RENTAN — endpoint sensitif tanpa proteksi apa pun
router.delete('/mahasiswa/:id', ctrl.hapus);   // siapa saja bisa hapus data!

// ❌ RENTAN — IDOR (Insecure Direct Object Reference)
// endpoint memeriksa LOGIN, tapi tidak memeriksa KEPEMILIKAN data
router.get('/pesanan/:id', butuhLogin, async (req, res) => {
    const pesanan = await prisma.pesanan.findUnique({ where: { id: Number(req.params.id) } });
    res.json({ data: pesanan });   // user A bisa lihat pesanan milik user B!
});

// ✅ AMAN — proteksi DAN kepemilikan diperiksa
router.delete('/mahasiswa/:id', butuhLogin, butuhRole('admin'), ctrl.hapus);

router.get('/pesanan/:id', butuhLogin, async (req, res, next) => {
    const pesanan = await prisma.pesanan.findUnique({ where: { id: Number(req.params.id) } });
    if (pesanan.userId !== req.user.id) {
        return next(new AppError(403, 'Bukan milik Anda', 'FORBIDDEN'));   // cek KEPEMILIKAN
    }
    res.json({ data: pesanan });
});
IDOR (Insecure Direct Object Reference) adalah pola A01 yang paling sering luput: endpoint memeriksa apakah pengguna login, tetapi lupa memeriksa apakah data itu memang miliknya. Cukup mengganti angka di URL (/pesanan/5 menjadi /pesanan/6), penyerang bisa melihat data orang lain.

Satu prinsip menutup seluruh kategori A01: default-deny. Anggap setiap endpoint baru tertutup sampai ada alasan jelas untuk membukanya — role tertentu, kepemilikan data, atau memang publik — bukan sebaliknya. butuhLogin dan butuhRole dari Pertemuan 9 adalah cara menuliskan alasan itu secara eksplisit di setiap baris route, bukan membiarkannya jadi asumsi yang mudah terlewat.

1.5 Cryptographic Failures (A02): Bukan Cuma Soal Password

Kategori ini mencakup semua kegagalan melindungi data yang seharusnya rahasia, bukan hanya password. Tiga pola yang relevan untuk REST API kita:

PolaContohSudah dicegah di materi mana
Password tidak di-hashKolom passwordHash ternyata berisi teks biasaPertemuan 9.1 (bcrypt)
Secret lemah atau ter-commitJWT_SECRET=secret, atau ter-push ke GitHubPertemuan 9.4.3, Section 2.4 & 3.3
Data sensitif lewat HTTP polosLogin dikirim tanpa HTTPS, bisa disadap di jaringan publikDibahas lagi Pertemuan 14 (deploy)
Algoritma JWT none. Spesifikasi JWT membolehkan header {"alg":"none"}, yang berarti “token ini tidak ditandatangani”. Beberapa library lama (bukan jsonwebtoken versi yang kita pakai) secara keliru tetap menerima token semacam ini kalau dipanggil tanpa menyebut algoritma yang diizinkan. Ini bukan celah di JWT sebagai konsep, melainkan di implementasi yang longgar — jwt.verify(token, secret) milik jsonwebtoken aman karena secara default menolak alg: none.

1.6 Authentication Failures (A07): Celah di Luar Logika Login

Login dan registrasi kalian di Pertemuan 9 sudah benar secara logika (password di-hash, pesan error disamakan). A07 mencakup hal-hal di sekitar logika itu yang sering terlewat:

  • Tidak ada pembatasan percobaan — endpoint login dicoba ribuan kali per detik (brute-force), ditutup dengan rate limiting (Section 2.3).
  • Session/token tidak pernah expired — token yang bocor sekali berlaku selamanya. Pertemuan 9 menutup ini dengan expiresIn.
  • Credential stuffing — penyerang mencoba kombinasi email/password yang bocor dari situs lain (manusia sering memakai password yang sama di banyak tempat). Rate limiting membantu, tetapi mitigasi penuhnya butuh MFA (multi-factor authentication) — di luar cakupan wajib mata kuliah ini.
  • Pesan error yang membedakan — “email tidak ada” vs “password salah” membocorkan email mana yang terdaftar (user enumeration, sudah ditutup di Pertemuan 9.3.3).

1.7 Security Logging and Alerting Failures (A09): Kalau Insiden Terjadi, Apa yang Kalian Punya?

Sembilan kategori sebelumnya soal mencegah serangan; kategori ini soal apa yang terjadi kalau pencegahannya gagal atau dicoba ditembus. logger middleware dari Pertemuan 5 mencatat setiap request ke terminal (method, URL, status, durasi), dan itu sudah modal awal yang baik — tapi tiga hal berikut biasanya masih hilang pada proyek mahasiswa:

Yang sering hilangAkibatnya
Log tidak menyebut siapa (user id) yang melakukan aksiData berubah, tidak ada yang bisa ditanyai “kamu yang mengubah ini?”
Log hanya di terminal, hilang saat server restartInsiden minggu lalu tidak bisa ditelusuri lagi hari ini
Tidak ada yang memantau log secara aktifPercobaan login gagal 10.000 kali tidak memicu siapa pun sampai data sudah bocor — bedanya logging (mencatat) dan alerting (memberi tahu), penekanan baru di edisi 2025
Untuk skala mata kuliah ini, log ke terminal (atau file) yang menyertakan req.user?.id di setiap baris sudah menunjukkan kesadaran akan A09. Di produksi sungguhan, log dikirim ke layanan terpusat (misalnya ELK Stack atau Datadog) yang bisa memicu alert otomatis — dibahas sebagai pengayaan, bukan kewajiban.

2. Header Keamanan, CORS, Rate Limiting & Pengelolaan Secret Indikator 5.4

2.1 Header Keamanan dengan Helmet

helmet tidak menguji apa pun; ia hanya menambahkan header respons yang membatasi apa yang boleh dilakukan browser terhadap halaman/API kalian. Satu baris memasang lebih dari sepuluh header sekaligus:

$ npm install helmet
import helmet from 'helmet';
app.use(helmet());

Header yang benar-benar terkirim setelah helmet() dipasang (hasil tangkapan sungguhan dari endpoint lokal, bukan daftar dari dokumentasi):

Content-Security-Policy: default-src 'self';base-uri 'self';font-src 'self' https: data:;form-action 'self';frame-ancestors 'self';img-src 'self' data:;object-src 'none';script-src 'self';script-src-attr 'none';style-src 'self' https: 'unsafe-inline';upgrade-insecure-requests Cross-Origin-Opener-Policy: same-origin Cross-Origin-Resource-Policy: same-origin Origin-Agent-Cluster: ?1 Referrer-Policy: no-referrer Strict-Transport-Security: max-age=31536000; includeSubDomains X-Content-Type-Options: nosniff X-DNS-Prefetch-Control: off X-Download-Options: noopen X-Frame-Options: SAMEORIGIN X-Permitted-Cross-Domain-Policies: none X-XSS-Protection: 0
HeaderMencegah
Content-Security-PolicyScript asing yang disuntikkan lewat XSS dijalankan browser (hanya sumber dari 'self' yang dipercaya)
Strict-Transport-SecurityKoneksi turun ke HTTP biasa (bukan HTTPS) selama 1 tahun (max-age=31536000 detik) ke depan

Mengapa ini kategori A05 (Security Misconfiguration), bukan A02/A03? Tidak ada bug di kode kalian; API-nya berjalan sempurna secara fungsional. Masalahnya murni konfigurasi yang dilewatkan, dan itu memang persis definisi A05: pengaturan keamanan yang tersedia tapi tidak diaktifkan.

2.2 CORS: Siapa Boleh Memanggil API Kita

Browser punya aturan bawaan bernama Same-Origin Policy: JavaScript yang berjalan di domain A tidak boleh membaca respons dari domain B, kecuali domain B mengizinkannya secara eksplisit. Sejak Pertemuan 1 arsitektur kita memang dua proyek terpisah (backend di localhost:3000, frontend React nanti di localhost:5173 — dua origin yang berbeda), jadi tanpa izin eksplisit, browser akan menolak respons API sebelum sampai ke kode React, walau request-nya sendiri sukses di sisi server.

$ npm install cors
import cors from 'cors';

app.use(cors({ origin: 'http://localhost:5173' }));   // hanya origin ini yang diizinkan
cors() tanpa argumen mengizinkan SEMUA origin (header Access-Control-Allow-Origin: *). Itu nyaman saat belajar, tetapi di produksi berarti situs mana pun di internet bisa memanggil API kalian langsung dari browser korban yang sudah login — persis definisi A05 Security Misconfiguration. Selalu sebutkan origin secara eksplisit sebelum deploy (dibahas lagi Pertemuan 14).

Satu detail yang sering membingungkan: untuk request tertentu (misalnya DELETE, atau yang membawa header Authorization), browser mengirim request OPTIONS dulu secara otomatis sebelum request aslinya — disebut preflight — untuk bertanya ke server “method dan header apa yang kamu izinkan dari origin ini?”. Middleware cors menjawab preflight ini otomatis; kalian tidak perlu menulis handler OPTIONS sendiri.

2.3 Rate Limiting

Tanpa pembatasan, endpoint login bisa dicoba ribuan kali per detik (serangan brute-force, A07 — Section 1.6).

$ npm install express-rate-limit
import rateLimit from 'express-rate-limit';

const batasLogin = rateLimit({
    windowMs: 15 * 60 * 1000,   // 15 menit
    max: 5,                        // maksimal 5 percobaan per IP
    message: { error: { pesan: 'Terlalu banyak percobaan, coba lagi nanti' } }
});

router.post('/auth/login', batasLogin, ctrl.login);

express-rate-limit menghitung mundur fixed window: setiap IP diberi jatah 5 request per 15 menit, dan jatahnya di-reset total begitu jendela waktu berakhir (bukan “5 request dalam 15 menit terakhir” yang bergeser terus). Cukup untuk login, karena pengguna sah jarang butuh lebih dari 5 kali percobaan dalam 15 menit.

Kalau secret sudah pernah ter-commit ke Git, mengganti isinya SAJA TIDAK CUKUP. Secret itu tetap ada di riwayat commit lama dan bisa ditemukan siapa saja yang meng-clone repository. Nilai yang bocor harus diganti sepenuhnya (rotate), dan idealnya riwayat Git dibersihkan.

Untuk skala mata kuliah ini, file .env yang benar di .gitignore sudah cukup. Tim di luar kelas yang mengelola banyak secret dan banyak lingkungan biasanya memakai secret manager khusus — HashiCorp Vault, Doppler, atau fitur bawaan platform seperti AWS Secrets Manager — supaya secret tidak pernah tersimpan sebagai file sama sekali, hanya diambil saat runtime dan tercatat siapa yang mengaksesnya kapan.

3. Scan Otomatis & Pengujian Manual Indikator 5.4

Empat tool di bawah ini saling melengkapi, masing-masing menutupi sisi yang berbeda. Tidak satu pun yang cukup dipakai sendirian, seperti akan terlihat di tabel perbandingan Section 3.5.

3.1 OWASP ZAP: Baseline Scan vs Full Scan

ZAP (Zed Attack Proxy) adalah proyek flagship OWASP sendiri (Section 1.1): sebuah proxy yang diposisikan di antara client dan server, sehingga bisa membaca, menganalisis, dan (kalau diminta) memodifikasi setiap request/response yang lewat. Cara kerjanya dua tahap:

  1. Spider — ZAP merayapi API kalian untuk menemukan endpoint apa saja yang ada, mirip cara Google mengindeks halaman web.
  2. Scan — setiap endpoint yang ditemukan diperiksa. Perbedaan baseline dan full ada di tahap ini.
 Baseline scanFull scan
Jenis pemeriksaanPassive — hanya mengamati response yang wajar, tidak mengirim payload anehPassive + Active — benar-benar mengirim payload mencoba menembus (SQLi, XSS, dsb)
Aman untukAPI mana pun, termasuk yang sedang berjalan normal di localhostHanya lingkungan development/staging — active scan bisa membuat data tidak valid, bahkan membuat server crash
Biasa dipakai diSetiap kali commit (CI), karena cepat dan amanSesekali, manual, saat punya waktu memeriksa lebih dalam

Perintah di bawah menjalankan baseline scan (karena itu yang aman kita coba sekarang) lewat image Docker resmi ZAP:

$ docker run -t zaproxy/zap-stable zap-baseline.py \ -t http://host.docker.internal:3000 -r laporan-zap.html ... scanning endpoint ... WARN-NEW: Missing Anti-clickjacking Header [10020] x 3 WARN-NEW: X-Content-Type-Options Header Missing [10021] x 5 PASS: SQL Injection [40018] FAIL-NEW: 0 FAIL-INPROG: 0 WARN-NEW: 2 WARN-INPROG: 0 INFO: 0 IGNORE: 0 PASS: 42

Angka di kurung siku ([10020], [40018]) adalah Rule ID ZAP, bisa dicari di dokumentasinya untuk penjelasan lengkap dan cara perbaikan. PASS: SQL Injection [40018] di atas konsisten dengan yang sudah kita pelajari di Pertemuan 6: Prisma memang menolak percobaan SQL injection selama tidak memakai $queryRawUnsafe.

Endpoint yang butuh login bagaimana? ZAP tidak otomatis tahu cara login ke API kalian. Tanpa konfigurasi tambahan, ia hanya bisa men-scan endpoint yang terbuka (seperti POST /auth/login sendiri). Men-scan endpoint di belakang butuhLogin butuh authentication context (ZAP diberi tahu cara mendapat token lebih dulu) — di luar cakupan wajib mata kuliah ini, tetapi perlu kalian ketahui keterbatasannya: baseline scan default tidak otomatis menguji GET /mahasiswa yang terproteksi.
Catatan: baseline scan ZAP dijalankan lewat paket distribusi resminya (bisa via Docker atau distribusi mandiri) — bukan menyerang sistem produksi siapa pun, hanya API lokal kalian sendiri di localhost.

3.2 Audit Dependency: npm audit

Library pihak ketiga (dari npm install) bisa mengandung vulnerability yang sudah diketahui publik. Ini persis A06 Vulnerable & Outdated Components dari Section 1.3. npm audit mencocokkan nama dan versi setiap package di node_modules kalian dengan GitHub Advisory Database, database celah yang dikumpulkan dari laporan GitHub, National Vulnerability Database (NVD), dan tim keamanan npm sendiri.

$ npm audit # npm audit report lodash <4.17.21 Severity: high Prototype Pollution - https://github.com/advisories/GHSA-... 3 vulnerabilities (1 moderate, 2 high) $ npm audit fix
SeverityArtinya
criticalMudah dieksploitasi, akibatnya parah (misalnya remote code execution)
highSerius, tapi butuh kondisi tertentu untuk dieksploitasi
moderateBerdampak terbatas, atau butuh akses yang sudah lumayan tinggi
low / infoRisiko kecil, sering berupa potensi, bukan eksploitasi langsung
npm audit fix --force bukan tombol aman. npm audit fix biasa hanya menaikkan versi patch/minor yang seharusnya tidak merusak apa pun (mengikuti semver). --force akan menaikkan ke versi major kalau itu satu-satunya cara menutup celahnya — dan versi major sering mengandung breaking change. Setelah --force, jalankan ulang seluruh test (Pertemuan 13) sebelum percaya aplikasinya masih berjalan.

Dependency yang rentan juga tidak harus salah satu yang kalian npm install langsung. express bisa saja aman, tapi salah satu dependency dari dependency-nya (disebut transitive dependency, tersembunyi beberapa lapis di node_modules) yang bermasalah. npm audit memeriksa seluruh pohon dependency, bukan hanya yang disebut di package.json. Tool komersial seperti Snyk atau Socket.dev melakukan hal serupa dengan database yang lebih luas dan integrasi CI yang lebih kaya; GitHub juga menawarkan Dependabot yang otomatis membuka pull request saat dependency kalian punya celah baru.

3.3 Secret Scan: gitleaks

Memeriksa apakah pernah ada .env, API key, atau password yang ter-commit tanpa sengaja (Section 2.4). Cara kerjanya dua lapis:

  1. Pencocokan pola (regex) — setiap rule gitleaks punya pola untuk bentuk kredensial yang dikenal (API key AWS, token GitHub, dsb punya format yang khas dan mudah dikenali).
  2. Entropy — untuk nilai yang tidak punya format khas (seperti password bebas), gitleaks mengukur keacakan teksnya (entropi Shannon). Teks acak seperti hasil randomBytes punya entropi tinggi; teks seperti "contoh-password-123" atau placeholder dokumentasi punya entropi lebih rendah dan bisa diabaikan lewat allowlist, mengurangi false positive.
$ npx gitleaks detect --source . -v Finding: DATABASE_URL=postgresql://postgres:rahasia123@... Secret: rahasia123 File: .env Line: 2 Commit: a1b2c3d 3:41PM WARN 1 leaks found

Kolom Commit di output itu menunjukkan bahwa gitleaks memeriksa seluruh riwayat Git, bukan hanya file yang ada sekarang — sejalan dengan peringatan di Section 2.4: menghapus .env dari commit terbaru tidak menghapusnya dari riwayat lama.

gitleaks mendeteksi setelah secret ter-commit. Pencegahan yang lebih awal dipasang sebagai pre-commit hook (lewat tool seperti husky) yang menjalankan gitleaks otomatis sebelum commit diterima, sehingga secret tidak pernah sampai masuk ke riwayat sama sekali. Tool sejenis lain: truffleHog dan detect-secrets.

3.4 Pengujian Manual dengan Postman

ZAP, npm audit, dan gitleaks mendeteksi pola umum, tapi tidak satu pun memahami logika bisnis aplikasi kalian — seperti IDOR pada Section 1.4, yang hanya ketahuan kalau penguji tahu persis “pesanan id 5 itu milik user mana”. Postman, yang sudah kalian pakai sejak Pertemuan 6, berperan di sini sebagai alat uji manual, bukan sekadar pengganti curl.

Tiga fitur Postman yang membuat pengujian manual sistematis, bukan sekadar klik Send berulang:

FiturGunanya untuk uji keamanan
Environment & VariableSimpan token hasil login sebagai variable (misalnya {{token}}); ganti satu nilai, semua request terproteksi ikut terupdate — penting saat menguji dengan token milik role berbeda (mahasiswa vs admin)
CollectionKumpulan request tersimpan dan berurutan; cocok untuk mencatat langkah reproduksi sebuah temuan agar bisa diulang orang lain persis sama
Collection RunnerMenjalankan seluruh collection berurutan sekali klik — berguna untuk mengulang satu skenario (misalnya brute-force 5 percobaan login) tanpa mengirim satu per satu secara manual

Contoh konkret menguji IDOR dari Section 1.4 di Postman: login sebagai dua user berbeda, simpan masing-masing token sebagai variable terpisah, lalu coba akses resource milik user A memakai token user B.

Tampilan Postman (ilustrasi; Authorization: Bearer {{tokenUserB}}, bukan milik pemesan)
GEThttp://localhost:3000/pesanan/5Send
Response200 OK
{ "data": { "id": 5, "userId": 3, "item": "..." } }

Respons 200 di atas adalah temuannya: token user B seharusnya ditolak (403), bukan diterima. Ganti ID, ganti token, catat responsnya — itu saja sudah jadi langkah reproduksi yang bisa diulang orang lain.

4. Laboratorium OWASP Juice Shop Indikator 5.4 & 5.5

OWASP Juice Shop adalah toko online tiruan yang sengaja dibuat penuh lubang keamanan untuk latihan — proyek flagship OWASP sendiri (Section 1.1), bukan buatan pihak ketiga. Bedanya dengan contoh kode di Section 1: di sana kalian membaca potongan route yang rentan, di Juice Shop kalian benar-benar menemukan dan mengeksploitasi lubangnya sendiri di aplikasi yang berjalan nyata, tanpa melihat kodenya dulu.

4.1 Menjalankan Juice Shop

Cara paling sederhana tetap lewat image Docker resminya, sama seperti ZAP di Section 3.1:

$ docker run -d -p 3000:3000 bkimminich/juice-shop

Buka http://localhost:3000 setelah container berjalan. Kalau ingin versi tertentu (bukan yang paling baru), ganti tag image-nya, misalnya bkimminich/juice-shop:v17.0.0. Dua cara lain yang juga resmi kalau tidak mau memakai Docker: clone repository juice-shop/juice-shop di GitHub lalu jalankan npm install && npm start, atau unduh paket rilis siap pakai dari halaman Releases repository tersebut.

4.2 Score Board, Tingkat Kesulitan, dan Hint

Juice Shop tidak menampilkan daftar tantangannya begitu saja di halaman utama — kalian harus menemukan Score Board-nya sendiri dulu, dan itu sebenarnya tantangan pertamanya (klik ikon topi toga di banner selamat datang, atau cari linknya yang disembunyikan di HTML halaman). Begitu ditemukan, Score Board itu jadi pusat latihannya:

  • Daftar tantangan dikelompokkan per kategori OWASP (Broken Access Control, Injection, Security Misconfiguration, dst.), persis kategori yang sudah dibahas di Section 1.
  • Tingkat kesulitan ditandai 1 sampai 6 bintang. Mulai dari bintang 1–2 dulu; beberapa tantangan berbintang tinggi butuh teknik di luar cakupan mata kuliah ini.
  • Tombol hint (ikon topi toga juga) muncul di tiap tantangan kalau kalian benar-benar buntu. Boleh dipakai, tetapi coba dulu tanpa hint — proses mencari sendiri itu yang melatih kepekaan terhadap celah.
  • Tantangan yang berhasil diselesaikan otomatis tercoret di Score Board, jadi progres kalian selalu terlihat tanpa perlu mencatat manual.
