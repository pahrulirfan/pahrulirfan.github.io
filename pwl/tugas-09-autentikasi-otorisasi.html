Menambahkan Login pada Proyek ETS Tugas 9

Tujuan: menambahkan register, login (password di-hash, token JWT), dan pembagian halaman publik dan wajib login pada proyek ETS kalian sendiri. Rujukan langkahnya ada di Materi 9, Section 1–4 (di materi dikerjakan pada api-mahasiswa; di tugas ini pada proyek ETS).

Proyek Dasar

Kerjakan di atas REST API Mini Project ETS kalian (kasus kalian sendiri: Books, Students, Orders, dan seterusnya). Di bawah ini tabel utama ETS ditulis /resource; ganti dengan nama resource kalian (mis. /books).

  1. Salin folder proyek ETS ke folder baru tanpa .git dan node_modules, lalu jalankan npm install.
  2. Buat repository baru T9-AUTENTIKASI untuk folder itu (repository ETS tidak diubah, supaya nilai ETS tetap utuh).
  3. Boleh memakai database ETS yang sama. Tabel dan migrasi lama tidak diubah; kalian hanya menambah tabel users.
Cek terlebih dahulu apakah Proyek ETS sudah bisa dijalankan di folder baru jika belum silahkan perbaiki dulu. atau bisa menggunakan project api-mahasiswa dari Materi 7 dengan resource /mahasiswa.

Bagian 1 — Endpoint Autentikasi

MethodURLSyaratHasil
POST/auth/registerbody email, password201 berisi { id, email }; 409 EMAIL_DUPLIKAT; 422 VALIDATION_ERROR
POST/auth/loginbody email, password200 berisi { token }; 401 LOGIN_GAGAL
GET/auth/sayawajib login200 berisi data dari token (id); 401 bila tanpa token
Hal yang diperiksaAturan
Validasi (Joi)email: format email, maksimal 100 karakter, wajib. password: string 8–72 karakter, wajib. Kalau tidak sesuai, 422.
PasswordDisimpan sebagai hash bcrypt (cost 10) di kolom passwordHash. Hash tidak pernah ikut dikirim ke client.
Pesan login gagalEmail tidak terdaftar dan password salah dijawab sama persis: 401, LOGIN_GAGAL, “Email atau password salah”.
TokenJWT berisi { id }, expiresIn: '2h', ditandatangani dengan secret buatan kalian sendiri.

Bagian 2 — Tabel users dan Akun Uji

  • Tabel users dengan kolom id, email (unik), passwordHash, dan createdAt. Satu jenis pengguna saja, tanpa role. Cara membuatnya bebas: lewat model Prisma + migrasi baru (npx prisma migrate dev --name tambah_user, seperti Materi 9, 4.2), atau langsung dengan SQL/phpMyAdmin. Kalau dibuat langsung, sertakan SQL CREATE TABLE-nya di README.
  • Tidak perlu seeder. Akun uji dibuat lewat endpoint /auth/register.
  • Secret JWT: nilai dan cara menyimpannya kalian tentukan sendiri.
Repository ini public. Password akun uji yang kalian tulis di README harus password sembarang untuk tugas (bukan password email, media sosial, atau Berajah kalian).

Bagian 3 — Halaman Publik dan Halaman Wajib Login

Buat src/middleware/auth.js berisi butuhLogin (pola Materi 9, Section 3.3 dan 4.6). Middleware ini membaca header Authorization: Bearer ..., memeriksa token dengan jwt.verify, dan mengirim error lewat next(new AppError(...)) ke errorHandler terpusat dari ETS:

SituasiStatusKode
Header Authorization tidak ada atau bukan Bearer401TOKEN_DIPERLUKAN
Token rusak, signature salah, atau expired401TOKEN_TIDAK_VALID

Format error tetap seragam: { error: { pesan, kode } }. Setelah itu bagi endpoint proyek ETS menjadi dua kelompok. Pasang middleware di route (bukan di controller atau service), sebelum validasi: butuhLogin → validasi → controller.

KelompokEndpoint ETSTanpa tokenDengan token valid
PublikPOST /auth/register, POST /auth/login, GET /resource (daftar), GET /resource/:id, endpoint tabel kedua (include)BerhasilBerhasil
Wajib loginGET /auth/saya, POST /resource, PUT /resource/:id, DELETE /resource/:id, endpoint transaksi dua tabel401Berhasil
Jebakan dari materi: endpoint publik tidak boleh dipasangi butuhLogin; mengambil keputusan dari jwt.decode (harus jwt.verify); lupa select sehingga passwordHash ikut terkirim; bcrypt.compare itu async (lupa await membuat semua password dianggap benar); password lebih dari 72 karakter terpotong oleh bcrypt.

Bagian 4 — Dua Percobaan Wajib

Seperti di ETS, kalian sengaja membuat sesuatu gagal lalu menjelaskan akibatnya. Keduanya didokumentasikan di README (hasil, screenshot, dan 2–3 kalimat penjelasan dengan kata-kata sendiri):

NoPercobaanYang harus terlihat
1Token dipalsukan. Login, lalu ganti payload token (mis. id menjadi angka lain) dengan Base64 manual atau jwt.io tanpa mengetahui secret, dan kirim ke endpoint wajib login.401 TOKEN_TIDAK_VALID. Jelaskan kenapa payload bisa dibaca dan diubah siapa saja, tetapi tetap ditolak.
2Token expired. Ubah sementara expiresIn menjadi '5s', login, tunggu 6 detik, kirim request. Kembalikan ke '2h' sebelum commit.401 TOKEN_TIDAK_VALID. Jelaskan dari mana server tahu token itu expired tanpa menyimpan catatan apa pun.

Pengujian: requests.http

Cukup tunjukkan bahwa halaman publik bisa dibuka tanpa login, sedangkan halaman wajib login (mis. tambah data) ditolak tanpa token dan berhasil dengan token. Buat requests.http (REST Client) dengan variabel @token, minimal 5 request berikut:

NoRequestHasil
1POST /auth/register201
2POST /auth/login200 berisi token (salin ke @token)
3GET /resource tanpa token (halaman publik)200
4POST /resource (tambah data) tanpa token401
5POST /resource dengan header Authorization: Bearer {{token}}201

Request lain (PUT, DELETE, endpoint transaksi, login gagal) boleh ditambahkan. Request dari dua percobaan di Bagian 4 juga dimasukkan ke file yang sama (diberi komentar ### Percobaan 1 dan seterusnya).
